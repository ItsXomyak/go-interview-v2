### 1. Чем Go отличается от других языков (Java, Python)? Почему его выбирают для backend?

**⚡ Суть за 10 секунд**
Go — компилируемый, статически типизированный язык со сборщиком мусора и конкурентностью на уровне языка ([горутины](glossary.md#goroutine) и каналы). На выходе один нативный бинарник, сборка быстрая, синтаксис простой. Поэтому Go — стандарт для сетевых backend-сервисов и облачной инфраструктуры.

**🔧 Под капотом**
- **Бинарник** = твой код + рантайм Go (планировщик, [GC](glossary.md#gc), [netpoller](glossary.md#netpoller), аллокатор), слинкованные статически. Нет VM и [JIT](glossary.md#jit-aot), как в Java, и нет интерпретатора, как в Python.
- **Горутина** — структура рантайма `g` со своим стеком от ~2 КБ, который растёт копированием. У потока ОС [стек](glossary.md#stack-heap) 1–8 МБ, а переключение идёт через ядро. Планировщик [G-M-P](glossary.md#gmp) мультиплексирует сотни тысяч горутин на [`GOMAXPROCS`](glossary.md#gomaxprocs) потоков ОС и переключает их в user space за десятки наносекунд.
- **Сетевой I/O** идёт через netpoller (epoll / kqueue / IOCP): горутина, ждущая сокет, паркуется, а поток ОС не блокируется. Отсюда модель «горутина на запрос» без callback'ов.
- **GC:** concurrent, non-generational, non-moving, tri-color mark & sweep с [write barrier](glossary.md#write-barrier). Паузы [STW](glossary.md#stw) обычно меньше 1 мс; с Go 1.26 по умолчанию работает [Green Tea GC](glossary.md#green-tea).
- **Нет [GIL](glossary.md#gil):** в отличие от Python, горутины реально выполняются параллельно на всех ядрах.

| | Go | Java | Python |
|---|---|---|---|
| Исполнение | AOT, нативный код | JVM + JIT | интерпретатор |
| Параллелизм | горутины, без GIL | потоки (+ virtual threads) | GIL мешает CPU-параллелизму |
| Старт и память | миллисекунды, мало | дольше, больше | быстро, но медленный рантайм |
| Деплой | один бинарник | JVM + jar | интерпретатор + зависимости |

**⚠️ Подвохи и версии Go**
- Не говори «Go быстрее Java» без оговорок: на долгоживущих CPU-задачах JIT может догнать. Сила Go — память, старт, предсказуемая латентность и простота.
- Горутины дешёвые, но не бесплатные: запуск без ограничения ведёт к утечкам и OOM.
- Вехи версий: 1.18 — дженерики; 1.22 — новая семантика цикла; 1.24 — [Swiss Tables](glossary.md#swiss-tables) в map; 1.25 — `GOMAXPROCS` учитывает лимит CPU в [cgroup](glossary.md#cgroup); 1.26 — Green Tea GC по умолчанию; 1.27 — generic-методы.

**🎤 Прямая речь**
> Go — компилируемый статически типизированный язык со сборщиком мусора и конкурентностью на уровне языка. На выходе один нативный бинарник, в который вшит рантайм: планировщик, GC и netpoller. Поэтому нет зависимости от VM, быстрый старт и маленькие Docker-образы, что удобно в Kubernetes.
>
> Для backend главное — горутины. Они стоят пару килобайт, планировщик G-M-P раскладывает их по потокам ОС, а сетевой I/O не блокирует потоки благодаря netpoller. Можно писать простой синхронный код «горутина на запрос» и держать десятки тысяч соединений. По сравнению с Java — меньше памяти и быстрее старт, по сравнению с Python — статическая типизация и настоящий параллелизм без GIL. Не случайно Docker, Kubernetes, etcd и Prometheus написаны на Go.

### 2. Технологические преимущества и недостатки Go

**⚡ Суть за 10 секунд**
Плюсы: простота, дешёвая конкурентность, быстрая компиляция, нативный бинарник, сильная stdlib и тулинг. Минусы: многословная обработка ошибок, слабая система типов (нет enum и sum types), ловушки с nil, накладные расходы [GC](glossary.md#gc).

**🔧 Под капотом** — почему плюсы и минусы именно такие
- **Быстрая компиляция:** нет заголовочных файлов и циклических импортов. Каждый пакет компилируется один раз в [export data](glossary.md#export-data), которую читают зависимые пакеты, а результат кэшируется.
- **Ошибки как значения:** `error` — интерфейс из двух машинных слов. Вернуть его дёшево, раскрутки [стека](glossary.md#stack-heap), как у исключений, нет. Цена — многословность.
- **GC без поколений и без перемещения объектов:** выбран ради низких пауз и простоты — раз объекты не двигаются, указатели можно безопасно отдавать в системные вызовы. Цена — больше CPU на GC при высоком темпе аллокаций; лечится уменьшением аллокаций и настройкой `GOGC` / `GOMEMLIMIT`.
- **Размер бинарника:** в него вшиты рантайм и метаданные для [рефлексии](glossary.md#reflection) и трейсбеков, поэтому даже hello world весит несколько МБ.
- **Дженерики** реализованы через [GC shape stenciling](glossary.md#gc-shape) + словари: один экземпляр кода на «форму» типов. Вызовы методов через словарь иногда медленнее полной мономорфизации, как в C++ и Rust.

| Преимущества | Недостатки |
|---|---|
| Один статический бинарник, кросс-компиляция | Многословный `if err != nil` |
| [Горутины](glossary.md#goroutine) и каналы в языке | Нет enum и типов-сумм |
| Быстрая компиляция | Дженерики с 1.18, generic-методы только с 1.27 |
| `gofmt`: единый стиль в команде | nil-указатели и typed nil в интерфейсах |
| Тесты, бенчмарки, race detector, pprof из коробки | GC: не для hard real-time |
| Мало памяти, быстрый старт | Нет неизменяемых структур и коллекций |
| Обещание совместимости Go 1 | Слабые экосистемы GUI и ML |

**⚠️ Подвохи и версии Go**
- «В Go нет ООП» — неверно. Есть инкапсуляция (экспорт по регистру), полиморфизм (интерфейсы) и композиция (встраивание); нет только наследования классов.
- Совместимость Go 1: код 2012 года собирается и сейчас. Изменения поведения управляются через [`GODEBUG`](glossary.md#godebug) и директиву `go` в `go.mod`.
- Часть минусов уже закрыли: дженерики (1.18), `errors.Join` (1.20), итераторы (1.23), generic-методы (1.27).

**🎤 Прямая речь**
> Главные плюсы Go — простота и предсказуемость. Язык маленький, код в команде выглядит одинаково благодаря `gofmt`, сборка быстрая, на выходе один бинарник. Конкурентность встроена в язык, а в стандартной поставке есть всё для продакшена: HTTP, тесты, бенчмарки, race detector, профайлер.
>
> Из минусов назову многословную обработку ошибок, бедную систему типов — нет enum и типов-сумм — и ловушки с nil, особенно typed nil в интерфейсах. GC даёт короткие паузы, но при высоком темпе аллокаций съедает CPU, так что в горячем коде приходится следить за аллокациями. Для сетевых сервисов плюсы перевешивают.

### 3. ⭐ Что огорчает в системе типов Go?

**⚡ Суть за 10 секунд**
Нет типов-сумм и настоящих enum; nil допустим для многих типов, плюс ловушка typed nil в интерфейсе; нет неизменяемости; дженерики ограничены.

**🔧 Под капотом**
- **Интерфейс в памяти — два слова:** [`iface{tab *itab, data unsafe.Pointer}`](glossary.md#interface-layout) для непустого интерфейса и `eface{_type, data}` для пустого. `err == nil` только когда **оба** слова нулевые. Если положить в `error` nil-указатель `*MyErr`, `tab` указывает на itab для `*MyErr`, а `data == nil` — и `err != nil`.
- **Enum через `iota`** — просто константы базового типа. В рантайме это int: нет проверки диапазона, а type switch не проверяет, разобраны ли все варианты.
- **Nullable по умолчанию:** аллокатор отдаёт обнулённую память, и нулевые биты для указателя, map, слайса, канала, функции и интерфейса означают nil. Типов, которые не могут быть nil, нет.
- **Дженерики:** [GC shape stenciling](glossary.md#gc-shape), нет специализации и вариантности; generic-методы появились только в 1.27.
- **Нет кортежей:** несколько результатов передаются через регистры ([register ABI](glossary.md#register-abi) с Go 1.17), но значением не являются — их нельзя положить в переменную или канал целиком.

**⚠️ Подвохи и версии Go**
```go
type MyErr struct{}

func (*MyErr) Error() string { return "boom" }

func do() error {
    var e *MyErr // nil-указатель
    return e     // интерфейс (тип=*MyErr, значение=nil)
}

fmt.Println(do() == nil) // false
```
- Лечение: в успешной ветке возвращать `nil` явно, а не переменную-указатель.
- Помогают линтеры (`nilness`, `exhaustive` для полноты switch по enum) и проверка реализации интерфейса на этапе компиляции: `var _ I = (*T)(nil)`.

**🎤 Прямая речь**
> Больше всего не хватает типов-сумм и нормальных enum: `iota` даёт просто числа, `Status(42)` скомпилируется, и компилятор не проверит, что я разобрал все варианты в switch. Второе — nil. Многие типы по умолчанию nullable, а у интерфейса есть ловушка: он состоит из двух слов, типа и значения, поэтому nil-указатель внутри интерфейса не равен nil.
>
> С этим можно жить: возвращаю `nil` явно, использую линтер `exhaustive`, для enum резервирую нулевое значение под «unknown» и добавляю валидацию. Дженерики тоже ограничены, но с 1.27 появились generic-методы, и главную боль это закрыло.

### 4. Go — императивный или декларативный? В чём разница?

**⚡ Суть за 10 секунд**
Go — императивный (процедурный) язык с элементами ООП и функционального стиля. Императивный код описывает, **как** получить результат (шаги, меняющие состояние); декларативный — **что** нужно получить, а как — решает исполнитель (SQL, HTML, манифесты Kubernetes).

**🔧 Под капотом**
- Компилятор переводит Go в [SSA](glossary.md#ssa)-представление, а затем в машинные инструкции, которые близко повторяют порядок операторов. В этом и суть императивной модели: явное состояние, присваивания, циклы.
- Декларативные элементы в экосистеме Go всё же есть:
  - struct-теги (`json:"name"`) — метаданные, которые читаются через [рефлексию](glossary.md#reflection);
  - `text/template` и SQL-строки;
  - Kubernetes-контроллеры на Go: императивный reconcile loop приводит систему к состоянию, описанному в манифесте декларативно.
- Функциональные элементы: функции первого класса, замыкания (захваченные переменные уходят в [кучу](glossary.md#stack-heap), если замыкание переживает функцию), итераторы `iter.Seq` (Go 1.23).

```go
// императивно: говорим, КАК искать
sum := 0
for _, v := range nums {
    if v > 0 {
        sum += v
    }
}
// декларативно (SQL): говорим, ЧТО нужно
// SELECT SUM(v) FROM nums WHERE v > 0;
```

**⚠️ Подвохи и версии Go**
- «Императивный vs декларативный» и «процедурный vs ООП» — разные оси классификации, их не смешивают.
- Go не функциональный язык: нет иммутабельности и не гарантируется оптимизация хвостовых вызовов ([TCO](glossary.md#tco)), поэтому глубокая рекурсия растит стек [горутины](glossary.md#goroutine).

**🎤 Прямая речь**
> Go — императивный язык: мы явно описываем последовательность шагов, которые меняют состояние программы. Декларативный подход описывает желаемый результат, а не алгоритм — как SQL, где я пишу, какие данные нужны, а планировщик БД сам решает, как их достать.
>
> При этом в Go есть элементы других парадигм: функции первого класса и замыкания из функционального стиля, методы и интерфейсы из ООП. А в экосистеме хватает декларативных вещей — struct-теги для JSON или Kubernetes-контроллеры, которые императивным кодом приводят кластер к декларативно описанному состоянию.

### 5. Какие типы есть в Go (целые, float, complex, string, bool, составные)?

**⚡ Суть за 10 секунд**
Базовые: `bool`, `string`, целые, вещественные, комплексные. Составные: массив, слайс, map, структура, указатель, функция, интерфейс, канал. Многие «ссылочные» типы на деле — небольшие заголовки с указателем внутри.

**🔧 Под капотом**

| Группа | Типы | Размер (64-бит) |
|---|---|---|
| Логический | `bool` | 1 байт |
| Целые со знаком | `int8`, `int16`, `int32`, `int64`, `int` | 1, 2, 4, 8, 8 |
| Целые без знака | `uint8`…`uint64`, `uint`, `uintptr` | 1…8, 8, 8 |
| Алиасы | `byte` = `uint8`, `rune` = `int32` | 1, 4 |
| Вещественные | `float32`, `float64` | 4, 8 |
| Комплексные | `complex64`, `complex128` | 8, 16 |

| Тип | Представление в памяти | Размер значения |
|---|---|---|
| `string` | `{ptr, len}`, данные неизменяемы, литералы лежат в [read-only секции](glossary.md#rodata) | 16 байт |
| `[]T` | `runtime.slice{array, len, cap}` | 24 байта |
| `map[K]V` | указатель на внутреннюю структуру ([Swiss Tables](glossary.md#swiss-tables) с 1.24) | 8 байт |
| `chan T` | указатель на [`runtime.hchan`](glossary.md#hchan) | 8 байт |
| `interface` | два слова: [`iface`](glossary.md#interface-layout) / `eface` | 16 байт |
| `func` | указатель на [funcval](glossary.md#funcval) (код + захваченные переменные) | 8 байт |
| `[N]T` | N элементов подряд | N × size(T) |
| `struct` | поля + [padding](glossary.md#alignment) | см. ниже |

**Выравнивание и padding.** Каждое поле выравнивается по своему размеру (`int64` — по 8, `int32` — по 4, `bool` — по 1), структура — по самому строгому полю. Поэтому порядок полей меняет размер:
```go
type Bad struct { // 24 байта
    a bool  // 1 + 7 padding
    b int64 // 8
    c bool  // 1 + 7 padding
}

type Good struct { // 16 байт
    b int64 // 8
    a bool  // 1
    c bool  // 1 + 6 padding
}
```
Проверить можно через `unsafe.Sizeof` / `Alignof` / `Offsetof` или анализатор `fieldalignment`. Подробнее — в блоке 1.6.

**⚠️ Подвохи и версии Go**
- Массив — значение: присваивание и передача копируют все элементы. `[3]int` и `[4]int` — разные типы.
- Слайс, map и канал «ведут себя как ссылки» только потому, что внутри указатель. Передаются они всё равно по значению.
- ⭐ Поле нулевого размера в конце структуры добавляет padding: `struct{ a int64; b struct{} }` занимает 16 байт, чтобы указатель на `b` не смотрел за пределы объекта.
- На 32-битных платформах 64-битным атомикам нужно выравнивание по 8; `atomic.Int64` (Go 1.19) гарантирует его сам.
- `any` — алиас `interface{}` с Go 1.18.

**🎤 Прямая речь**
> Базовые типы — `bool`, `string`, целые знаковые и беззнаковые разных размеров, `float32/64` и `complex`; `byte` и `rune` — алиасы для `uint8` и `int32`. Составные — массивы, слайсы, map, структуры, указатели, функции, интерфейсы и каналы.
>
> Важно понимать представление в памяти. Строка — это указатель плюс длина, 16 байт. Слайс — указатель, len и cap, 24 байта. Map и канал — указатели на внутренние структуры рантайма, интерфейс — два слова. Отсюда «ссылочное» поведение при передаче по значению. Для структур важен порядок полей: из-за выравнивания одна и та же структура может занимать 24 или 16 байт, это проверяется через `unsafe.Sizeof` и линтер `fieldalignment`.

### 6. Что такое zero value? Нулевые значения всех типов

**⚡ Суть за 10 секунд**
Zero value — значение, которое переменная получает без явной инициализации: `0`, `false`, `""`, `nil`, а для массивов и структур — поэлементно. Неинициализированной памяти в Go не бывает.

**🔧 Под капотом**
- Аллокатор отдаёт обнулённую память: [`mallocgc`](glossary.md#allocator) зануляет блок или берёт заранее чистый span. Слоты [стека](glossary.md#stack-heap), в которых лежат указатели, зануляются в прологе функции — иначе [GC](glossary.md#gc) принял бы мусор за живые указатели.
- Поэтому zero value — это буквально нулевые биты: для чисел это 0, для ссылочных типов — nil.
- **nil-map:** при чтении рантайм возвращает указатель на общий нулевой буфер; запись паникует (`assignment to entry in nil map`).
- **nil-слайс** — это `{nil, 0, 0}`: `len`, `range`, `append` работают, `append` сам выделит память.
- **nil-канал:** отправка и приём паркуют [горутину](glossary.md#goroutine) навсегда. В `select` такой case просто никогда не выбирается — этим отключают ветки.

| Тип | Zero value |
|---|---|
| Числа | `0` |
| `bool` | `false` |
| `string` | `""` |
| Указатель, слайс, map, канал, функция, интерфейс | `nil` |
| Массив, структура | zero value каждого элемента / поля |

**⚠️ Подвохи и версии Go**
- Идиома «make the zero value useful»: `sync.Mutex`, `sync.WaitGroup`, `bytes.Buffer`, `strings.Builder` работают без конструктора.
- Структуру с мьютексом нельзя копировать после начала использования — это ловит `go vet` (проверка copylocks).
- Zero value маскирует баги: незаполненное `Status = 0` выглядит валидным, поэтому резервируй 0 под «unknown».
- В JSON отсутствующее поле и поле с нулём неразличимы, если поле не указатель (`*int`). Для таких полей удобен `new(expr)` из Go 1.26.

**🎤 Прямая речь**
> Zero value — это значение по умолчанию, которое Go гарантирует для любой объявленной переменной: ноль для чисел, `false`, пустая строка, `nil` для указателей, слайсов, map, каналов, функций и интерфейсов, а у структур и массивов зануляется каждое поле. Под капотом аллокатор всегда отдаёт обнулённую память, поэтому неинициализированных данных в Go не бывает.
>
> Хорошая практика — делать нулевое значение рабочим, как у `sync.Mutex` или `bytes.Buffer`. Но надо помнить нюансы: nil-слайс полностью рабочий, из nil-map можно читать, а запись в неё паникует, nil-канал блокирует навсегда. И в доменных enum я резервирую ноль под «неизвестно», чтобы незаполненное поле не выглядело валидным.

### 7. `var x int`, `x := 0`, `new(int)` — в чём разница?

**⚡ Суть за 10 секунд**
`var x int` и `x := 0` создают переменную типа `int` со значением 0; `new(int)` создаёт безымянную переменную и возвращает указатель `*int`. Где окажется память — на [стеке](glossary.md#stack-heap) или в куче — решает **[escape analysis](glossary.md#escape-analysis)**, а не синтаксис.

**🔧 Под капотом**

| Запись | Тип `x` | Где можно | Особенности |
|---|---|---|---|
| `var x int` | `int` | везде, включая уровень пакета | явный тип, zero value |
| `x := 0` | `int` (выведен) | только внутри функций | слева нужна хотя бы одна новая переменная |
| `x := new(int)` | `*int` | везде, где допустимо выражение | `*x == 0` |

- **Escape analysis** работает на этапе компиляции. Если указатель не переживает функцию — не возвращается, не сохраняется в глобальную переменную или в объект в куче, не уходит в интерфейс или замыкание, которое живёт дольше вызова, — переменная остаётся **на стеке**, даже созданная через `new` или `&x`. Иначе компилятор выделяет её в куче (`runtime.newobject`), и потом её собирает [GC](glossary.md#gc).
- Лимиты стека: явно объявленная переменная — до 10 МБ; неявная (`new`, `&T{}`, `make` с константным размером) — до 64 КБ. Всё, что больше, идёт в кучу.

```go
func local() int {
    p := new(int) // не убегает → стек
    *p = 42
    return *p
}

func leak() *int {
    x := 0
    return &x // убегает → куча
}
```
Посмотреть решения компилятора: `go build -gcflags=-m` выдаст `new(int) does not escape` и `moved to heap: x`.

**⚠️ Подвохи и версии Go**
- `:=` без новых переменных слева — ошибка `no new variables on left side of :=`. А во вложенном блоке `:=` создаёт новую переменную — отсюда shadowing ([вопрос 16](#q1-1-16)).
- «Указатель — значит быстрее» — миф. Указатель может увести объект в кучу и добавить работы GC; маленькие структуры часто дешевле передавать по значению.
- Go 1.26: `new` принимает выражение — `p := new(42)`, удобно для опциональных полей-указателей.

**🎤 Прямая речь**
> `var x int` и `x := 0` дают одно и то же — переменную типа `int` со значением ноль. Разница в том, что `var` можно писать на уровне пакета и с явным типом, а короткое объявление — только внутри функций, с выводом типа. `new(int)` возвращает указатель на новую обнулённую переменную.
>
> Ключевой момент: ни `new`, ни взятие адреса не означают выделение в куче. Это решает escape analysis на этапе компиляции. Если указатель не покидает функцию, переменная остаётся на стеке, а если возвращается наружу или попадает в интерфейс — уходит в кучу и становится работой для GC. Я проверяю это через `-gcflags=-m`, когда оптимизирую горячий код.

<a id="q1-1-08"></a>
### 8. `new` vs `make`

**⚡ Суть за 10 секунд**
`new(T)` работает с любым типом: выделяет обнулённую память и возвращает `*T`. `make` работает только со слайсами, map и каналами: создаёт их внутреннюю структуру и возвращает сам `T`.

**🔧 Под капотом**
- Что вызывается в рантайме:
  - `make([]T, len, cap)` → `runtime.makeslice` (backing array через [`mallocgc`](glossary.md#allocator));
  - `make(map[K]V, hint)` → `runtime.makemap` ([Swiss Tables](glossary.md#swiss-tables) с 1.24, подсказка размера сразу выделяет таблицы);
  - `make(chan T, n)` → `runtime.makechan` ([`hchan`](glossary.md#hchan) + кольцевой буфер);
  - `new(T)` → `runtime.newobject` или слот на [стеке](glossary.md#stack-heap).
- **[Escape analysis](glossary.md#escape-analysis) работает и для `make`:** `make([]int, 8)`, который не покидает функцию, кладётся на стек (при константном размере до 64 КБ). `make` с размером из переменной исторически шёл в кучу; с Go 1.25 компилятор кладёт backing array на стек в большем числе случаев.
- **Зачем два способа:** слайс, map и канал — заголовки над внутренними структурами. Обнулённый заголовок — это nil, а nil-map и nil-канал для работы непригодны, поэтому нужна инициализация.

| | `new(T)` | `make(T, ...)` |
|---|---|---|
| Типы | любые | `slice`, `map`, `chan` |
| Возвращает | `*T` | `T` |
| Что делает | обнуляет память | создаёт backing array / хеш-таблицу / буфер канала |

```go
s := make([]int, 3, 10)        // len 3, cap 10
m := make(map[string]int, 100) // 100 — подсказка по размеру
ch := make(chan int, 5)

mp := new(map[string]int)
(*mp)["a"] = 1 // паника: внутри nil-map
```

**⚠️ Подвохи и версии Go**
- `new([]int)` и `new(map[string]int)` дают указатель на nil — почти всегда это ошибка.
- `make([]int, 10)` уже содержит 10 нулей, и `append` добавит одиннадцатый элемент. Для буфера нужно `make([]int, 0, 10)` — классическая ошибка.
- Подсказка размера для map и слайса убирает переаллокации при росте — в горячем коде это заметно.

**🎤 Прямая речь**
> `new` универсален: выделяет обнулённую память под любой тип и возвращает указатель. `make` нужен только для слайсов, map и каналов. Это заголовки над внутренними структурами рантайма, и `make` вызывает `makeslice`, `makemap` или `makechan`, чтобы создать backing array, хеш-таблицу или буфер канала. Возвращает он само значение, а не указатель.
>
> Как и с `new`, место выделения решает escape analysis: слайс фиксированного размера, который не покидает функцию, может жить на стеке. На практике я всегда передаю в `make` capacity или подсказку размера, если знаю объём, — это убирает переаллокации. И слежу за разницей между `make([]T, n)` и `make([]T, 0, n)`, это частый баг.

### 9. Отличия `int`, `int32`, `int64`. Чем `int` отличается от `uint`? От чего зависит размер `int`?

**⚡ Суть за 10 секунд**
`int32` и `int64` имеют фиксированный размер — 4 и 8 байт. `int` — машинное слово: 8 байт на 64-битных платформах, 4 на 32-битных (определяется `GOARCH`). `uint` — беззнаковый вариант того же размера. Всё это разные типы, неявных преобразований между ними нет.

**🔧 Под капотом**
- Размер `int` фиксируется при компиляции по `GOARCH`: `amd64` и `arm64` дают 64 бита, совпадающие с шириной регистра и указателя. В коде: `strconv.IntSize` или `bits.UintSize`.
- На `amd64` у `int` и `int64` одинаковое представление, поэтому конверсия между ними ничего не стоит. `int32 → int64` — инструкция расширения знака; `int64 → int32` — отбрасывание старших бит.
- Знаковые числа хранятся в [дополнительном коде](glossary.md#twos-complement) (two's complement). `uint` той же ширины использует знаковый бит под значение: диапазон `0 … 2ⁿ−1`.

```go
var a int = 1
var b int64 = a        // ошибка компиляции: разные типы
var c int64 = int64(a) // ок
var z uint
fmt.Println(z-1 == math.MaxUint) // true: беззнаковое вычитание «переворачивается»
// а константа uint(0) - 1 не скомпилируется: overflows uint
```

**⚠️ Подвохи и версии Go**
- В сериализации, протоколах и БД используют только фиксированные размеры: `int` в бинарном формате делает данные непереносимыми между 32- и 64-битными системами.
- Беззнаковые типы — для битовых операций, хешей и сырых байтов, а не «для неотрицательных чисел»: вычитание легко уходит в огромные значения ([вопрос 11](#q1-1-11)).
- На 32-битных платформах 64-битные атомики требуют [выравнивания](glossary.md#alignment) по 8 — используй `atomic.Int64` (Go 1.19).

**🎤 Прямая речь**
> `int32` и `int64` — типы фиксированного размера, 4 и 8 байт. `int` зависит от архитектуры: это машинное слово, 64 бита на `amd64` и `arm64`, 32 бита на 32-битных платформах. `uint` — беззнаковая версия, тот же размер, но диапазон от нуля до 2ⁿ−1. Все они разные типы, Go не делает неявных преобразований даже между `int` и `int64`, хотя в памяти на 64-битной машине они устроены одинаково.
>
> В обычном коде я использую `int` для индексов, длин и счётчиков, а фиксированные размеры — для данных, которые уходят наружу: протоколы, бинарные форматы, БД. Беззнаковые типы беру только для битовых операций и хешей, потому что вычитание единицы из нулевого `uint` превращается в максимальное значение.

### 10. Сколько памяти занимают `int32`/`int64`, их предельные значения? Что при переполнении?

**⚡ Суть за 10 секунд**
`int32` — 4 байта (около ±2,1 млрд), `int64` — 8 байт (около ±9,2·10¹⁸). Переполнение в рантайме — молчаливый wraparound без паники; переполнение константы — ошибка компиляции.

**🔧 Под капотом**
- Арифметика выполняется железом в [дополнительном коде](glossary.md#twos-complement), поэтому `MaxInt32 + 1` даёт `MinInt32`.
- В отличие от C, где знаковое переполнение — undefined behavior, спецификация Go **определяет** wraparound. Поэтому компилятору запрещено оптимизировать код в расчёте на отсутствие переполнения — например, считать `x < x+1` всегда истинным.
- Константы компилятор считает с произвольной точностью, поэтому `var b int8 = 128` ловится на сборке.

| Тип | Байт | Минимум | Максимум |
|---|---|---|---|
| `int8` | 1 | −128 | 127 |
| `int32` | 4 | −2 147 483 648 | 2 147 483 647 |
| `int64` | 8 | −9 223 372 036 854 775 808 | 9 223 372 036 854 775 807 |
| `uint8` | 1 | 0 | 255 |
| `uint32` | 4 | 0 | 4 294 967 295 |
| `uint64` | 8 | 0 | 18 446 744 073 709 551 615 |

```go
var a int32 = math.MaxInt32
a++
fmt.Println(a) // -2147483648

var u uint8
u--
fmt.Println(u) // 255

var b int8 = 128 // ошибка компиляции: 128 overflows int8
```

**⚠️ Подвохи и версии Go**
- Переполнение незаметно: счётчики, суммы денег, вычисление `len * size` перед выделением памяти.
- Защита: проверять границы до операции; `math/bits.Add64` / `Mul64` возвращают перенос; `math/big` — для произвольной точности.
- Деньги хранят в int64 в минимальных единицах (копейках), а не во float.

**🎤 Прямая речь**
> `int32` занимает 4 байта, диапазон примерно плюс-минус 2,1 миллиарда; `int64` — 8 байт, примерно плюс-минус 9,2 квинтиллиона. Точные границы есть в пакете `math`: `MaxInt32`, `MinInt64` и так далее.
>
> При переполнении в рантайме паники нет: значение молча заворачивается по правилам дополнительного кода, `MaxInt32 + 1` становится `MinInt32`. В отличие от C, это поведение определено спецификацией, так что компилятор не делает на нём опасных оптимизаций. А вот переполнение константы ловится на этапе компиляции. В критичных местах — деньги, размеры буферов — я проверяю границы явно или использую `math/bits`, который возвращает флаг переноса.

<a id="q1-1-11"></a>
### 11. ⭐ Почему `len()` возвращает `int`, а не `uint`?

**⚡ Суть за 10 секунд**
Чтобы избежать ловушек беззнаковой арифметики и лишних конверсий: индексы, длины и их разности участвуют в обычной арифметике, а она в Go ведётся в `int`.

**🔧 Под капотом**
- В заголовках слайса и строки поля `len` и `cap` имеют тип `int`.
- **[Bounds check](glossary.md#bounds-check):** компилятор сравнивает индекс с длиной как беззнаковые числа (`uint(i) < uint(len)`). Одна инструкция ловит и выход за верхнюю границу, и отрицательный индекс, так что знаковый тип не требует лишних проверок.
- 63 бит хватает с запасом: длина ограничена адресуемой памятью, и `makeslice` паникует с `len out of range` гораздо раньше.

```go
for i := len(s) - 1; i >= 0; i-- { ... }
// будь len беззнаковым, условие i >= 0 было бы всегда истинным,
// а на пустом слайсе len(s)-1 дал бы огромное число
```

**⚠️ Подвохи и версии Go**
- Разность `len(a) - len(b)` бывает отрицательной; с `uint` она превратилась бы в гигантское число.
- Отрицательные значения удобны как сигнал «не найдено»: `strings.Index` возвращает `-1`.
- При конверсии `uint64` из внешних данных (протокол, файл) в `int` проверяй диапазон — иначе получишь отрицательную длину.

**🎤 Прямая речь**
> Длина не бывает отрицательной, но с длинами постоянно считают: вычитают единицу, берут разности, идут циклом от конца. С беззнаковым типом это источник багов — `len(s) - 1` на пустом слайсе стал бы огромным числом, а цикл `i >= 0` никогда бы не закончился. Плюс в Go нет неявных преобразований, и все индексы — это `int`; беззнаковый `len` требовал бы конверсий почти в каждом выражении.
>
> По производительности знаковый тип ничего не стоит: при bounds check компилятор сравнивает индекс с длиной как беззнаковые числа, и одна инструкция ловит и отрицательный индекс, и выход за границу. А одного бита на знак не жалко — длина всё равно ограничена памятью.

<a id="q1-1-12"></a>
### 12. Что будет при делении int на 0 и float на 0?

**⚡ Суть за 10 секунд**
Целочисленное деление на ноль в рантайме — паника. Деление float на ноль — значения по [IEEE 754](glossary.md#ieee754): `+Inf`, `-Inf` или `NaN`, без паники. Если делитель — константа 0, это ошибка компиляции в обоих случаях.

**🔧 Под капотом**
- **Целые:** рантайм бросает `runtime.Error` через `runtime.panicdivide` — `panic: runtime error: integer divide by zero`. Это обычная паника, её ловит `recover`. Остаток `%` от деления на ноль ведёт себя так же.
- ⭐ **`MinInt64 / -1`:** спецификация требует результат `MinInt64` без паники. На `amd64` инструкция `IDIV` в этом случае вызывает аппаратное исключение, поэтому компилятор вставляет отдельную проверку делителя на −1.
- **float:** FPU работает по IEEE 754 с замаскированными исключениями, поэтому результат — специальные значения, а не прерывание.

```go
a, b := 10, 0
fmt.Println(a / b) // panic: runtime error: integer divide by zero

x := 0.0
fmt.Println(1/x, -1/x, x/x) // +Inf -Inf NaN

m, n := int64(math.MinInt64), int64(-1)
fmt.Println(m/n == math.MinInt64) // true

const c = 10 / 0 // ошибка компиляции: division by zero
```

**⚠️ Подвохи и версии Go**
- `NaN != NaN`. Проверка — `math.IsNaN`, бесконечности — `math.IsInf`.
- `NaN` как ключ map: каждая вставка создаёт новую запись, найти её нельзя (очистить map поможет `clear` из Go 1.21).
- `encoding/json` не кодирует `Inf` и `NaN`: `json: unsupported value: NaN`.

**🎤 Прямая речь**
> Целочисленное деление на ноль — это паника в рантайме, `integer divide by zero`. Её можно поймать через `recover`, но правильнее проверять делитель заранее. Если ноль — константа, код вообще не скомпилируется.
>
> С float паники нет: по IEEE 754 получается плюс или минус бесконечность, а ноль на ноль даёт NaN. Тут свои ловушки: NaN не равен самому себе, его нельзя закодировать в JSON, а как ключ map он создаёт записи, которые потом не найти. Из любопытного: `MinInt64 / -1` по спецификации не паникует и возвращает `MinInt64`, и компилятор специально генерирует проверку, потому что на `amd64` такая инструкция деления падает.

### 13. Преобразования между строками и числами (`strconv`). Можно ли сделать `string(int)` и `int(string)`?

**⚡ Суть за 10 секунд**
Строки и числа конвертируют через `strconv`: `Atoi`/`Itoa`, `ParseInt`/`FormatInt`, `ParseFloat`, `ParseBool`. `string(65)` компилируется, но даёт `"A"` (символ с кодом 65), а не `"65"`. `int("42")` не компилируется.

**🔧 Под капотом**
- У `Atoi` есть быстрый путь для коротких строк (до 18 символов на 64-битной платформе) без проверок переполнения; длинные строки уходят в `ParseInt`.
- `Itoa` / `FormatInt` для чисел 0–99 возвращают подстроку из заранее вычисленной таблицы — без аллокации. Для остальных создаётся новая строка в [куче](glossary.md#stack-heap).
- **Без аллокаций:** `strconv.AppendInt(buf, n, 10)` и `AppendFloat` дописывают в существующий `[]byte`. Так устроены быстрые сериализаторы и логгеры вроде zerolog.
- `string(rune)` кодирует руну в [UTF-8](glossary.md#utf8) (1–4 байта).
- Смежная тема: `string(b)` и `[]byte(s)` обычно **копируют** данные, потому что строки неизменяемы. Исключения — оптимизации компилятора: `m[string(b)]`, сравнение `string(b) == "x"`, `for range []byte(s)`. Zero-copy с Go 1.20: `unsafe.String(unsafe.SliceData(b), len(b))`, но менять байты после этого нельзя. Подробно — в блоке 1.2.

```go
n, err := strconv.Atoi("42")             // 42, nil
s := strconv.Itoa(42)                    // "42"
i, err := strconv.ParseInt("ff", 16, 64) // 255
bin := strconv.FormatInt(5, 2)           // "101"
buf := strconv.AppendInt(nil, 42, 10)    // []byte("42")

_, err = strconv.Atoi("abc")
// *strconv.NumError{Func: "Atoi", Num: "abc", Err: strconv.ErrSyntax}

fmt.Println(string(rune(65))) // "A"
// string(65) — go vet предупреждает: получится один символ, а не "65"
// int("42")  — ошибка компиляции
```

**⚠️ Подвохи и версии Go**
- `fmt.Sprintf("%d", n)` медленнее `strconv.Itoa`: [рефлексия](glossary.md#reflection) плюс упаковка в интерфейс с аллокацией.
- Ошибки проверяй через `errors.Is(err, strconv.ErrRange)` или `ErrSyntax`. При выходе за диапазон `ParseInt` вернёт `ErrRange` и значение, обрезанное до границы `bitSize`.
- `string(int)` ловит анализатор `stringintconv` в `go vet`.

**🎤 Прямая речь**
> Для конвертации строк и чисел есть пакет `strconv`: `Atoi` и `Itoa` для простых случаев, `ParseInt`, `ParseFloat` и `FormatInt` — когда нужны основание системы счисления и размер. Ошибки возвращаются как `*strconv.NumError`, и через `errors.Is` можно отличить синтаксическую ошибку от выхода за диапазон.
>
> `string(65)` — ловушка: это конверсия руны, получится буква «A», и `go vet` об этом предупреждает. `int("42")` не скомпилируется вовсе. В горячем коде я избегаю `fmt.Sprintf` и использую `strconv.Append*`, которые пишут в готовый буфер без аллокаций. Ещё помню, что конверсии между `string` и `[]byte` обычно копируют данные, а zero-copy через `unsafe.String` возможен, но требует гарантии, что байты больше не изменятся.

### 14. Константы: можно ли изменить? Типизированные vs нетипизированные

**⚡ Суть за 10 секунд**
Константа — значение времени компиляции, изменить её нельзя. Бывают только числовые, строковые, рунные и булевы. Нетипизированная константа подстраивается под тип контекста и хранится с высокой точностью; типизированная ведёт себя как значение своего типа.

**🔧 Под капотом**
- Компилятор хранит нетипизированные константы с произвольной точностью, как `math/big`; спецификация требует минимум 256 бит для целых. Выражения из констант сворачиваются на этапе компиляции ([constant folding](glossary.md#constant-folding)).
- В бинарнике константы — не переменные: числа подставляются прямо в инструкции, строки лежат в [read-only секции](glossary.md#rodata) и дедуплицируются [линкером](glossary.md#linker). Поэтому у константы нет адреса: `&c` — ошибка компиляции.
- Тип по умолчанию у нетипизированной константы применяется только тогда, когда тип обязателен: `x := c` или передача в `any`. Целые → `int`, вещественные → `float64`, руны → `rune`, комплексные → `complex128`.

```go
const untyped = 10      // нетипизированная
const typed int32 = 10

var f float64 = untyped // ок: подстроилась под float64
var g float64 = typed   // ошибка: нужно float64(typed)

const huge = 1 << 100   // ок, пока не нужен конкретный тип
fmt.Println(huge >> 98) // 4: свернулось на этапе компиляции
fmt.Println(huge)       // ошибка: переполняет int (тип по умолчанию)
```

**⚠️ Подвохи и версии Go**
- Константных слайсов, map и структур нет. Варианты: функция, которая возвращает новую копию, или неэкспортируемая переменная с геттером.
- `const x = 1 / 2` равно 0 (целочисленное деление нетипизированных целых), а `1.0 / 2` — 0.5.
- Типизированные константы удобны для enum: `const Active Status = 1` не смешается с обычным `int` без конверсии.

**🎤 Прямая речь**
> Константы в Go вычисляются на этапе компиляции и не меняются. Допускаются только базовые типы: числа, строки, руны, bool; константного слайса или структуры сделать нельзя. В бинарнике это не переменные — числа вшиваются прямо в инструкции, поэтому у константы нельзя взять адрес.
>
> Главная тонкость — нетипизированные константы. Компилятор хранит их с высокой точностью и подставляет в любой совместимый тип без конверсии: одну и ту же константу можно присвоить и `int`, и `float64`. Типизированная константа ведёт себя как обычное значение своего типа и требует явной конверсии. Поэтому общие числовые константы я оставляю нетипизированными, а для enum делаю типизированные, чтобы компилятор не дал их перепутать.

### 15. Что такое `iota`? Как сделать enum?

**⚡ Суть за 10 секунд**
`iota` — счётчик строк внутри блока `const`: 0, 1, 2… Enum в Go — это свой тип плюс константы с `iota` и метод `String()`.

**🔧 Под капотом**
- Всё происходит на этапе компиляции: в рантайме enum — обычные числа, никаких объектов.
- Строка без выражения неявно повторяет предыдущее выражение с новым значением `iota`.
- `String()` обычно пишут через `switch`; для больших switch по целым и строкам компилятор (с Go 1.19, на `amd64`/`arm64`) строит [jump table](glossary.md#jump-table). Утилита `stringer` генерирует одну строку со всеми именами и массив смещений, так что `String()` работает без аллокаций.

```go
type Status int

const (
    StatusUnknown Status = iota // 0 — zero value означает «не задано»
    StatusActive                // 1
    StatusBlocked               // 2
)

const (
    _  = iota             // пропускаем 0
    KB = 1 << (10 * iota) // 1024
    MB                    // 1048576
)

type Perm uint8

const (
    Read  Perm = 1 << iota // 1
    Write                  // 2
    Exec                   // 4
)
```

**Правила:** `iota` сбрасывается в 0 в каждом новом блоке `const`; растёт с каждой строкой, даже если в ней `_` или `iota` не используется; внутри одной строки значение одно и то же (`a, b = iota, iota`).

**⚠️ Подвохи и версии Go**
- `Status(42)` скомпилируется. Значения из JSON и БД валидируй (метод `IsValid()`).
- Ноль резервируй под `Unknown`, чтобы незаполненное поле не выглядело валидным.
- Новая константа в середине блока сдвигает все следующие значения. Если числа хранятся в БД или уходят в протокол, задавай их явно или добавляй новые только в конец.
- Полноту switch по enum проверяет линтер `exhaustive`. `String()` генерируется командой `//go:generate stringer -type=Status`.

**🎤 Прямая речь**
> `iota` — предопределённый счётчик в блоке `const`: на первой строке он равен нулю и растёт на единицу с каждой строкой, а строки без выражения повторяют предыдущее выражение. Enum делается так: объявляю тип, например `type Status int`, и константы этого типа через `iota`, плюс метод `String()`, который удобно генерировать утилитой `stringer`. Тот же приём даёт битовые флаги через `1 << iota` и размеры вроде KB и MB.
>
> Надо понимать, что это не настоящий enum: под капотом обычный int, и `Status(42)` скомпилируется. Поэтому я резервирую ноль под «unknown», валидирую значения на входе, использую линтер `exhaustive`. И если значения хранятся в базе, никогда не вставляю новую константу в середину — это сдвинет все числа.

### 16. Shadowing переменных — что это и чем опасно?

**⚡ Суть за 10 секунд**
Shadowing — объявление во вложенной области видимости переменной с тем же именем, что и снаружи; внутренняя скрывает внешнюю. Опасно тем, что присваиваешь не той переменной — чаще всего `err`.

**🔧 Под капотом**
- Компилятор строит дерево областей видимости: universe → пакет → файл → функция → блоки. Каждый `:=` во вложенном блоке создаёт **новый объект** со своим слотом на [стеке](glossary.md#stack-heap) (или в куче, если его захватит замыкание, которое живёт дольше функции). Внешняя переменная при этом не меняется.
- Компилятор не предупреждает, потому что затенение часто легитимно: `if err := f(); err != nil { ... }` ограничивает `err` областью `if`.

```go
func load() error {
    var err error
    if needLoad {
        data, err := fetch() // := создаёт НОВЫЙ err внутри if
        _ = data
    }
    return err // всегда nil: ошибка fetch потерялась
}

// исправление: объявить заранее и присвоить через =
var data []byte
data, err = fetch()
```

**⚠️ Подвохи и версии Go**
- Затенение пакетов и встроенных функций: `len := 3`, `copy := ...`, переменная `url` поверх пакета `net/url` — после этого пакет в блоке недоступен.
- Голый `return` при затенённом именованном результате — ошибка компиляции `err is shadowed during return`.
- Переменная из `if x, err := f(); ...` видна и в ветке `else`.
- Ловить: анализатор `shadow` (`golang.org/x/tools/go/analysis/passes/shadow`), в golangci-lint — `govet` с включённым shadow.

**🎤 Прямая речь**
> Shadowing — это когда во вложенном блоке объявляется переменная с тем же именем, что и снаружи. Компилятор создаёт новый объект, и внешняя переменная остаётся нетронутой. Самый частый баг — с `err`: внутри `if` пишут `x, err := f()`, создаётся новый `err`, а функция возвращает внешний, который так и остался nil. Ошибка молча теряется.
>
> Компилятор не ругается, потому что затенение бывает полезным, например `if err := f(); err != nil` ограничивает область видимости. Поэтому я включаю анализатор `shadow` в golangci-lint, внимательно смотрю на `:=` во вложенных блоках и не называю переменные именами пакетов и встроенных функций вроде `url` или `len`.

### 17. Модификаторы доступа (экспортируемые имена)

**⚡ Суть за 10 секунд**
Ключевых слов `public`/`private` нет. Имя с заглавной буквы экспортируется и видно из других пакетов, со строчной — видно только внутри своего пакета. Граница доступа — пакет, а не файл и не тип.

**🔧 Под капотом**
- Проверку делает компилятор при проверке типов: экспортированные имена попадают в [export data](glossary.md#export-data) пакета, которую читают импортирующие пакеты.
- [Рефлексия](glossary.md#reflection) **видит** неэкспортированные поля, но работать с ними не даёт: `reflect.Value.CanSet()` возвращает false, а `Interface()` паникует. Поэтому `encoding/json` пропускает такие поля.
- Каталог `internal/` проверяет не компилятор, а команда `go`: импорт разрешён только из дерева родительского каталога.
- ⭐ [`//go:linkname`](glossary.md#linkname) позволяет вызвать неэкспортированную функцию другого пакета в обход правил. С Go 1.23 [линкер](glossary.md#linker) запрещает так ссылаться на внутренние символы stdlib, если они не помечены для этого явно.
- Заглавной считается любая буква Unicode категории Lu: имя `Привет` тоже экспортируется.

```go
package user

type User struct {
    Name     string // видно снаружи и в JSON
    password string // только внутри пакета user, в JSON не попадёт
}

func New(name string) *User { return &User{Name: name} } // экспорт
func hash(s string) string  { return s }                  // приватная
```

**⚠️ Подвохи и версии Go**
- Тесты в том же пакете видят всё; тесты в `package foo_test` работают только через экспортированный API (black-box).
- Экспортированная функция, которая возвращает неэкспортированный тип, — антипаттерн: снаружи с ним неудобно работать.
- «Почему JSON пустой?» — потому что поля структуры с маленькой буквы.

**🎤 Прямая речь**
> В Go нет модификаторов `public` и `private`: видимость определяется регистром первой буквы. С заглавной — имя экспортируется из пакета, со строчной — доступно только внутри пакета, во всех его файлах. Правило одно для типов, функций, полей и методов, а `protected` и приватности на уровне файла нет.
>
> Важные следствия: `encoding/json` и другие библиотеки на рефлексии не могут работать с неэкспортированными полями, поэтому структура с маленькими буквами сериализуется в пустой объект. Для ограничения на уровне модуля есть каталог `internal`, его проверяет команда `go`. Технически ограничение можно обойти через `go:linkname`, но с 1.23 линкер закрывает это для stdlib, и в продакшен-коде так делать не стоит.

<a id="q1-1-18"></a>
### 18. `type A B` vs `type A = B`

**⚡ Суть за 10 секунд**
`type A B` — **определение нового типа** с тем же базовым типом: другая идентичность, нужна явная конверсия, методы `B` не наследуются. `type A = B` — **алиас**: тот же самый тип под другим именем.

**🔧 Под капотом**
- У определённого типа в рантайме свой [дескриптор](glossary.md#type-descriptor) (`_type` со своим именем и набором методов): `reflect.TypeOf` разный, type switch их различает. Конверсия между `A` и `B` ничего не стоит — представление в памяти одинаковое.
- Алиас нового дескриптора не создаёт: в рантайме это тот же тип. Поэтому `%T` для `byte` печатает `uint8`, а для `rune` — `int32`.
- У нового типа над конкретным типом набор методов пустой. Исключения — методы встроенных полей структуры и методы интерфейса, если `B` — интерфейс.

```go
type Celsius float64           // новый тип
type Duration2 = time.Duration // алиас

var c Celsius = 36.6
var f float64 = c              // ошибка: нужно float64(c)

var d Duration2 = time.Second
fmt.Println(d.String())        // работает: это тот же time.Duration

type MyMutex sync.Mutex
var m MyMutex
m.Lock() // ошибка: m.Lock undefined (type MyMutex has no field or method Lock)
```

| | `type A B` | `type A = B` |
|---|---|---|
| Новый тип | да | нет |
| Присваивание без конверсии | нет | да |
| Методы `B` | не наследуются | те же |
| Свои методы | можно | только если `B` объявлен в этом же пакете |

**⚠️ Подвохи и версии Go**
- Чтобы «унаследовать» методы, нужно встраивание: `type MyMutex struct{ sync.Mutex }`.
- Новые типы дают доменную типобезопасность: `type UserID int64` не перепутать с `OrderID int64`.
- Алиасы нужны для постепенного рефакторинга — переноса типа между пакетами без поломки клиентов. С Go 1.24 алиасы могут иметь параметры типа.

**🎤 Прямая речь**
> `type A B` создаёт новый именованный тип с тем же базовым типом. Это отдельный тип со своим дескриптором в рантайме: присвоить его без явной конверсии нельзя, и методы исходного типа не переходят. Например, `type MyMutex sync.Mutex` не имеет метода `Lock`; чтобы получить методы, нужно встраивание. Конверсия при этом бесплатная, раскладка в памяти одна и та же.
>
> `type A = B` — алиас, просто второе имя того же типа: все методы на месте, конверсия не нужна. Алиасы появились для рефакторинга больших кодовых баз, чтобы переносить типы между пакетами, а встроенные `byte`, `rune` и `any` — тоже алиасы. Новые типы я использую для доменной типобезопасности, например `UserID` и `OrderID`, чтобы их нельзя было перепутать.

### 19. Что делает `_` (blank identifier)?

**⚡ Суть за 10 секунд**
`_` — пустое имя: значение, присвоенное ему, отбрасывается, прочитать из `_` нельзя.

**🔧 Под капотом**
- Под `_` компилятор не выделяет память, но правая часть всё равно вычисляется: вызовы функций и побочные эффекты сохраняются.
- `var _ io.Reader = (*T)(nil)` — проверка на этапе компиляции; в итоговый бинарник она не попадает.
- `import _ "pkg"` линкует пакет в бинарник и выполняет его `init()`: так регистрируются драйверы `database/sql`, декодеры `image/png`, хендлеры `net/http/pprof`. Размер бинарника при этом растёт.

```go
_, err := strconv.Atoi(s)          // ненужное возвращаемое значение
for _, v := range items { }        // не нужен индекс
import _ "github.com/lib/pq"       // регистрирует драйвер postgres
var _ io.Reader = (*MyReader)(nil) // компилятор проверит реализацию интерфейса

const (
    _  = iota                      // пропуск значения
    KB = 1 << (10 * iota)
)

type header struct {
    _    [4]byte                   // поле-заполнитель
    Size uint32
}
```

**⚠️ Подвохи и версии Go**
- `import _ "net/http/pprof"` регистрирует `/debug/pprof` в `http.DefaultServeMux`. Если внешний сервер использует его, данные профилирования доступны снаружи. pprof поднимай на отдельном внутреннем порту.
- `_ = x` глушит ошибку «declared and not used» — удобно при отладке, но не забывай убрать.
- Вместо `for _ = range ch` пиши `for range ch`.

**🎤 Прямая речь**
> Blank identifier — это «пустое» имя, куда отбрасывают ненужное: лишнее возвращаемое значение, индекс в `range`, значение `iota`. Правая часть при этом всё равно вычисляется, просто результат никуда не сохраняется.
>
> Два важных идиоматических применения. Первое — `var _ Interface = (*T)(nil)`: проверка на этапе компиляции, что тип реализует интерфейс, в рантайме это ничего не стоит. Второе — импорт ради побочного эффекта, `import _`, который выполняет `init` пакета, например регистрирует драйвер БД. С `net/http/pprof` осторожно: он вешает хендлеры на дефолтный mux, и их легко случайно открыть наружу.

### 20. Какие циклы есть в Go? Как завершить `for` без условия? `break`/`continue` с меткой, `goto`

**⚡ Суть за 10 секунд**
Цикл в Go один — `for`, у него несколько форм: классическая, «while», бесконечная и `range`. Бесконечный цикл завершают `break`, `return`, `panic` или `os.Exit`. Метки дают `break`/`continue` по внешнему циклу; `goto` — переход к метке внутри той же функции.

**🔧 Под капотом**
- Все формы компилируются в одно и то же: проверка условия + условный переход назад.
- **range по слайсу:** выражение вычисляется один раз, длина фиксируется на старте — `append` внутри цикла не добавляет итераций. **range по массиву** (не по указателю на него) работает с копией массива.
- **range по map** стартует со случайной позиции, поэтому порядок обхода не определён.
- **range по каналу** принимает значения, пока канал не закроют.
- `break`/`continue` с меткой и `goto` — безусловные переходы. Ограничения `goto` (нельзя перепрыгнуть объявление переменной в её область видимости и нельзя прыгнуть внутрь блока) нужны, чтобы не получить неинициализированную переменную.

```go
for i := 0; i < n; i++ { }  // классический
for cond { }                // аналог while
for { }                     // бесконечный
for i, v := range slice { } // массив, слайс, строка, map, канал
for i := range 10 { }       // range по числу (Go 1.22)
for v := range seq { }      // range по функции-итератору (Go 1.23)

loop:
for {
    select {
    case <-ctx.Done():
        break loop        // выходим из for, а не только из select
    case v := <-ch:
        if v < 0 {
            continue loop // следующая итерация внешнего цикла
        }
        process(v)
    }
}
```

**⚠️ Подвохи и версии Go**
- `break` внутри `select` или `switch` выходит только из них. Без метки воркер с `ctx.Done()` не завершится — частая ошибка.
- `v` в `range` — копия элемента: `v.Field = x` не изменит слайс, нужно `s[i].Field = x`.
- Версии: `range` по числу и новая переменная на каждой итерации — Go 1.22; `range` по функциям — Go 1.23.

**🎤 Прямая речь**
> В Go единственный цикл — `for`, но у него четыре формы: классическая с тремя частями, с одним условием вместо `while`, бесконечная и `range` по слайсам, строкам, map, каналам, а с недавних версий ещё по числам и функциям-итераторам. Бесконечный цикл завершается через `break` или `return`.
>
> Главная практическая тонкость — `break` внутри `select` или `switch` выходит только из них, а не из цикла. В воркерах, которые слушают `ctx.Done()`, для этого нужен `break` с меткой. Ещё помню, что в `range` переменная — копия элемента, и что длина слайса фиксируется на старте цикла. `goto` в языке есть, но в обычном коде я его не использую.

### 21. Что изменилось в циклах `for` в Go 1.22 (переменная цикла, `range int`)?

**⚡ Суть за 10 секунд**
1. Переменная цикла теперь создаётся **заново на каждой итерации** — это убрало классический баг с замыканиями, [горутинами](glossary.md#goroutine) и `&v`.
2. Появился `range` по целому числу: `for i := range 10`.

**🔧 Под капотом**
- Компилятор заводит новую переменную на каждую итерацию и копирует в неё текущее значение. Если переменная не убегает, она остаётся тем же слотом на [стеке](glossary.md#stack-heap) и ничего не стоит. Если её захватывает убегающее замыкание или убегает её адрес, на каждой итерации будет аллокация в куче.
- Новая семантика включается директивой `go` в `go.mod` того модуля, где написан цикл (1.22 и выше). В Go 1.21 её можно было включить через `GOEXPERIMENT=loopvar`.
- `for i := range 10` компилируется в обычный счётный цикл.

```go
var prints []func()
for i := 0; i < 3; i++ {
    prints = append(prints, func() { fmt.Print(i, " ") })
}
for _, p := range prints {
    p()
}
// go 1.22+ в go.mod: 0 1 2
// go 1.21 в go.mod:  3 3 3
```
То же касалось горутин `go func() { use(v) }()` в цикле и `ptrs = append(ptrs, &v)`: раньше все указатели смотрели на одну переменную.

**⚠️ Подвохи и версии Go**
- Старое поведение сохраняется на свежем компиляторе, если в `go.mod` указано `go 1.21` или ниже. На код-ревью это любимая ловушка: смотри версию в `go.mod`.
- Анализатор `loopclosure` в `go vet` для нового кода больше не нужен.
- Следующий шаг — Go 1.23: `range` по функциям-итераторам (`iter.Seq`).

**🎤 Прямая речь**
> В Go 1.22 поменялась семантика переменной цикла: раньше она была одна на весь цикл, и замыкания или горутины, захватившие её, видели последнее значение — классический вывод «3 3 3». Теперь на каждой итерации создаётся своя переменная, и тот же код печатает «0 1 2». Если переменная не убегает, это ничего не стоит; если её захватывает замыкание, на каждую итерацию будет аллокация.
>
> Важная деталь: поведение зависит от директивы `go` в `go.mod`, а не от версии компилятора. Модуль с `go 1.21` работает по-старому даже на новом тулчейне, поэтому на ревью я всегда смотрю версию. Второе изменение 1.22 — `range` по числу: `for i := range n`.

### 22. Как устроен `switch` (fallthrough, switch без выражения)?

**⚡ Суть за 10 секунд**
Case проверяются сверху вниз, выполняется первый подходящий, `break` ставится неявно. `fallthrough` — явный переход в тело следующего case **без проверки** его условия. `switch` без выражения — это `switch true`, замена цепочки `if-else`.

**🔧 Под капотом**
- Switch по константам компилятор оптимизирует: сортирует case и делает бинарный поиск, а для больших switch по целым и строкам (Go 1.19+, `amd64`/`arm64`) строит [jump table](glossary.md#jump-table). Семантика порядка при этом сохраняется.
- Switch с неконстантными case — последовательная цепочка сравнений, как `if-else`.
- Type switch сравнивает [дескриптор](glossary.md#type-descriptor) типа, лежащий в интерфейсе, с типом каждого case.

```go
switch {                 // без выражения
case score >= 90:
    grade = "A"
case score >= 75:
    grade = "B"
default:
    grade = "C"
}

switch n := 2; n {       // init-выражение, как в if
case 1:
    fmt.Println("one")
case 2:
    fmt.Println("two")
    fallthrough
case 3:
    fmt.Println("three") // выполнится: условие case 3 НЕ проверяется
case 4:
    fmt.Println("four")  // не выполнится
}
// two
// three

switch day {
case "sat", "sun":       // несколько значений в одном case
    fmt.Println("weekend")
}
```

**⚠️ Подвохи и версии Go**
- `fallthrough` должен быть последней инструкцией case; его нельзя ставить в последнем case и в type switch.
- Одинаковые константы в разных case — ошибка компиляции.
- `break` внутри `switch` выходит из `switch`, а не из окружающего цикла ([вопрос 20](#q1-1-20)).
- Case-выражения не обязаны быть константами — можно вызывать функции; они вычисляются по порядку до первого совпадения.

**🎤 Прямая речь**
> `switch` в Go проверяет case сверху вниз и выполняет первый подходящий, а `break` подставляется автоматически, так что провалиться случайно нельзя. Если нужно перейти в следующий case, пишут `fallthrough`, причём условие следующего case уже не проверяется. В одном case можно перечислить несколько значений, а `switch` без выражения — это удобная замена длинной цепочки `if-else`.
>
> Под капотом switch по константам компилятор превращает в бинарный поиск, а большие — в jump table, так что он не медленнее `if`. Из ловушек: `break` внутри `switch` в цикле выходит только из `switch`, и `fallthrough` нельзя использовать в type switch.

### 23. Порядок выполнения логических операций, short-circuit. `true && !false`? `(true && false) || (false && true) || !(false && false)`?

**⚡ Суть за 10 секунд**
Приоритет: `!` → сравнения → `&&` → `||`. Вычисление ленивое: правая часть `&&` считается, только если слева `true`; правая часть `||` — только если слева `false`. `true && !false` = **true**; второе выражение = `false || false || true` = **true**.

**🔧 Под капотом**
- Short-circuit компилируется в условные переходы: правый операнд просто не выполняется. Поэтому безопасно писать `p != nil && p.x > 0`.
- `bool` в памяти — один байт со значением 0 или 1. Неявного приведения чисел к `bool` нет, перегрузки операторов тоже.

| Уровень | Бинарные операторы |
|---|---|
| 5 (высший) | `*` `/` `%` `<<` `>>` `&` `&^` |
| 4 | `+` `-` `\|` `^` |
| 3 | `==` `!=` `<` `<=` `>` `>=` |
| 2 | `&&` |
| 1 | `\|\|` |

Унарные операторы (`!`, `-`, `^`, `*`, `&`) выше всех бинарных.

```go
if p != nil && p.Age > 18 { }    // p.Age не вычислится для nil
if len(s) > 0 && s[0] == '#' { } // нет выхода за границы
```

**⚠️ Подвохи и версии Go**
- Побочный эффект в правом операнде (`ok && save()`) может не выполниться — не прячь туда важную логику.
- `&` и `|` для `bool` в Go не определены, это только побитовые операции над целыми.
- `if 1 {}` не скомпилируется: условие обязано быть `bool`.

**🎤 Прямая речь**
> Сначала выполняется унарное отрицание, потом сравнения, потом `&&` и в конце `||`. `true && !false` — это `true && true`, то есть `true`. Во втором выражении обе скобки дают `false`, а `!(false && false)` — `true`, так что итог тоже `true`.
>
> Важнее порядок вычисления: `&&` и `||` ленивые. Если левая часть уже определяет результат, правая не выполняется вообще. На этом строятся идиомы вроде `p != nil && p.Field` и проверки длины перед индексом. Обратная сторона — побочные эффекты в правой части могут не случиться, поэтому функции с важными действиями я туда не ставлю.

### 24. Пакет `fmt`: `Println`, `Printf`, `Sprintf`, `Scan`; основные verbs (`%v`, `%+v`, `%T`)

**⚡ Суть за 10 секунд**
`Print*` пишут в stdout, `Sprint*` возвращают строку, `Fprint*` пишут в любой `io.Writer`, `Errorf` создаёт ошибку (`%w` оборачивает исходную). `Scan*` читают ввод в переменные по указателю. Главные verbs: `%v`, `%+v`, `%#v`, `%T`, `%d`, `%s`, `%q`, `%x`, `%f`, `%p`.

**🔧 Под капотом**
- Аргументы передаются как `...any`: каждое значение упаковывается в интерфейс, и часто это аллокация — значение убегает в [кучу](glossary.md#stack-heap).
- Внутри работает структура-принтер `pp`, которую переиспользуют через [`sync.Pool`](glossary.md#sync-pool); для `%v` значение обходится через [рефлексию](glossary.md#reflection).
- Порядок проверки методов: `fmt.Formatter` → для `%v`/`%s` сначала `error`, потом `fmt.Stringer`. Паника внутри `String()` перехватывается и печатается как `%!v(PANIC=String method: ...)`.
- `os.Stdout` не буферизован: каждый `Println` — отдельный системный вызов `write`. Для массового вывода оборачивай его в `bufio.Writer`.

| Функция | Что делает |
|---|---|
| `Print` | пробелы только между операндами, если оба не строки |
| `Println` | пробелы между всеми операндами + перевод строки |
| `Printf` / `Sprintf` / `Fprintf` | по формату: в stdout / в строку / в `io.Writer` |
| `Errorf` | `error`; `%w` оборачивает исходную ошибку |
| `Scan`, `Scanln`, `Scanf`, `Sscan`, `Fscan` | читают в `&x` |

```go
type User struct {
    Name string
    Age  int
}
u := User{"Ann", 30}

fmt.Printf("%v\n", u)    // {Ann 30}
fmt.Printf("%+v\n", u)   // {Name:Ann Age:30}
fmt.Printf("%#v\n", u)   // main.User{Name:"Ann", Age:30}
fmt.Printf("%T\n", u)    // main.User
fmt.Printf("%q\n", "hi") // "hi"
fmt.Printf("%x %b %c %U\n", 255, 5, 'Я', 'Я')            // ff 101 Я U+042F
fmt.Printf("%08.3f|%-5s|%5d|%t\n", 3.14159, "go", 42, true) // 0003.142|go   |   42|true
fmt.Print("a", "b", 1, 2, "\n")                           // ab1 2
```

**⚠️ Подвохи и версии Go**
- `String()`, внутри которого вызывается `fmt.Sprintf("%v", u)`, уходит в **бесконечную рекурсию**. Лечится конверсией в тип без методов: `type plain User; fmt.Sprintf("%v", plain(u))`.
- Неверное число аргументов даёт `%!d(MISSING)` или `%!(EXTRA ...)` в выводе — такое ловит `go vet` (анализатор printf).
- В горячем коде `strconv` быстрее `fmt`.
- `fmt.Scan` медленный на большом вводе: на live coding читай через `bufio.NewReader(os.Stdin)` + `fmt.Fscan` или `bufio.Scanner`.

**🎤 Прямая речь**
> В `fmt` три семейства функций: `Print` пишет в stdout, `Sprint` возвращает строку, `Fprint` пишет в любой `io.Writer`, у каждой есть варианты с переводом строки и с форматом. `Errorf` создаёт ошибку, а `%w` её оборачивает. Основные verbs: `%v` — значение по умолчанию, `%+v` добавляет имена полей, `%#v` печатает в синтаксисе Go, `%T` — тип; плюс `%d`, `%s`, `%q`, `%x`, `%f` с шириной и точностью.
>
> Под капотом `fmt` работает через рефлексию, а аргументы упаковываются в интерфейсы, что даёт аллокации, поэтому в горячем коде я использую `strconv` или `Append`-функции. Если у типа есть `String()` или `Error()`, `fmt` вызывает их, и тут есть ловушка — `Sprintf("%v")` внутри `String()` даёт бесконечную рекурсию. Для большого ввода и вывода оборачиваю stdin и stdout в `bufio`, потому что `os.Stdout` не буферизован.

<a id="q1-1-25"></a>
### 25. Пакеты: как создавать и импортировать? Порядок инициализации пакета

**⚡ Суть за 10 секунд**
Пакет — каталог с `.go`-файлами, у которых одинаковая строка `package name`. Импортируют по пути: путь модуля из `go.mod` плюс путь каталога. Порядок инициализации: импортированные пакеты → переменные уровня пакета (в порядке зависимостей) → все `init()` → `main()`.

**🔧 Под капотом**
- Пакет — единица компиляции: он компилируется отдельно в объектный файл с [export data](glossary.md#export-data), результат кэшируется в [build cache](glossary.md#build-cache). Зависимые пакеты читают только export data — отсюда быстрая инкрементальная сборка.
- Порядок инициализации переменных компилятор вычисляет статически по графу зависимостей и генерирует для каждого пакета задачу инициализации.
- Старт программы: рантайм инициализирует себя (планировщик, аллокатор, [GC](glossary.md#gc)), запускает главную [горутину](glossary.md#goroutine) `runtime.main`, та выполняет инициализацию всех пакетов в порядке зависимостей и только потом вызывает `main.main`. Все `init()` выполняются последовательно в одной горутине.
- [Линкер](glossary.md#linker) выкидывает неиспользуемые функции ([dead code elimination](glossary.md#dce)), но пакет, импортированный ради `init`, попадает в бинарник вместе со своими зависимостями.

```
myapp/
├── go.mod              // module github.com/me/myapp
├── main.go             // package main + func main()
└── internal/storage/
    └── storage.go      // package storage
```

```go
import (
    "fmt"                                  // stdlib
    "github.com/me/myapp/internal/storage" // свой пакет
    str "strings"                          // алиас
    _ "net/http/pprof"                     // только ради init()
)

var a = b + 1 // инициализируется вторым
var b = f()   // первым: от него зависит a
```

**Порядок инициализации:**
1. Импортированные пакеты — рекурсивно, каждый ровно один раз. С Go 1.21 порядок детерминирован: пакеты отсортированы по import path.
2. Переменные уровня пакета — в порядке зависимостей, а не объявления.
3. Функции `init()` — в порядке файлов (`go build` передаёт их по алфавиту) и в порядке объявления внутри файла. В одном файле может быть несколько `init`; вызвать `init` вручную нельзя.
4. `main.main()`.

**⚠️ Подвохи и версии Go**
- Циклические импорты запрещены (`import cycle not allowed`). Выход — вынести общий интерфейс или тип в отдельный пакет.
- Неиспользуемый импорт — ошибка компиляции.
- Тяжёлый `init` (подключение к БД, сетевые вызовы) — плохая практика: замедляет старт, ломает тесты, а ошибку из `init` нельзя вернуть, только паниковать.
- Не полагайся на порядок `init` между файлами — он зависит от их имён.
- Dot-импорт `import . "fmt"` не рекомендуется: непонятно, откуда взялось имя.

**🎤 Прямая речь**
> Пакет — это каталог, все файлы в котором объявляют одно имя пакета. Импортирую по полному пути: путь модуля из `go.mod` плюс каталог. Пакет — единица компиляции, он собирается отдельно и кэшируется, поэтому сборка Go быстрая. Циклические импорты запрещены, а каталог `internal` ограничивает, кто может импортировать пакет.
>
> Инициализация идёт так: рантайм запускает главную горутину, которая сначала инициализирует все импортированные пакеты, каждый один раз. Внутри пакета сначала переменные уровня пакета, причём в порядке зависимостей, а не объявления, потом все функции `init` в порядке файлов, и только после этого `main`. Я стараюсь не класть в `init` ничего тяжёлого — подключения к БД и чтение конфигов лучше делать явно в `main`, где можно нормально обработать ошибку.
