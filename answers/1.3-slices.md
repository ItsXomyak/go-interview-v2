### 1. Массив vs слайс. Массив — значение: что из этого следует?

**⚡ Суть**
Массив — фиксированная длина, которая входит в тип (`[3]int` и `[4]int` — разные типы), и семантика значения: присваивание и передача копируют все элементы. Слайс — лёгкий [дескриптор](glossary.md#type-descriptor) (указатель, len, cap) над массивом, с динамической длиной.

**🔧 Под капотом**
- Массив хранится «как есть», без заголовка: `[N]T` занимает `N × size(T)` и лежит прямо внутри структуры или на [стеке](glossary.md#stack-heap).
- Массив сравним через `==`, если сравнимы элементы, поэтому может быть ключом map. Слайс сравнивается только с `nil`.
- Передача большого массива по значению копирует его целиком; поэтому передают `*[N]T` или слайс `arr[:]`.

```go
arr := [3]int{1, 2, 3}
arr2 := arr // копия всех элементов
arr2[0] = 9
fmt.Println(arr, arr2, arr == [3]int{1, 2, 3}) // [1 2 3] [9 2 3] true
```

**⚠️ Подвохи и версии Go**
- `range` по массиву (не по указателю на него) работает с копией массива.
- Массивы удобны там, где размер известен заранее: ключи фиксированной длины (`map[[32]byte]T`), хеши — `sha256.Sum256` возвращает `[32]byte`, буферы.
- `len` у массива — константа времени компиляции.

**🎤 Прямая речь**
> Массив в Go — это значение фиксированного размера, и размер входит в тип. Присваивание или передача в функцию копирует все элементы, массивы можно сравнивать через `==` и использовать как ключи map. Слайс — дескриптор поверх массива: указатель, длина и capacity. Он лёгкий, его длина меняется, а данные он делит с массивом.
>
> В обычном коде почти всегда используются слайсы. Массивы я беру для данных фиксированного размера — хешей, UUID, ключей map — и помню, что большой массив по значению копируется целиком.

### 2. Как устроен слайс (ptr, len, cap)? Сколько весит заголовок слайса?

**⚡ Суть**
Слайс — структура из трёх машинных слов: указатель на элемент базового массива, длина `len` и ёмкость `cap`. На 64-битной платформе — **24 байта**, независимо от числа элементов.

**🔧 Под капотом**
- В рантайме это `runtime.slice{array unsafe.Pointer; len, cap int}`.
- `len` — сколько элементов доступно; `cap` — сколько есть от указателя до конца базового массива.
- `s[i]` — проверка `i < len` ([bounds check](glossary.md#bounds-check)) и обращение по адресу `ptr + i × size`.
- Срез `s[a:b]` создаёт новый заголовок за O(1) без копирования данных; передача слайса в функцию копирует только 24 байта.

```go
fmt.Println(unsafe.Sizeof([]int{}))              // 24
fmt.Println(unsafe.Sizeof(make([]int, 1000000))) // тоже 24: данные лежат отдельно
```

**⚠️ Подвохи и версии Go**
- Несколько слайсов могут смотреть в один массив — отсюда большинство багов ([вопрос 5](#q1-3-05)).
- У nil-слайса указатель nil, а len и cap равны 0.

**🎤 Прямая речь**
> Слайс — это заголовок из трёх слов: указатель на начало данных в базовом массиве, длина и capacity. На 64-битной машине это 24 байта, сколько бы элементов ни было, потому что сами данные лежат в отдельном массиве. Длина — сколько элементов видно сейчас, capacity — сколько поместится до конца массива без переаллокации.
>
> Поэтому срез слайса стоит O(1) — это новый заголовок над теми же данными, а передача в функцию копирует только заголовок. Обратная сторона — несколько слайсов легко делят одну память, и это нужно держать в голове.

### 3. Способы создать слайс. nil-слайс vs пустой слайс; можно ли `append` в nil? Как проверить на пустоту?

**⚡ Суть**
Способы: `var s []T` (nil), литерал `[]T{1, 2}`, `make([]T, len, cap)`, срез массива или слайса `arr[1:3]`. nil-слайс и пустой одинаково работают с `len`, `range` и `append` — в nil-слайс `append` работает. Пустоту проверяют через `len(s) == 0`, а не через `s == nil`.

**🔧 Под капотом**
- nil-слайс — `{nil, 0, 0}`. Пустой (`[]T{}`, `make([]T, 0)`) — указатель на специальный адрес для объектов нулевого размера, `len` и `cap` равны 0.
- `append` в nil-слайс выделяет массив через рантайм, как при обычном росте.

```go
var a []int  // nil
b := []int{} // пустой, не nil
ja, _ := json.Marshal(a)
jb, _ := json.Marshal(b)
fmt.Println(a == nil, b == nil, len(a), len(b), string(ja), string(jb))
// true false 0 0 null []

a = append(a, 1) // [1] — append в nil работает
```

**⚠️ Подвохи и версии Go**
- **JSON:** nil-слайс кодируется в `null`, пустой — в `[]`. Если фронтенд ждёт массив, инициализируй `make([]T, 0)`.
- `s == nil` как проверка пустоты — баг: пустой слайс не nil.
- `reflect.DeepEqual(nil, []int{})` возвращает `false`, а `slices.Equal` — `true`. В тестах на пустоту лучше проверять `len` или использовать `assert.Empty`.

**🎤 Прямая речь**
> Слайс создают через `var` — получится nil, через литерал, через `make` с длиной и capacity или срезом другого слайса или массива. nil-слайс и пустой слайс ведут себя одинаково: у обоих нулевая длина, по ним можно итерироваться, в оба можно делать `append` — в nil-слайс он просто выделит память.
>
> Разница проявляется на границах: nil равен `nil`, в JSON он превращается в `null`, а пустой — в `[]`, и `reflect.DeepEqual` их различает. Поэтому пустоту я всегда проверяю через `len(s) == 0`, а в API, где клиент ждёт массив, отдаю `make([]T, 0)`.

### 4. Как работает `append` и рост capacity (старая и новая формула)? Можно ли `append` к массиву? Напиши свой `append`

**⚡ Суть**
Если `cap` хватает, `append` пишет в тот же массив и возвращает слайс с большей `len`. Если нет — выделяет новый массив, копирует данные и возвращает слайс на него. Рост с Go 1.18: до 256 элементов — ×2, дальше плавный переход к ×1.25; до 1.18 было ×2 до 1024 элементов, потом ×1.25. Итог округляется вверх до класса размера аллокатора. К массиву `append` нельзя — только к слайсу (`arr[:]`).

**🔧 Под капотом**
- Рост делает `runtime.growslice`, новую ёмкость считает `nextslicecap`:
  - нужно больше, чем вдвое (`newLen > 2 × oldCap`) → `newcap = newLen`;
  - `oldCap < 256` → `newcap = 2 × oldCap`;
  - иначе в цикле `newcap += (newcap + 3 × 256) / 4`, пока не хватит. Коэффициент плавно падает с 2 до 1.25.
- Затем размер в байтах округляется до класса [аллокатора](glossary.md#allocator), поэтому реальный `cap` бывает больше формулы. Замер для `[]int` при росте по одному элементу: `1 2 4 8 … 256 512 848 1280 1792 2560` (848 — это 832 после округления).
- Сложность — амортизированная O(1): при геометрическом росте суммарное копирование ≤ ~2n.
- Компилятор оптимизирует `append` в циклах: с Go 1.25 неубегающий слайс может начать с буфера на [стеке](glossary.md#stack-heap), поэтому наблюдаемые значения `cap` отличаются от формулы. На точное значение `cap` полагаться нельзя.

```go
// упрощённый append: без плавного перехода к ×1.25 и без округления
func appendInt(s []int, vals ...int) []int {
    n := len(s) + len(vals)
    if n > cap(s) {
        ns := make([]int, len(s), max(2*cap(s), n))
        copy(ns, s)
        s = ns
    }
    s = s[:n]
    copy(s[n-len(vals):], vals)
    return s
}
```

**⚠️ Подвохи и версии Go**
- Результат `append` всегда присваивай: `s = append(s, x)`. Слайс мог переехать в новый массив.
- Если размер известен, выдели память заранее: `make([]T, 0, n)` — одна аллокация вместо нескольких.
- Формула роста изменилась в Go 1.18: старый порог был 1024 элемента.

**🎤 Прямая речь**
> `append` сначала проверяет capacity. Если место есть, элемент пишется в тот же базовый массив и возвращается слайс с увеличенной длиной. Если места нет, рантайм через `growslice` выделяет новый массив, копирует данные и возвращает слайс на него. Поэтому результат `append` обязательно присваивают обратно.
>
> С Go 1.18 маленькие слайсы до 256 элементов растут вдвое, а большие — плавно переходят к росту примерно на 25%. Раньше порог был 1024. Потом размер округляется до класса размера аллокатора, так что реальная capacity бывает чуть больше. За счёт геометрического роста `append` амортизированно O(1). В горячем коде я заранее выделяю память через `make` с capacity, чтобы избежать промежуточных копирований.

### 5. Общий базовый массив: когда изменение одного слайса видно в другом?

**⚡ Суть**
Слайсы, полученные срезом одного массива, делят память: изменение элемента видно во всех — пока `append` не вызвал переаллокацию. `append` в подслайс, у которого есть запас `cap`, **перезаписывает** элементы исходного слайса.

**🔧 Под капотом**
- Срез не копирует данные: новый заголовок указывает в тот же массив, и `cap(sub) = cap(base) − low`.
- `append` в пределах `cap` пишет на месте — прямо в чужие элементы. Выход за `cap` — новый массив, и связь рвётся.

```go
base := []int{1, 2, 3, 4, 5}
sub := base[1:3] // [2 3], cap 4
sub[0] = 20      // видно в base
sub = append(sub, 40) // запас cap есть → затирает base[3]
fmt.Println(base, sub, len(sub), cap(sub))
// [1 20 3 40 5] [20 3 40] 3 4
```

**⚠️ Подвохи и версии Go**
- Поведение зависит от `cap`, поэтому баг «то есть, то нет».
- Два `append` от одного слайса:
  ```go
  x := []int{1, 2, 3}
  a := append(x[:2], 10)
  b := append(x[:2], 20)
  fmt.Println(a, b, x) // [1 2 20] [1 2 20] [1 2 20] — все три смотрят в один массив
  ```
- Защита — полное выражение среза `s[a:b:c]` ([вопрос 7](#q1-3-07)) или явная копия.

**🎤 Прямая речь**
> Срез не копирует данные — новый слайс смотрит в тот же базовый массив. Поэтому изменение элемента через один слайс видно через все остальные, которые перекрывают этот участок. Самое коварное — `append`: если у подслайса есть свободная capacity, `append` запишет элемент прямо в базовый массив и затрёт данные исходного слайса.
>
> Связь рвётся только тогда, когда `append` выходит за capacity и переаллоцирует массив. Из-за этого баг проявляется не всегда, а в зависимости от capacity. Защищаюсь полным выражением среза `s[a:b:b]`, которое обрезает capacity, или явным копированием, когда отдаю часть слайса наружу.

<a id="q1-3-06"></a>
### 6. Слайс передан в функцию: изменится ли он снаружи при изменении элемента? А при `append`?

**⚡ Суть**
Слайс передаётся по значению: копируется заголовок (24 байта), а массив общий. Изменение элементов видно снаружи; `append` — нет: внутри функции меняется `len` (а при переаллокации и указатель) у копии заголовка. Чтобы изменения дошли, функция возвращает слайс или принимает `*[]T`.

**🔧 Под капотом**
- Внутри функции заголовок — отдельная переменная. `append` в пределах `cap` пишет в общий массив, но длина вызывающего слайса не меняется, поэтому новый элемент «не виден».
- Если `append` переаллоцировал массив, дальнейшие изменения элементов внутри функции идут уже в **новый** массив и снаружи не видны.

```go
func add(s []int) {
    s = append(s, 100) // cap хватает → пишет в общий массив
    s[0] = -1          // тот же массив → видно снаружи
}

s := make([]int, 3, 10)
add(s)
fmt.Println(s, len(s), s[:4]) // [-1 0 0] 3 [-1 0 0 100]
```
Если бы у `s` не было запаса `cap`, `append` создал бы новый массив и `s[0] = -1` снаружи бы не появилось.

**⚠️ Подвохи и версии Go**
- Идиома — функция возвращает слайс, как сам `append`: `s = process(s)`.
- С map не так: map — указатель на структуру рантайма, и любые изменения видны снаружи.

**🎤 Прямая речь**
> В Go всё передаётся по значению, и слайс не исключение: функция получает копию заголовка, но указатель в нём смотрит на тот же массив. Поэтому изменение элементов видно снаружи, а `append` — нет: он меняет длину в копии заголовка. Даже если элемент физически записался в общий массив, вызывающий его не увидит, потому что у него старая длина.
>
> Есть тонкость: если `append` внутри функции вызвал переаллокацию, все последующие изменения элементов пойдут уже в новый массив. Чтобы не гадать, я делаю как стандартная библиотека — функция возвращает новый слайс, и вызывающий присваивает результат.

### 7. Реслайсинг `s[a:b]`; полное выражение `s[a:b:c]` — зачем?

**⚡ Суть**
`s[a:b]` — новый слайс над тем же массивом: `len = b − a`, `cap = cap(s) − a`. Полное выражение `s[a:b:c]` ограничивает ёмкость (`cap = c − a`), чтобы `append` в результат не мог затереть данные исходного слайса: при выходе за `cap` он переаллоцирует.

**🔧 Под капотом**
- Границы: `0 ≤ a ≤ b ≤ c ≤ cap(s)`. Расширять срез можно до `cap`: `s[:cap(s)]` показывает элементы за пределами `len`.
- Полное выражение ничего не копирует — оно только уменьшает `cap` в новом заголовке.

```go
base := []int{1, 2, 3, 4, 5}
safe := base[1:3:3]     // len 2, cap 2
safe = append(safe, 40) // cap не хватает → новый массив
fmt.Println(base, safe) // [1 2 3 4 5] [2 3 40] — base не тронут
```

**⚠️ Подвохи и версии Go**
- Применение: функция отдаёт часть своего буфера наружу — `return buf[i:j:j]`.
- `slices.Clip(s)` (Go 1.21) — то же, что `s[:len(s):len(s)]`.
- `s[:cap(s)]` может «оживить» старые данные за пределами `len`.
- Элементы в пределах `len` по-прежнему общие: запись `safe[0] = x` до `append` изменит `base[1]`.
- Для строк трёхиндексной формы нет.

**🎤 Прямая речь**
> Реслайсинг `s[a:b]` даёт новый заголовок над тем же массивом: длина `b − a`, а capacity тянется до конца исходного массива. Отсюда проблема — `append` в такой подслайс может перезаписать данные исходного слайса.
>
> Полное выражение `s[a:b:c]` задаёт ещё и границу capacity. Если сделать `c = b`, свободного места нет, и первый же `append` выделит новый массив, оставив исходные данные нетронутыми. Я использую это, когда возвращаю часть внутреннего буфера наружу, или вызываю `slices.Clip`, который делает то же самое.

### 8. Как скопировать слайс (`copy`, трюк с `append`)? Как слить два слайса?

**⚡ Суть**
`copy(dst, src)` копирует `min(len(dst), len(src))` элементов и возвращает это число; у `dst` должна быть нужная `len`, а не `cap`. Полная копия: `slices.Clone(s)` (Go 1.21) или `append([]T(nil), s...)`. Слить: `append(a, b...)` или `slices.Concat(a, b, c)` (Go 1.22), который всегда возвращает новый слайс.

**🔧 Под капотом**
- `copy` выполняется через `memmove` и корректно работает при перекрытии (`copy(s, s[1:])` — сдвиг влево).
- Копия поверхностная: указатели, вложенные слайсы и map остаются общими.
- `append(a, b...)` может записать `b` в свободную ёмкость `a` — если `a` разделяет массив с кем-то ещё, это порча данных.

```go
dst := make([]int, 2)
n := copy(dst, []int{1, 2, 3})
fmt.Println(n, dst) // 2 [1 2]

buf := make([]int, 0, 3)
fmt.Println(copy(buf, []int{1, 2, 3}), buf) // 0 [] — len 0, копировать некуда

c := slices.Clone(s)                     // полная копия; Clone(nil) == nil
all := slices.Concat([]int{1}, []int{2, 3}) // [1 2 3] — новый массив
```

**⚠️ Подвохи и версии Go**
- `copy` в `make([]T, 0, n)` копирует 0 элементов — классическая ошибка. Нужно `make([]T, n)`.
- Для глубокой копии вложенных структур копируй элементы вручную.

**🎤 Прямая речь**
> Встроенный `copy` копирует столько элементов, сколько помещается в длину приёмника, и возвращает их число. Важно, что считается именно длина, а не capacity: копирование в `make([]T, 0, n)` ничего не скопирует. Самый простой способ сделать полную копию — `slices.Clone` или старый трюк `append([]T(nil), s...)`.
>
> Слить слайсы можно через `append(a, b...)`, но если у `a` есть свободная capacity и он с кем-то делит массив, `append` запишет данные прямо туда. Поэтому для безопасного слияния использую `slices.Concat` из Go 1.22 — он всегда создаёт новый слайс. И помню, что любая такая копия поверхностная.

<a id="q1-3-09"></a>
### 9. Удаление элемента с сохранением порядка и без

**⚡ Суть**
С сохранением порядка — сдвиг хвоста: `s = append(s[:i], s[i+1:]...)` или `slices.Delete(s, i, i+1)`, O(n). Без сохранения — поставить на место `i` последний элемент и укоротить слайс, O(1).

**🔧 Под капотом**
- Сдвиг хвоста — это `memmove` внутри того же массива.
- `slices.Delete` с Go 1.22 зануляет освободившиеся элементы в хвосте (`clear`), чтобы [GC](glossary.md#gc) мог собрать объекты, на которые они ссылались.

```go
d := []int{1, 2, 3, 4, 5}
d = slices.Delete(d, 1, 2)
fmt.Println(d, d[:5]) // [1 3 4 5] [1 3 4 5 0] — хвост занулён

sw := []int{1, 2, 3, 4, 5}
i := 1
sw[i] = sw[len(sw)-1] // без сохранения порядка
sw = sw[:len(sw)-1]
fmt.Println(sw) // [1 5 3 4]
```

**⚠️ Подвохи и версии Go**
- Исходная переменная, если она смотрит в тот же массив, увидит сдвинутые данные.
- Удаление в цикле по индексу пропускает элементы; для удаления по условию есть `slices.DeleteFunc`.
- При ручном варианте с `append` хвост с указателями остаётся в массиве и держит объекты в памяти. Перед укорачиванием обнули его: `s[len(s)-1] = nil` или `clear`.

**🎤 Прямая речь**
> Если порядок важен, элемент удаляют сдвигом хвоста: `append(s[:i], s[i+1:]...)` или `slices.Delete`. Это линейная операция, потому что сдвигаются все элементы после удаляемого. Если порядок не важен, есть приём за O(1): ставим на место удаляемого последний элемент и укорачиваем слайс на один.
>
> Из ловушек — память: после ручного удаления в хвосте массива остаются ссылки, и GC не соберёт эти объекты. `slices.Delete` начиная с Go 1.22 сам зануляет хвост, а при ручном удалении я делаю это явно. Для удаления по условию беру `slices.DeleteFunc`, а не цикл с индексами.

<a id="q1-3-10"></a>
### 10. Удалить дубликаты из слайса без переаллокации — можно ли?

**⚡ Суть**
Да: уникальные элементы перезаписываются в начало того же слайса (через индекс записи), а затем слайс обрезается. Если порядок не важен — `slices.Sort` + `slices.Compact`, обе работают на месте. Если порядок важен — тот же приём плюс map «уже видел» (map аллоцирует, массив слайса — нет).

**🔧 Под капотом**
- `slices.Compact` убирает **соседние** дубликаты двумя указателями за O(n); с Go 1.22 зануляет хвост.
- `slices.Sort` — [pdqsort](glossary.md#pdqsort) на месте, O(n log n).

```go
dd := []int{3, 1, 3, 2, 1, 2}
slices.Sort(dd)
dd = slices.Compact(dd) // [1 2 3]

w := []int{3, 1, 3, 2, 1, 2} // с сохранением порядка
seen := map[int]bool{}
k := 0
for _, v := range w {
    if !seen[v] {
        seen[v] = true
        w[k] = v
        k++
    }
}
clear(w[k:]) // зануляем хвост (важно для указателей)
w = w[:k]    // [3 1 2]
```

**⚠️ Подвохи и версии Go**
- `Compact` без предварительной сортировки уберёт только идущие подряд дубликаты.
- Для структур — `slices.CompactFunc` или map по ключу.
- `clear` — встроенная функция с Go 1.21.

**🎤 Прямая речь**
> Да, можно — алгоритмом с двумя указателями на месте. Один индекс читает, второй пишет: уникальный элемент копируется в позицию записи, в конце слайс обрезается по ней. Новая память под слайс не нужна. Если порядок неважен, проще всего отсортировать через `slices.Sort` и вызвать `slices.Compact`, который убирает соседние дубликаты.
>
> Если порядок важен, использую тот же приём с map просмотренных значений: массив слайса переиспользуется, аллоцирует только map. И не забываю занулить хвост через `clear`, если элементы содержат указатели.

<a id="q1-3-11"></a>
### 11. Как сделать из слайса массив?

**⚡ Суть**
С Go 1.20 — прямая конверсия `[N]T(s)`: копирует первые N элементов в новый массив. С Go 1.17 — `(*[N]T)(s)`: указатель на массив поверх данных слайса, без копирования. Если `len(s) < N` — паника.

**🔧 Под капотом**
- Обе конверсии проверяют длину в рантайме. Значение копируется через `memmove`, а указатель просто переинтерпретирует адрес начала данных слайса.

```go
src := []int{1, 2, 3, 4}
ar := [3]int(src)      // копия
ap := (*[3]int)(src)   // окно в тот же массив
ap[0] = 100
fmt.Println(ar, src)   // [1 2 3] [100 2 3 4]

_ = [5]int(src)
// panic: runtime error: cannot convert slice with length 4 to array or pointer to array with length 5
```

**⚠️ Подвохи и версии Go**
- `N` должно быть константой. Ошибка длины — паника в рантайме, а не ошибка компиляции.
- До Go 1.17 писали `copy(arr[:], s)`.
- Применение: ключи фиксированной длины, UUID и хеши из байтового слайса.

**🎤 Прямая речь**
> Начиная с Go 1.20 слайс можно напрямую конвертировать в массив: `[N]T(s)` копирует первые N элементов. С Go 1.17 есть конверсия в указатель на массив, `(*[N]T)(s)`, — она не копирует данные, а даёт окно в тот же базовый массив, поэтому изменения видны через слайс.
>
> В обоих случаях длина проверяется в рантайме: если в слайсе меньше N элементов, будет паника. Я использую это, например, чтобы превратить байты хеша или UUID в массив фиксированного размера и сделать его ключом map.

<a id="q1-3-12"></a>
### 12. Что лучше — связный список или массив? Почему (локальность, кэш CPU)?

**⚡ Суть**
Почти всегда слайс. Элементы лежат подряд, процессор читает их [кэш-линиями](glossary.md#cache-line) и подгружает следующие заранее (prefetch), нет аллокации и указателя на каждый элемент. Список выигрывает только при O(1) вставке и удалении по уже известному узлу — например, в LRU-кэше (map + двусвязный список).

**🔧 Под капотом**
- Кэш-линия — 64 байта, в неё помещаются 8 значений `int64`. Проход по слайсу — последовательное чтение, идеальное для кэша.
- Связный список — это прыжки по указателям: каждый узел — отдельный объект в [куче](glossary.md#stack-heap), каждый переход грозит промахом кэша, а [GC](glossary.md#gc) обходит каждый указатель.
- `container/list` хранит значения как `any` — ещё аллокации и приведения типов.
- Вставка в середину слайса формально O(n), но `memmove` настолько быстрый, что на тысячах элементов слайс обычно быстрее списка даже на вставках.

**⚠️ Подвохи и версии Go**
- Big-O — не всё: важны константы и иерархия памяти.
- Для очереди лучше кольцевой буфер на слайсе или канал, а не список.

**🎤 Прямая речь**
> В большинстве случаев слайс быстрее, даже там, где по асимптотике выигрывает список. Элементы слайса лежат в памяти подряд, процессор читает их целыми кэш-линиями и подгружает заранее. Список — это узлы, разбросанные по куче: каждый переход по указателю может стоить промаха кэша, каждый узел — отдельная аллокация и лишняя работа для GC.
>
> Список оправдан, когда нужна O(1) вставка или удаление по уже известному узлу без сдвигов — классический пример LRU-кэш из map и двусвязного списка. Во всех остальных случаях беру слайс, а для очередей — кольцевой буфер.

<a id="q1-3-13"></a>
### 13. Big-O всех операций со слайсом

**⚡ Суть**
Доступ по индексу, `len`, `cap` и срез — O(1); `append` — амортизированно O(1); вставка и удаление в середине — O(n); поиск — O(n), а в отсортированном слайсе — O(log n); сортировка — O(n log n).

**🔧 Под капотом**

| Операция | Сложность |
|---|---|
| `s[i]`, `len(s)`, `cap(s)` | O(1) |
| Срез `s[a:b]` | O(1) — новый заголовок |
| `append` | амортизированно O(1), при росте O(n) |
| Вставка или удаление в середине | O(n) — сдвиг хвоста |
| Удаление без сохранения порядка | O(1) |
| `slices.Contains`, `Index` | O(n) |
| `slices.BinarySearch` (слайс отсортирован) | O(log n) |
| `copy`, `Clone`, `Concat`, `Reverse`, `Compact` | O(n) |
| `slices.Sort` | O(n log n) |

- Амортизация `append`: ёмкость растёт геометрически, поэтому суммарное копирование при n вставках — O(n), то есть O(1) на операцию. При коэффициенте 1.25 константа больше, но асимптотика та же.

**⚠️ Подвохи и версии Go**
- «`append` — O(1)» верно только в среднем: конкретный вызов с ростом стоит O(n).
- Вставка в начало слайса в цикле даёт O(n²) — лучше собрать в обратном порядке и развернуть.

**🎤 Прямая речь**
> Доступ по индексу, длина, capacity и срез — константные операции, срез создаёт только новый заголовок. `append` амортизированно O(1): ёмкость растёт геометрически, поэтому редкие дорогие копирования размазываются по всем вставкам. Вставка или удаление в середине — O(n) из-за сдвига, удаление без сохранения порядка — O(1).
>
> Поиск линейный, а в отсортированном слайсе через `slices.BinarySearch` — логарифмический; сортировка — O(n log n). На практике я дополнительно смотрю на аллокации: предвыделение через `make` убирает копирования при росте.

### 14. Утечка памяти через подслайс — как избежать?

**⚡ Суть**
Подслайс держит в памяти весь базовый массив. Вырезал 10 байт из буфера на 10 МБ — GC не освободит эти 10 МБ, пока жив подслайс. Лечение — скопировать нужное (`slices.Clone`, `append([]T(nil), sub...)`). Вторая утечка: указатели за пределами `len` после удаления или укорачивания остаются достижимыми — их надо занулять.

**🔧 Под капотом**
- [GC](glossary.md#gc) отслеживает достижимость целых объектов, а не диапазонов: указатель внутрь блока держит живым весь блок.
- Элементы между `len` и `cap` — часть того же объекта. Если в них лежат указатели, объекты по ним тоже остаются живыми.

```go
func firstLine(data []byte) []byte {
    i := bytes.IndexByte(data, '\n')
    if i < 0 {
        i = len(data)
    }
    return slices.Clone(data[:i]) // без Clone вернули бы окно во весь data
}

// очередь на слайсе
q[0] = nil // обнулить голову, если элементы — указатели
q = q[1:]
```

**⚠️ Подвохи и версии Go**
- То же со строками: подстрока держит всю строку, лечится `strings.Clone`.
- Очередь вида `q = q[1:]` бесконечно держит уже обработанные элементы в начале массива.
- Типичный сценарий: прочитали большой файл или ответ целиком, а сохранили маленький кусок.

**🎤 Прямая речь**
> GC в Go освобождает объекты целиком, поэтому маленький подслайс, который ссылается на большой массив, держит в памяти весь массив. Классика — прочитать мегабайтный ответ, вырезать из него ID и положить в долгоживущий кэш: в памяти останется весь мегабайт. Лечится явной копией нужного куска через `slices.Clone`.
>
> Вторая разновидность — указатели в хвосте за пределами длины. После удаления элементов или в очереди на слайсе они остаются в массиве и не дают GC собрать объекты. Поэтому я зануляю освободившиеся элементы через `clear` или использую `slices.Delete`, который с 1.22 делает это сам.

<a id="q1-3-15"></a>
### 15. Пакет `slices` (Go 1.21+) — что знать

**⚡ Суть**
`slices` (Go 1.21) — дженерик-функции для работы со слайсами: сортировка и поиск, сравнение, вставка и удаление, клонирование. В Go 1.22 добавился `Concat`, в 1.23 — функции-итераторы (`All`, `Values`, `Backward`, `Collect`, `Sorted`, `Chunk`) и `Repeat`.

**🔧 Под капотом**
- Функции на дженериках, без [рефлексии](glossary.md#reflection), поэтому быстрее старого `sort.Slice`. `Sort` — [pdqsort](glossary.md#pdqsort).
- `Delete`, `DeleteFunc`, `Compact`, `Replace` с Go 1.22 зануляют освободившийся хвост.
- Функции, которые меняют длину, возвращают новый слайс — его нужно присвоить, как с `append`.

| Группа | Функции |
|---|---|
| Поиск | `Contains`, `Index`, `IndexFunc`, `BinarySearch`, `BinarySearchFunc` |
| Сортировка | `Sort`, `SortFunc`, `SortStableFunc`, `IsSorted` |
| Изменение | `Insert`, `Delete`, `DeleteFunc`, `Replace`, `Compact`, `CompactFunc`, `Reverse` |
| Память | `Clone`, `Grow`, `Clip` |
| Сравнение | `Equal`, `EqualFunc`, `Compare`, `Min`, `Max` |
| Go 1.22 | `Concat` |
| Go 1.23 | `All`, `Values`, `Backward`, `AppendSeq`, `Collect`, `Sorted`, `SortedFunc`, `SortedStableFunc`, `Chunk`, `Repeat` |

```go
s = slices.Insert(s, 1, 42)
s = slices.DeleteFunc(s, func(v int) bool { return v < 0 })
i, found := slices.BinarySearch([]int{1, 3, 5, 7}, 5) // 2 true
keys := slices.Sorted(maps.Keys(m))                   // отсортированные ключи map (1.23)
```

**⚠️ Подвохи и версии Go**
- Результат функций, меняющих длину, нужно присваивать: `s = slices.Delete(...)`.
- `Sort` нестабильна; для стабильной сортировки — `SortStableFunc`.
- `slices.Equal(nil, []int{})` — `true`, в отличие от `reflect.DeepEqual`.
- Вместе со `slices` в Go 1.21 появились пакет `maps` и встроенные `min`, `max`, `clear`.

**🎤 Прямая речь**
> Пакет `slices` появился в Go 1.21 вместе с дженериками в стандартной библиотеке и закрыл большую часть ручного кода: поиск, бинарный поиск, сортировка, вставка, удаление, `Compact`, `Clone`, сравнение. Всё на дженериках, без рефлексии, поэтому `slices.SortFunc` быстрее старого `sort.Slice`.
>
> Дальше пакет дополнялся: в 1.22 появился `Concat`, а функции удаления начали занулять хвост; в 1.23 — итераторы, например `slices.Sorted(maps.Keys(m))` даёт отсортированные ключи map одной строкой. Главное правило — функции, которые меняют длину, возвращают новый слайс, и его нужно присвоить.

<a id="q1-3-16"></a>
### 16. Как отсортировать слайс структур по полю (`sort.Slice`, `slices.SortFunc`)?

**⚡ Суть**
Сейчас стандарт — `slices.SortFunc(users, func(a, b User) int { return cmp.Compare(a.Name, b.Name) })` (Go 1.21): дженерик, без рефлексии, быстрее. Классический вариант — `sort.Slice(users, func(i, j int) bool { return users[i].Name < users[j].Name })`. Стабильная сортировка — `slices.SortStableFunc` / `sort.SliceStable`, несколько ключей — `cmp.Or` (Go 1.22).

**🔧 Под капотом**
- `sort.Slice` переставляет элементы через [рефлексию](glossary.md#reflection) и сравнивает их через замыкание по индексам. `slices.SortFunc` — дженерик, компаратор возвращает `int` (<0, 0, >0).
- Обе нестабильные, алгоритм — [pdqsort](glossary.md#pdqsort) (с Go 1.19), O(n log n). Стабильные варианты медленнее.

```go
users := []User{{"Bob", 30}, {"alice", 25}, {"Ann", 30}}

sort.Slice(users, func(i, j int) bool { return users[i].Name < users[j].Name })
// [{Ann 30} {Bob 30} {alice 25}] — "alice" в конце: сравнение по байтам

slices.SortFunc(users, func(a, b User) int {
    return cmp.Or(
        cmp.Compare(b.Age, a.Age),   // по возрасту, по убыванию
        cmp.Compare(a.Name, b.Name), // затем по имени
    )
})
```

**⚠️ Подвохи и версии Go**
- Сравнение строк побайтовое и регистрозависимое: `"alice"` встанет после `"Bob"`. Для «человеческого» порядка — `strings.ToLower` или `golang.org/x/text/collate`.
- Компаратор должен задавать согласованный порядок; противоречивое сравнение даёт мусорный результат.
- В `sort.Slice` замыкание должно обращаться к тому же слайсу, который сортируется.

**🎤 Прямая речь**
> Сегодня я сортирую через `slices.SortFunc` с компаратором на `cmp.Compare`: это дженерик-функция из Go 1.21, без рефлексии, и работает быстрее классического `sort.Slice`. Для сортировки по нескольким полям удобен `cmp.Or` из 1.22 — он берёт первое ненулевое сравнение, например сначала по возрасту, потом по имени.
>
> Обе функции используют pdqsort и нестабильны, поэтому если важен исходный порядок равных элементов, беру `SortStableFunc`. Из ловушек — сравнение строк регистрозависимое и побайтовое, поэтому «alice» окажется после «Bob»; для пользовательской сортировки нужна нормализация регистра или collation из `x/text`.
