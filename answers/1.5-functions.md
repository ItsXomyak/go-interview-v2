### 1. Зачем нужны функции? Функции как значения (first-class)

**⚡ Суть**
Функция — именованный кусок логики с входами и выходами: переиспользование, изоляция и тестируемость. В Go функции — значения первого класса: их можно присвоить переменной, передать аргументом, вернуть из функции, положить в map или поле структуры.

```go
func apply(xs []int, f func(int) int) []int {
	out := make([]int, 0, len(xs))
	for _, x := range xs {
		out = append(out, f(x))
	}
	return out
}

double := func(x int) int { return x * 2 }
fmt.Println(apply([]int{1, 2, 3}, double)) // [2 4 6]

ops := map[string]func(int, int) int{
	"+": func(a, b int) int { return a + b },
	"*": func(a, b int) int { return a * b },
}
fmt.Println(ops["+"](2, 3), ops["*"](2, 3)) // 5 6
```

**🔧 Под капотом**
- Значение функционального типа — один указатель (8 байт) на структуру `funcval`. В её первом слове — адрес машинного кода, дальше могут лежать захваченные переменные замыкания ([вопрос 3](#q1-5-03)).
- Вызов через переменную — косвенный: адрес `funcval` кладётся в специальный регистр (closure context pointer: `RDX` на amd64, `R26` на arm64), код функции достаёт оттуда захваченные данные.
- Прямой вызов именованной функции компилятор может встроить ([inlining](glossary.md#inlining)), косвенный — обычно нет.

**⚠️ Подвохи и версии Go**
- Нулевое значение функционального типа — `nil`, вызов nil-функции — [паника](glossary.md#panic-recover) `invalid memory address or nil pointer dereference`.
- Функции сравниваются только с `nil`: `f == g` — ошибка компиляции `invalid operation: f == g (func can only be compared to nil)`. Поэтому функцию нельзя сделать ключом map.
- Функциональные типы — основа стандартной библиотеки: `http.HandlerFunc`, `sort.Slice`, `strings.Map`, `slices.SortFunc`.

**🎤 Прямая речь**
> Функции нужны, чтобы разбить логику на понятные, переиспользуемые и тестируемые куски. В Go функции — значения первого класса: их присваивают переменным, передают в другие функции, возвращают и хранят в map. На этом построены колбэки, middleware, стратегии вроде компаратора в `slices.SortFunc`.
>
> Под капотом функциональное значение — указатель на структуру `funcval`, где лежит адрес кода и, для замыканий, захваченные переменные. Сравнивать функции можно только с nil, и вызов nil-функции даёт панику.

### 2. Чем полезны анонимные и вариативные функции?

**⚡ Суть**
Анонимная функция — функциональный литерал без имени, объявленный прямо там, где нужен: колбэк, [горутина](glossary.md#goroutine), `defer`. Вариативная функция принимает переменное число аргументов последнего параметра: `func f(xs ...int)`. Внутри `xs` — обычный слайс.

```go
func sum(nums ...int) int {
	t := 0
	for _, n := range nums {
		t += n
	}
	return t
}

fmt.Println(sum(), sum(1, 2, 3)) // 0 6
s := []int{1, 2, 3}
fmt.Println(sum(s...))           // 6: передаём готовый слайс
```

**🔧 Под капотом**
- `sum(1, 2, 3)` компилятор превращает в `sum([]int{1, 2, 3})`: создаётся новый слайс (если он не убегает, то на [стеке](glossary.md#stack-heap)).
- `sum()` без аргументов передаёт `nil`-слайс.
- `sum(s...)` передаёт **тот же** слайс без копирования — функция видит и может изменить исходный массив:
  ```go
  func zero(nums ...int) { nums[0] = 100 }
  s := []int{1, 2, 3}
  zero(s...)
  fmt.Println(s) // [100 2 3]
  ```

**Где полезны анонимные функции:**
- колбэки и компараторы: `slices.SortFunc(a, func(x, y T) int { … })`;
- запуск горутины: `go func() { … }()`;
- `defer func() { … }()` — например, с `recover`;
- замыкания со состоянием ([вопрос 3](#q1-5-03));
- немедленный вызов `func() { … }()`, чтобы ограничить область видимости переменных.

**Где полезны вариативные:** `fmt.Println(a ...any)`, `append(s, xs...)`, необязательные параметры и [функциональные опции](#q1-5-12).

**⚠️ Подвохи и версии Go**
- Вариативным может быть только последний параметр.
- `[]string` нельзя передать в `...any`: `fmt.Println(s...)` — ошибка `cannot use s (variable of type []string) as []any value in argument to fmt.Println`. Нужно сначала собрать `[]any`.
- `f(s...)` разделяет массив с вызывающим кодом: если функция меняет элементы или делает `append` в пределах capacity, это видно снаружи.

**🎤 Прямая речь**
> Анонимные функции удобны там, где логика нужна в одном месте: колбэк для сортировки, тело горутины, отложенный вызов с recover. Плюс они могут захватывать переменные из окружения и становиться замыканиями.
>
> Вариативная функция принимает любое число аргументов последнего параметра, а внутри это обычный слайс. Важная деталь: при вызове `f(s...)` слайс передаётся как есть, без копии, поэтому функция может изменить элементы исходного массива. А при вызове без аргументов внутри будет nil-слайс.

### 3. Замыкание: что это, примеры, где полезно

**⚡ Суть**
Замыкание — функция вместе с переменными из окружающей области видимости, которые она использует. Переменные захватываются по ссылке: замыкание видит и меняет саму переменную, а не её копию на момент создания.

```go
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}

c1, c2 := counter(), counter()
fmt.Println(c1(), c1(), c1(), c2()) // 1 2 3 1 — у каждого замыкания свой n

x := 1
g := func() { x++ }
g(); g()
fmt.Println(x) // 3
```

**🔧 Под капотом**
- Замыкание — `funcval`: адрес кода + захваченные переменные.
- Семантически захват всегда по ссылке. Оптимизация компилятора: переменную до 128 байт, которую не переприсваивают и адрес которой не берут, он копирует в замыкание по значению — поведение от этого не меняется.
- Если замыкание переживает функцию, где создано, захваченная переменная уходит в [кучу](glossary.md#stack-heap). Это видно в `-gcflags=-m`:
  ```
  esc/main.go:6:2: moved to heap: n
  esc/main.go:7:9: func literal escapes to heap
  ```
  Замыкание, которое не выходит за пределы функции, может остаться на стеке вместе с переменными.

**Где полезно:** генераторы и счётчики, middleware (`func(next http.Handler) http.Handler`), мемоизация, функциональные опции, отложенные действия в `defer`, передача контекста в колбэк без глобальных переменных.

**⚠️ Подвохи и версии Go**
- **Переменная цикла.** До Go 1.22 переменная цикла была одна на весь цикл, и все замыкания видели последнее значение. С 1.22 переменная создаётся на каждой итерации. Поведение зависит от строки `go` в `go.mod`:
  ```go
  var fs []func()
  for i := 0; i < 3; i++ {
  	fs = append(fs, func() { fmt.Print(i, " ") })
  }
  for _, f := range fs {
  	f()
  }
  // go 1.21 в go.mod: 3 3 3
  // go 1.22 и новее:  0 1 2
  ```
- Захват большой структуры или слайса держит их в памяти, пока живо замыкание.
- Замыкание в [горутине](glossary.md#goroutine), которое меняет общую переменную, — гонка данных; нужна синхронизация.

**🎤 Прямая речь**
> Замыкание — это функция плюс переменные из внешней области видимости, которые она использует. Захват идёт по ссылке: если замыкание меняет переменную, это видно снаружи, и наоборот. Классический пример — счётчик, который возвращает функцию, увеличивающую свой собственный n.
>
> Под капотом замыкание — структура [funcval](glossary.md#funcval) с адресом кода и захваченными переменными. Если замыкание живёт дольше функции, где создано, переменные уходят в кучу — это видно через `-gcflags=-m`. И стоит помнить про переменную цикла: до Go 1.22 все замыкания в цикле видели одно и то же последнее значение, с 1.22 у каждой итерации своя переменная.

### 4. Рекурсия: примеры, какие проблемы (глубина стека, производительность)?

**⚡ Суть**
Рекурсия — функция, которая вызывает саму себя, уменьшая задачу до базового случая. Естественна для деревьев, графов, перебора, «разделяй и властвуй». Проблемы: каждый вызов занимает кадр [стека](glossary.md#stack-heap), повторные вычисления могут дать экспоненциальное время, а хвостовую рекурсию Go не оптимизирует.

**🔧 Под капотом**
- Стек [горутины](glossary.md#goroutine) начинается с 2 КБ (с Go 1.19 стартовый размер подстраивается под средний размер стеков) и растёт: при нехватке рантайм выделяет стек вдвое больше и копирует туда старый, исправляя указатели.
- Лимит стека — 1 ГБ на 64-битных системах (`maxstacksize = 1000000000` в рантайме), 250 МБ на 32-битных. Меняется через `debug.SetMaxStack`.
- Поэтому глубина в миллион вызовов работает (`depth(1_000_000)` проходит), а бесконечная рекурсия падает:
  ```
  runtime: goroutine stack exceeds 1000000000-byte limit
  fatal error: stack overflow
  ```
  Это [fatal error](glossary.md#fatal-error), а не [паника](glossary.md#panic-recover): `recover` её не ловит, процесс завершается.
- Хвостовой рекурсии ([TCO](glossary.md#tco)) в Go нет: даже `return f(n-1)` занимает новый кадр.

**⚠️ Подвохи и версии Go**
- Наивная рекурсия с повторными подзадачами экспоненциальна: `fib(40)` рекурсивно — ~430 мс, циклом — ~125 нс (замер на Go 1.26). Лечится мемоизацией или переходом к циклу (DP).
- Каждый кадр стоит памяти и времени на вызов; глубокую рекурсию по данным от пользователя (вложенный JSON, дерево) лучше ограничивать или переписывать на явный стек.
- Рекурсивное замыкание объявляется в два шага: `var dfs func(int)`, затем `dfs = func(i int) { … dfs(i + 1) … }`.

**🎤 Прямая речь**
> Рекурсия — когда функция вызывает саму себя на меньшей подзадаче, пока не дойдёт до базового случая. Она естественна для деревьев, графов и перебора. В Go стек горутины начинается с пары килобайт и растёт копированием, лимит — гигабайт на 64-битной системе, поэтому глубина в сотни тысяч вызовов обычно работает. Но бесконечная рекурсия заканчивается fatal error stack overflow, который recover не ловит.
>
> Проблемы две: память под кадры стека — хвостовую рекурсию Go не оптимизирует, — и повторные вычисления. Наивный рекурсивный Фибоначчи от 40 считается сотни миллисекунд против наносекунд у цикла. Поэтому для глубокой или повторяющейся рекурсии я использую мемоизацию, явный стек или цикл.

### 5. Передача аргументов: по значению или по ссылке? Какие типы ведут себя как ссылки?

**⚡ Суть**
В Go всё передаётся **по значению**: функция получает копию аргумента. Передачи по ссылке, как `&` в C++, нет. Но некоторые типы сами содержат указатель на данные — у них копируется маленький [дескриптор](glossary.md#type-descriptor), а данные остаются общими: указатели, слайсы, map, каналы, функции, интерфейсы.

```go
func modStruct(u User)        { u.Name = "changed" }     // копия структуры
func modPtr(u *User)          { u.Name = "changed" }     // копия указателя, данные общие
func reassignPtr(u *User)     { u = &User{"new"} }       // меняет только локальную копию
func modArray(a [3]int)       { a[0] = 100 }             // копия массива
func modSlice(s []int)        { s[0] = 100 }             // общий массив
func appendSlice(s []int)     { s = append(s, 4) }       // новая длина — только в копии
func modMap(m map[string]int) { m["a"] = 100 }           // общая хеш-таблица
func newMap(m map[string]int) { m = map[string]int{} }   // меняет только локальную копию

// struct: orig · ptr: changed · reassign ptr: changed
// array: [1 2 3] · slice: [100 2 3] 3 · map: map[a:100]
```

**🔧 Под капотом**

| Тип | Что копируется | Изменения внутри видны снаружи? |
|---|---|---|
| `int`, `string`, структура, массив | всё значение (у строки — заголовок 16 байт, данные общие, но неизменяемые) | нет |
| `*T` | 8-байтный указатель | да, через `*p`; переприсвоение `p` — нет |
| `[]T` | заголовок 24 байта | элементы — да; `append` и новая длина — нет ([1.3 · 6](1.3-slices.md#q1-3-06)) |
| `map`, `chan`, `func` | указатель на структуру рантайма | да |
| интерфейс | 16 байт: тип + указатель на данные | зависит от того, что внутри |

**⚠️ Подвохи и версии Go**
- «Слайс передаётся по ссылке» — неточно: копируется заголовок. `append` внутри функции не меняет длину снаружи — возвращай слайс.
- Большие структуры по значению — лишнее копирование; по указателю — копирование 8 байт, но объект может уйти в [кучу](glossary.md#stack-heap). Для небольших структур значение часто быстрее.
- Структуру с `sync.Mutex` нельзя передавать по значению — копируется и состояние мьютекса. `go vet` ловит: `show passes lock by value: …S contains sync.Mutex`.

**🎤 Прямая речь**
> В Go всё передаётся по значению — функция всегда получает копию. Просто у части типов эта копия — маленький дескриптор с указателем на общие данные: у указателей, слайсов, map, каналов, функций и интерфейсов. Поэтому изменение элементов слайса или записи в map видно снаружи, а переприсвоение самого параметра — нет.
>
> Самый частый подвох — слайс: элементы общие, но `append` внутри функции меняет только локальный заголовок, и вызывающий новую длину не увидит. Поэтому функции, которые добавляют элементы, возвращают слайс, как сам `append`.

### 6. Функция vs метод. Как создать свой метод? Можно ли объявить метод на типе из другого пакета?

**⚡ Суть**
Метод — функция с получателем (receiver): `func (c Counter) Value() int`. Методы задают поведение типа и позволяют ему реализовывать интерфейсы. Объявить метод можно только на типе из **своего** пакета — на `time.Duration` или `int` нельзя.

```go
func (d time.Duration) Double() time.Duration { return d * 2 }
// cannot define new methods on non-local type time.Duration
func (i int) Inc() int { return i + 1 }
// cannot define new methods on non-local type int
```

**🔧 Под капотом**
- Метод — обычная функция, у которой получатель стал первым аргументом. Это видно по method expression:
  ```go
  f := (*Counter).Inc // func(*Counter)
  f(&c)
  Counter.Value(c)    // то же, что c.Value()
  ```
- Method value `v := c.Value` связывает метод с получателем. Для value receiver получатель **копируется в момент вычисления**:
  ```go
  v := c.Value
  c.Inc()
  fmt.Println(v(), c.Value()) // 2 3: v видит старую копию c
  ```

**Как добавить метод к чужому типу:**
- Новый тип на его основе: `type MyDuration time.Duration` и методы на нём. Методы исходного типа при этом **не наследуются**.
- Встраивание в структуру: `type Timer struct{ time.Duration }` — методы `Duration` доступны, можно добавить свои.

**⚠️ Подвохи и версии Go**
- Получателем не может быть тип-указатель или интерфейс: `type P *int; func (p P) M()` — ошибка `invalid receiver type P (pointer or interface type)`.
- У методов не может быть своих параметров типа: `func (b Box[T]) Map[U any](…)` — `syntax error: method must have no type parameters` (Go 1.26).
- Метод с pointer receiver можно вызвать на nil-указателе — и обработать nil внутри:
  ```go
  func (l *List) Len() int {
  	if l == nil {
  		return 0
  	}
  	return 1 + l.next.Len()
  }
  ```

**🎤 Прямая речь**
> Метод — это функция с получателем, она привязана к типу. Через методы тип получает поведение и реализует интерфейсы. Под капотом метод — обычная функция, где получатель — первый аргумент, это видно по method expression вроде `(*T).Method`.
>
> Объявить метод можно только на типе из своего пакета: на `time.Duration` или `int` компилятор скажет «cannot define new methods on non-local type». Обходится это двумя способами: объявить свой тип на основе чужого — но тогда методы исходного типа теряются, — или встроить чужой тип в свою структуру, тогда его методы сохраняются и можно добавить новые.

### 7. Value receiver vs pointer receiver — когда что? Method set

**⚡ Суть**
Value receiver получает копию значения, pointer receiver — указатель и может менять оригинал. [Method set](glossary.md#method-set) определяет, какие интерфейсы реализует тип: у `T` — только методы с value receiver, у `*T` — все методы.

```go
type Counter struct{ n int }

func (c *Counter) Inc()      { c.n++ }      // меняет оригинал
func (c Counter) Value() int { return c.n }
func (c Counter) IncCopy()   { c.n++ }      // меняет копию — бесполезно

var c Counter
c.Inc()     // компилятор сам берёт адрес: (&c).Inc()
c.IncCopy()
fmt.Println(c.Value()) // 1
```

**🔧 Под капотом**

| Тип | Method set | Реализует `interface{ Inc() }`? |
|---|---|---|
| `Counter` | `Value`, `IncCopy` | нет |
| `*Counter` | `Inc`, `Value`, `IncCopy` | да |

- Вызов `c.Inc()` на переменной работает, потому что переменная **[адресуема](glossary.md#addressability)** — компилятор подставляет `&c`.
- Значение, у которого нельзя взять адрес, — элемент map, результат функции, литерал — вызвать pointer-метод не может:
  ```go
  var _ Incer = Counter{}
  // Counter does not implement Incer (method Inc has pointer receiver)
  m["a"].Inc() // cannot call pointer method Inc on Counter
  Counter{}.Inc() // cannot call pointer method Inc on Counter
  ```
- Почему у `T` нет pointer-методов в method set: в интерфейсе лежит копия значения, и менять её через указатель бессмысленно — изменения потерялись бы.

**Когда что:**
- **pointer receiver** — метод меняет состояние; структура большая; внутри `sync.Mutex` или другое, что нельзя копировать; нужна единообразность (если хоть один метод pointer — делай все pointer);
- **value receiver** — маленькие неизменяемые типы (`time.Time`), типы на основе map, func, chan, базовых типов.

**⚠️ Подвохи и версии Go**
- Смешивание receiver-ов путает: значение реализует один интерфейс, указатель — другой.
- Value receiver на большой структуре копирует её при каждом вызове.
- `for _, v := range items { v.Inc() }` меняет копию; нужно `items[i].Inc()`.

**🎤 Прямая речь**
> Value receiver работает с копией, pointer receiver — с оригиналом через указатель. Pointer беру, когда метод меняет состояние, структура большая или в ней есть мьютекс, и тогда делаю pointer все методы типа для единообразия. Value — для маленьких неизменяемых типов вроде time.Time.
>
> Method set решает, какие интерфейсы реализует тип: у значения T только методы с value receiver, у указателя *T — все. Поэтому если Inc объявлен на указателе, `Counter{}` нельзя присвоить интерфейсу с Inc, а `&Counter{}` можно. По той же причине не вызвать pointer-метод на элементе map: он неадресуем, компилятор не может взять адрес.

### 8. Функция `init`: зачем нужна, порядок вызова

**⚡ Суть**
`init` — функция без аргументов и результатов, которую рантайм вызывает автоматически при инициализации пакета: после всех переменных уровня пакета и до `main`. Таких функций может быть несколько, даже в одном файле. Вызвать `init` вручную нельзя.

```go
var a = initA() // сначала переменные пакета

func initA() int { fmt.Println("var a"); return 1 }

func init() { fmt.Println("init 1") }
func init() { fmt.Println("init 2") }

func main() { fmt.Println("main") }
// var a
// init 1
// init 2
// main
```

**🔧 Под капотом**
- Порядок: сначала полностью инициализируются импортированные пакеты (каждый один раз), затем переменные текущего пакета в порядке зависимостей, затем его `init` в порядке появления в файлах — файлы `go build` передаёт компилятору отсортированными по имени. Подробно — в [1.1 · 25](1.1-basics.md#q1-1-25).
- Всё выполняется в одной [горутине](glossary.md#goroutine), последовательно.
- `init()` из кода — ошибка `undefined: init`: идентификатор не объявляется в области видимости.

**Зачем нужна:**
- регистрация реализаций: драйверы `database/sql` (`import _ "github.com/lib/pq"`), форматы `image/png`;
- вычисление таблиц и проверка инвариантов, которые нельзя записать в объявлении переменной.

**⚠️ Подвохи и версии Go**
- Скрытые побочные эффекты: импорт пакета что-то делает сам; сложно тестировать и нельзя вернуть ошибку — только [паника](glossary.md#panic-recover).
- Подключения к БД, чтение конфига и сеть в `init` — антипаттерн: делай это явно в `main` или конструкторе.
- Полагаться на порядок `init` в разных файлах одного пакета хрупко: переименование файла меняет порядок.

**🎤 Прямая речь**
> `init` — специальная функция, которую рантайм вызывает сам при инициализации пакета: после того как проинициализированы импортированные пакеты и переменные уровня пакета, но до main. Таких функций может быть несколько даже в одном файле, а вызвать init вручную нельзя — компилятор скажет undefined.
>
> Типичное применение — регистрация: драйверы database/sql, форматы картинок. Но тяжёлую логику я в init не кладу: подключения к базе, чтение конфигов и сеть там скрыты от читателя, их сложно тестировать, и ошибку не вернуть. Такое лучше делать явно в main.

### 9. `defer`: зачем, порядок вызова, когда вычисляются аргументы

**⚡ Суть**
`defer` откладывает вызов до выхода из функции — обычного или по [панике](glossary.md#panic-recover). Нужен, чтобы освобождение ресурса стояло рядом с захватом: `mu.Lock(); defer mu.Unlock()`. Отложенные вызовы выполняются в обратном порядке (LIFO), а их аргументы вычисляются **сразу**, в момент `defer`.

```go
for i := range 3 {
	defer fmt.Print(i, " ")
}
fmt.Print("defers: ")
// defers: 2 1 0

x := 1
defer fmt.Println("arg:", x) // выведет 1: аргумент вычислен сейчас
x = 2
```

**🔧 Под капотом**
- **[Open-coded](glossary.md#open-coded-defer) defers** (Go 1.14): если в функции не больше 8 `defer`, они не в цикле и «выходов × defer» не больше 15, компилятор встраивает отложенные вызовы прямо в эпилог функции. Стоимость почти нулевая.
- `defer` в цикле так не оптимизируется: рантайм создаёт запись о defer (флаг `-gcflags=-d=defer` покажет `heap-allocated defer`). Записи берутся из пула, поэтому аллокаций нет, но вызов дороже.

Замер на Go 1.26:

| Вариант | Время |
|---|---:|
| без `defer` | ~3.6 нс |
| `defer` в теле функции (open-coded) | ~3.7 нс |
| `defer` в цикле, одна итерация | ~24 нс |

- Получатель метода тоже вычисляется сразу: `defer t.Print()` для value receiver запомнит копию `t` на момент `defer`.

**⚠️ Подвохи и версии Go**
- `defer` в цикле копит вызовы до выхода из **функции**, а не итерации: `defer f.Close()` в цикле по тысяче файлов держит их все открытыми. Выноси тело цикла в функцию.
- `os.Exit` и `log.Fatal` не выполняют отложенные вызовы.
- Ошибка из `defer f.Close()` теряется ([вопрос 11](#q1-5-11)).

**🎤 Прямая речь**
> `defer` откладывает вызов до выхода из функции, в том числе при панике. Это способ гарантированно освободить ресурс и поставить освобождение рядом с захватом: Lock и сразу defer Unlock, Open и сразу defer Close. Отложенные вызовы выполняются в обратном порядке, как [стек](glossary.md#stack-heap), а аргументы вычисляются сразу в момент defer, а не при выполнении.
>
> С Go 1.14 defer почти бесплатен: компилятор встраивает его в конец функции, если defer немного и они не в цикле. В цикле defer дороже и, главное, откладывается до конца всей функции — если открывать файлы в цикле с defer Close, они все останутся открытыми. И ещё: os.Exit отложенные вызовы не выполняет.

### 10. Захват значений переменных в `defer`; `defer` и именованный результат

**⚡ Суть**
`defer f(x)` запоминает значение `x` сразу, а `defer func() { … x … }()` — замыкание, оно прочитает `x` в момент выполнения. Отложенная функция выполняется **после** того, как `return` записал результат, поэтому с именованным результатом она может его изменить.

```go
x := 1
defer fmt.Println("arg:", x)                  // arg: 1
defer func() { fmt.Println("closure:", x) }() // closure: 2
x = 2
// порядок вывода: closure: 2, затем arg: 1 (LIFO)

func named() (n int) {
	defer func() { n *= 2 }()
	return 21
}

func unnamed() int {
	n := 21
	defer func() { n *= 2 }()
	return n
}

fmt.Println(named(), unnamed()) // 42 21
```

**🔧 Под капотом**
- `return 21` в функции с именованным результатом — это «`n = 21`, потом выполнить defer, потом выйти». Defer видит и меняет `n`.
- В `unnamed` `return n` копирует значение `n` в безымянный слот результата; defer меняет локальную `n`, а результат уже записан.

**Где полезно:** обогатить или заменить ошибку на выходе, превратить [панику](glossary.md#panic-recover) в ошибку через `recover`:
```go
func returnPtr() (err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("returnPtr: %w", err)
		}
	}()
	return errors.New("boom")
}
// returnPtr: boom
```

**⚠️ Подвохи и версии Go**
- Затенение: внутри `if err := do(); err != nil { return }` голый `return` не скомпилируется — `result parameter err not in scope at return`. С явным `return err` код собирается, но затенённые переменные легко запутать в логике defer.
- Именованные результаты делают код менее явным; используй их, когда они нужны defer или документируют смысл значений.

**🎤 Прямая речь**
> Есть два способа передать значение в defer. Аргумент — `defer fmt.Println(x)` — вычисляется сразу, и потом изменения x не видны. Замыкание — `defer func() { … x … }()` — читает переменную в момент выполнения и видит последнее значение.
>
> С результатом работает так: return сначала записывает значение в результат, потом выполняются отложенные функции. Если результат именованный, defer может его поменять — так из функции с `return 21` можно вернуть 42. На этом построены оборачивание ошибки на выходе и превращение паники в ошибку через recover. С безымянным результатом изменения в defer до вызывающего не дойдут.

<a id="q1-5-11"></a>
### 11. Как вернуть ошибку изнутри `defer` (не просто залогировать)?

**⚡ Суть**
Через именованный результат: отложенная функция присваивает ему ошибку. Чтобы не потерять ни основную ошибку, ни ошибку закрытия, их объединяют `errors.Join` (Go 1.20).

```go
// Плохо: ошибка Close теряется
func saveBad(data []byte) error {
	f, err := open()
	if err != nil {
		return err
	}
	defer f.Close()
	return f.Write(data)
}

// Хорошо: именованный результат + errors.Join
func save(data []byte) (err error) {
	f, err := open()
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, f.Close())
	}()
	return f.Write(data)
}

// Close возвращает errDiskFull:
// saveBad: <nil>
// save: disk full, errors.Is(err, errDiskFull) == true
```

**🔧 Под капотом**
- `errors.Join(nil, nil)` возвращает `nil`, поэтому успешный путь остаётся успешным.
- Объединённая ошибка поддерживает `errors.Is` и `errors.As` для каждой части.

**⚠️ Подвохи и версии Go**
- Для файлов на запись ошибка `Close` важна: данные могли не записаться (буферы, сетевые ФС). Для файлов на чтение её обычно можно игнорировать.
- Альтернатива без Join — менять `err`, только если он ещё `nil`: `if cerr := f.Close(); cerr != nil && err == nil { err = cerr }`.
- Подробнее про ошибку `Close` и `Sync` для файлов на запись — [1.7 · 11](1.7-errors.md#q1-7-11).
- Нельзя `defer f.Close()` до проверки ошибки `Open`: при ошибке `f == nil`.

**🎤 Прямая речь**
> Вернуть ошибку из defer можно только через именованный результат: отложенная функция присваивает ему значение после return. Типичный случай — Close у файла на запись: если просто написать `defer f.Close()`, ошибка закрытия потеряется, а она может означать, что данные не дошли до диска.
>
> Я делаю результат `err error` именованным и в defer пишу `err = errors.Join(err, f.Close())`. Join возвращает nil, если обе ошибки nil, и сохраняет обе, если упали обе, а errors.Is и As работают по каждой части.

### 12. ⭐ Функциональные опции (functional options)

**⚡ Суть**
Паттерн для конструктора с множеством необязательных параметров: опция — функция, которая настраивает объект, конструктор принимает их вариативно и применяет поверх значений по умолчанию.

```go
type Server struct {
	addr    string
	timeout time.Duration
	maxConn int
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option         { return func(s *Server) { s.maxConn = n } }

func NewServer(addr string, opts ...Option) *Server {
	s := &Server{addr: addr, timeout: 30 * time.Second, maxConn: 100} // значения по умолчанию
	for _, opt := range opts {
		opt(s)
	}
	return s
}

s1 := NewServer(":8080")
s2 := NewServer(":8080", WithTimeout(5*time.Second), WithMaxConn(10))
fmt.Println(s1.timeout, s1.maxConn, s2.timeout, s2.maxConn) // 30s 100 5s 10
```

**🔧 Под капотом**
- Каждая `WithX` возвращает замыкание, которое захватило значение параметра.
- Опции применяются по порядку, поэтому более поздняя перекрывает раннюю.

**Плюсы и минусы**
- ✅ Новые параметры добавляются без изменения сигнатуры — API обратно совместим.
- ✅ Разумные значения по умолчанию, вызов читается: `NewServer(addr, WithTimeout(…))`.
- ❌ Больше кода, чем у структуры конфигурации; список опций неочевиден без документации.
- ❌ Для валидации нужна версия с ошибкой: `type Option func(*Server) error`.

**⚠️ Подвохи и версии Go**
- Альтернативы: структура `Config` (проще, но нулевое значение неотличимо от «не задано») и builder. Для 2–3 параметров опции избыточны.
- Паттерн широко используется: `grpc.Dial(addr, grpc.WithTransportCredentials(…))`, `zap.New(core, zap.AddCaller())`.

**🎤 Прямая речь**
> Функциональные опции — способ сделать конструктор с кучей необязательных параметров. Опция — это функция, которая принимает указатель на объект и что-то в нём настраивает. Конструктор выставляет значения по умолчанию, принимает опции вариативно и применяет их по очереди. Вызов выглядит как `NewServer(addr, WithTimeout(5*time.Second))`.
>
> Главный плюс — API можно расширять, не ломая сигнатуру, и пользователь задаёт только то, что ему нужно. Минус — больше кода, чем у простой структуры конфигурации, поэтому для двух-трёх параметров я беру Config. Если опции надо валидировать, делаю вариант, где опция возвращает ошибку.

### 13. Напиши `swap(&x, &y)`

**⚡ Суть**
Функция принимает указатели и меняет значения через разыменование, используя множественное присваивание Go:

```go
func swap(a, b *int) {
	*a, *b = *b, *a
}

x, y := 1, 2
swap(&x, &y)
fmt.Println(x, y) // 2 1
```

**🔧 Под капотом**
- Множественное присваивание выполняется в два этапа: сначала вычисляются все правые части и адреса слева, потом идёт запись. Поэтому временная переменная не нужна.
- Без указателей не работает — функция получит копии:
  ```go
  bad := func(a, b int) { a, b = b, a }
  bad(x, y) // x и y не изменились
  ```

**Варианты:**
```go
x, y = y, x                    // без функции — идиоматичный способ
a[0], a[2] = a[2], a[0]        // элементы слайса

func swapGeneric[T any](a, b *T) { *a, *b = *b, *a } // для любого типа
```

**⚠️ Подвохи и версии Go**
- XOR-трюк `*a ^= *b; *b ^= *a; *a ^= *b` ломается, если оба указателя на одну переменную: `xorSwap(&x, &x)` даёт `0`. Обычный `*a, *b = *b, *a` с одним адресом работает корректно.
- В Go функция swap почти не нужна: `x, y = y, x` короче и понятнее.

**🎤 Прямая речь**
> Функция принимает два указателя и делает `*a, *b = *b, *a`. Временная переменная не нужна, потому что в множественном присваивании сначала вычисляются все правые части, а потом идёт запись. Указатели обязательны: Go передаёт аргументы по значению, и без них функция поменяла бы местами свои копии.
>
> На практике отдельная функция редко нужна — достаточно `x, y = y, x`. Если надо для любого типа — пишу дженерик-версию с параметром `T any`. А XOR-трюк не использую: он обнуляет значение, если оба указателя смотрят на одну переменную.
