### 1. Что такое структура, зачем? Теги структур

**⚡ Суть**
Структура — составной тип из именованных полей разных типов: так группируют данные, которые описывают одну сущность. Структура — значение: присваивание и передача в функцию копируют все поля. Теги — строки-метаданные у полей, их читают библиотеки через [рефлексию](glossary.md#reflection): `encoding/json`, ORM, валидаторы.

```go
type User struct {
	ID    int    `json:"id" db:"user_id"`
	Name  string `json:"name,omitempty"`
	Email string `json:"-"`
}

f, _ := reflect.TypeFor[User]().FieldByName("ID")
fmt.Println(f.Tag.Get("json"), f.Tag.Get("db")) // id user_id
v, ok := f.Tag.Lookup("xml")
fmt.Printf("%q %v\n", v, ok)                    // "" false
```

**🔧 Под капотом**
- Поля лежат в памяти подряд в порядке объявления, с [выравниванием](glossary.md#alignment) ([вопрос 5](#q1-6-05)). Заголовка и скрытого указателя на класс, как в Java, нет: `struct{ X, Y int }` занимает ровно 16 байт.
- Тег — часть типа: он хранится в [дескрипторе](glossary.md#type-descriptor) типа, и две структуры с разными тегами — разные типы (но конвертируются друг в друга явно).
- Формат тега по соглашению — `ключ:"значение"` через пробел. `Tag.Get` возвращает пустую строку и для отсутствующего ключа, и для пустого значения, а `Tag.Lookup` (Go 1.7) различает эти случаи.

**⚠️ Подвохи и версии Go**
- Опечатка в теге (`json: "id"` с пробелом) молча ломает разбор. Её ловит `go vet` (анализатор `structtag`).
- Теги видны только через рефлексию — компилятор их не проверяет и не использует.
- `reflect.TypeFor[T]()` — с Go 1.22, раньше писали `reflect.TypeOf(T{})`.

**🎤 Прямая речь**
> Структура — это составной тип, набор именованных полей, которыми описывают одну сущность: пользователя, заказ, конфиг. В Go структура — значение, без скрытых заголовков, поля лежат в памяти подряд. При присваивании и передаче в функцию она копируется целиком, поэтому большие структуры обычно передают по указателю.
>
> Теги — это строки-метаданные у полей, вида `json:"id" db:"user_id"`. Компилятор их не трогает, их читают библиотеки через рефлексию: `encoding/json`, драйверы БД, валидаторы. Опечатки в тегах ловит `go vet`.

### 2. Можно ли сравнивать структуры? Пустая структура `struct{}` — зачем?

**⚡ Суть**
Структуры сравниваются через `==`, если сравнимы все их поля: тогда они равны, когда равны все поля. Структуру со слайсом, map или функцией сравнить нельзя — ошибка компиляции. `struct{}` занимает 0 байт: его используют как «значение без данных» — в множествах и сигнальных каналах.

```go
type P struct{ X, Y int }
fmt.Println(P{1, 2} == P{1, 2})   // true
m := map[P]string{{1, 2}: "ok"}   // сравнимая структура годится в ключ map

type WithSlice struct{ S []int }
_ = WithSlice{} == WithSlice{}
// invalid operation: WithSlice{} == WithSlice{} (struct containing []int cannot be compared)
```

**🔧 Под капотом**
- Компилятор сравнивает поля по очереди или, если в структуре нет «дыр» и float-полей, одним сравнением памяти.
- `unsafe.Sizeof(struct{}{})`, `[0]int{}` и даже `[100]struct{}{}` — 0 байт.

**⚠️ Подвохи и версии Go**
- Поле-интерфейс компилятор пропускает, а проверка уходит в рантайм:
  ```go
  type Box struct{ V any }
  fmt.Println(Box{1} == Box{1})                 // true
  fmt.Println(Box{[]int{1}} == Box{[]int{1}})   // panic: runtime error: comparing uncomparable type []int
  ```
- Структуры со слайсами сравнивают вручную (`slices.Equal`) или `reflect.DeepEqual` — последний медленный, им пользуются в тестах.
- Структуры разных именованных типов с одинаковыми полями напрямую сравнить нельзя, только после конверсии: `A{1} == A(B{1})`.
- Применение `struct{}`:
  - множество: `map[string]struct{}`;
  - сигнал в канале: `chan struct{}` ([вопрос 3](#q1-6-03));
  - тип-маркер без состояния, у которого есть только методы.

**🎤 Прямая речь**
> Структуры можно сравнивать через `==`, если сравнимы все их поля: числа, строки, указатели, массивы, вложенные сравнимые структуры. Тогда структура подходит и как ключ map. Если внутри есть слайс, map или функция — это ошибка компиляции. Отдельный случай — поле-интерфейс: компилятор разрешит сравнение, но если внутри окажется слайс, будет [паника](glossary.md#panic-recover) в рантайме.
>
> Пустая структура занимает ноль байт. Её используют как значение, которое ничего не несёт: в множестве `map[string]struct{}` и в каналах-сигналах `chan struct{}`, где важен сам факт события, а не данные.

### 3. Чем пустой интерфейс отличается от пустой структуры? Почему в канал-сигнал передают `struct{}`, а не `interface{}`?

**⚡ Суть**
`interface{}` (`any`) — контейнер, который может хранить значение любого типа: 16 байт, указатель на тип и указатель на данные. `struct{}` — тип без данных, 0 байт. В канал-сигнал кладут `struct{}`: это ничего не стоит по памяти и сразу говорит читателю кода, что важен только факт события.

**🔧 Под капотом**
- Буфер канала — массив элементов. Замер на Go 1.26, `make(chan T, 1000)`:

| Тип элемента | Аллоцировано |
|---|---:|
| `struct{}` | ~112 байт (только структура канала) |
| `bool` | ~1.1 КБ |
| `any` | ~16.5 КБ |

- Класть в `chan any` значение — ещё и упаковка в интерфейс, которая может аллоцировать ([вопрос 19](#q1-6-19)).

**⚠️ Подвохи и версии Go**
- Для сигнала «всем сразу» канал не пишут, а закрывают: `close(done)` будит всех читателей. Так устроен `ctx.Done()` — он возвращает `<-chan struct{}`.
- `chan bool` для сигналов тоже работает, но вызывает вопрос «а что значит false?».

**🎤 Прямая речь**
> Пустой интерфейс — это контейнер для значения любого типа, 16 байт: указатель на тип и указатель на данные. Пустая структура — тип, у которого нет данных вообще, ноль байт. Это противоположные вещи: один может хранить что угодно, другой не хранит ничего.
>
> Поэтому в канал-сигнал передают `struct{}`: буфер такого канала не занимает памяти, нет упаковки в интерфейс, и тип сам говорит, что важен только факт события. Так сделан `ctx.Done()`, а сигнал для всех подписчиков отправляют закрытием канала.

### 4. ⭐ Почему два `new(struct{})` могут иметь одинаковый адрес?

**⚡ Суть**
Объектам нулевого размера не нужна своя память, поэтому аллокатор возвращает для всех них один и тот же адрес — глобальную переменную `runtime.zerobase`. Спецификация прямо разрешает это: указатели на разные переменные нулевого размера «могут быть равны, а могут и не быть».

**🔧 Под капотом**
- [`mallocgc`](glossary.md#allocator) для размера 0 сразу возвращает `&zerobase` (`runtime/malloc.go`).
- Если объект не убегает в [кучу](glossary.md#stack-heap), компилятор кладёт его на стек и может вообще не сравнивать адреса, а сразу подставить результат.

```go
a, b := new(struct{}), new(struct{})
fmt.Printf("%p %p\n", a, b) // одинаковые адреса: %p заставляет убежать в кучу → zerobase
fmt.Println(a == b)         // true

c, d := new(struct{}), new(struct{})
println(c, d)               // 0xe68fcb1af17 0xe68fcb1af17 — адреса совпадают
fmt.Println(c == d)         // false — компилятор подставил результат сравнения
```

**⚠️ Подвохи и версии Go**
- Результат зависит от [escape analysis](glossary.md#escape-analysis) и версии компилятора — полагаться на равенство или неравенство таких указателей нельзя.
- Поле нулевого размера в конце структуры добавляет байты: `struct{ A int64; B struct{} }` — 16 байт, а с пустым полем в начале — 8. Иначе указатель на последнее поле указывал бы за пределы объекта, на чужую память.

**🎤 Прямая речь**
> Объекту нулевого размера память не нужна, поэтому рантайм не выделяет её, а возвращает адрес одной глобальной переменной — [`zerobase`](glossary.md#zerobase). Отсюда два `new(struct{})` могут дать одинаковый адрес. Спецификация это прямо разрешает: указатели на разные переменные нулевого размера могут быть равны, а могут и не быть.
>
> На практике результат зависит от escape analysis: если объекты ушли в кучу, сравнение даёт true, а если остались на стеке, компилятор может сразу подставить false, хотя `println` печатает одинаковые адреса. Поэтому на сравнение таких указателей нельзя опираться.

### 5. Выравнивание полей (alignment/padding), размер структуры

**⚡ Суть**
Каждый тип выравнивается по своему размеру (максимум по машинному слову): `int64` — по 8, `int32` — по 4, `bool` — по 1. Компилятор вставляет между полями пустые байты ([padding](glossary.md#alignment)), чтобы каждое поле стояло по своему выравниванию, а размер структуры округляет до выравнивания самого «строгого» поля. Поэтому порядок полей меняет размер.

```go
type Bad struct {  // 24 байта
	A bool  // 0, затем 7 байт padding
	B int64 // 8
	C bool  // 16, затем 7 байт padding
}
type Good struct { // 16 байт
	B int64
	A bool
	C bool
}

type Mixed struct { // 32 байта, смещения полей: 0 4 8 16 24
	A int8; B int32; C int8; D int64; E int16
}
type Sorted struct { // 16 байт: те же поля, от больших к маленьким
	D int64; B int32; E int16; A int8; C int8
}
```

**🔧 Под капотом**
- Процессор читает память словами; невыровненное чтение на одних архитектурах медленнее, на других вообще не работает.
- Проверить: `unsafe.Sizeof`, `unsafe.Alignof`, `unsafe.Offsetof`.
- Правило: поля от больших к маленьким — минимум padding.
- Найти «дырявые» структуры автоматически — анализатор `fieldalignment` из `golang.org/x/tools`; в обычный `go vet` он не входит.

**⚠️ Подвохи и версии Go**
- Экономия заметна, когда структур миллионы — в слайсах и кэшах. Для одной структуры порядок полей лучше выбирать по смыслу.
- На 32-битных платформах `int64` в структуре выровнен только по 4, поэтому 64-битные атомики раньше требовали ставить поле первым. С Go 1.19 есть `atomic.Int64`, который выравнивается сам.
- Подробнее про размеры базовых типов — в [1.1 · 5](1.1-basics.md#q1-1-05) и [1.4 · 15](1.4-maps.md#q1-4-15).

**🎤 Прямая речь**
> Каждое поле выравнивается по своему размеру: `int64` по 8 байт, `int32` по 4, `bool` по 1. Компилятор вставляет между полями пустые байты, чтобы поле стояло по выровненному адресу, и округляет размер всей структуры. Поэтому структура из bool, int64 и bool занимает 24 байта, а если поставить int64 первым — 16.
>
> Правило простое: поля от больших к маленьким. Проверяю через `unsafe.Sizeof` и `Offsetof`, а искать такие места можно линтером `fieldalignment`. Но оптимизирую это, только когда структур миллионы, — в остальных случаях порядок по смыслу важнее.

### 6. Что такое указатели? Когда их использовать?

**⚡ Суть**
Указатель `*T` хранит адрес значения типа `T`: `&x` берёт адрес, `*p` читает значение по адресу. Указатель нужен, чтобы функция могла изменить оригинал, чтобы не копировать большую структуру и чтобы выразить «значения может не быть» (nil). Арифметики указателей, как в C, нет.

```go
type Point struct{ X, Y int }

func move(p *Point)    { p.X++ } // меняет оригинал
func moveCopy(p Point) { p.X++ } // меняет копию

pt := Point{}
move(&pt)
moveCopy(pt)
fmt.Println(pt) // {1 0}
```

**🔧 Под капотом**
- Указатель — машинное слово, 8 байт на 64-битной платформе.
- `p.X` — автоматическое разыменование, то же самое, что `(*p).X`.
- Вернуть указатель на локальную переменную безопасно: [escape analysis](glossary.md#escape-analysis) увидит это и разместит переменную в [куче](glossary.md#stack-heap) (`&Point{...} escapes to heap` в выводе `-gcflags=-m`).
- `p++` — ошибка компиляции `invalid operation: p++ (non-numeric type *int)`. Арифметика возможна только через `unsafe`: `unsafe.Add(p, 8)` (Go 1.17) — и тогда гарантии безопасности на тебе.

**⚠️ Подвохи и версии Go**
- Указатель — не всегда быстрее: объект может уйти в кучу, а это аллокация и работа для [GC](glossary.md#gc). Маленькие структуры дешевле передавать по значению.
- Разыменование nil-указателя — [паника](glossary.md#panic-recover) `invalid memory address or nil pointer dereference`.
- Когда использовать:
  - функция или метод должны изменить значение;
  - большая структура (сотни байт и больше) или структура с `sync.Mutex` ([вопрос 18](#q1-6-18));
  - нужно отличить «нет значения» от нулевого (`*int` в JSON-модели).
- Слайсы, map, каналы уже содержат указатель внутри — указатель на них обычно не нужен.

**🎤 Прямая речь**
> Указатель хранит адрес значения: через амперсанд берём адрес, через звёздочку читаем значение. В Go всё передаётся по значению, поэтому указатель нужен, когда функция должна изменить оригинал, когда структура большая и копировать её дорого, и когда нужно выразить отсутствие значения через nil. Арифметики указателей нет — только через пакет `unsafe`.
>
> Возвращать указатель на локальную переменную безопасно: компилятор через escape analysis перенесёт её в кучу. Но поэтому указатели не бесплатны — лишние аллокации нагружают GC. Маленькие структуры я передаю по значению, а слайсы и map и так содержат указатель внутри.

### 7. Что такое интерфейс? Утиная типизация; чем отличается от интерфейсов в Java/PHP?

**⚡ Суть**
Интерфейс — тип, который описывает набор методов. Любой тип, у которого есть эти методы, реализует интерфейс автоматически, без слова `implements`. Это структурная типизация, проверяемая компилятором, — «утиная типизация» на этапе компиляции. В Java и PHP реализация номинальная: класс должен явно объявить `implements`.

```go
type Writer struct{}

func (Writer) Write(p []byte) (int, error) { return len(p), nil }

var _ io.Writer = Writer{} // Writer реализует io.Writer, хотя нигде об этом не сказано
```

**🔧 Под капотом**
- Значение интерфейсного типа хранит пару: конкретный тип и данные ([вопрос 9](#q1-6-09)).
- Вызов метода через интерфейс — косвенный вызов через таблицу методов. Компилятор не может его встроить (inline), если не догадается о конкретном типе ([девиртуализация](glossary.md#devirtualization), в том числе через PGO).

**⚠️ Подвохи и версии Go**
- Тип может реализовать интерфейс из пакета, о котором он не знает, — например, свой тип легко подходит под `io.Reader`. В Java для этого нужен адаптер.
- В Go интерфейсы маленькие: `io.Reader`, `io.Writer`, `fmt.Stringer` — по одному методу. Пословица Go: «чем больше интерфейс, тем слабее абстракция».
- Интерфейс с дженерик-ограничениями (`~int | ~string`) — отдельная история, он годится только как ограничение типа (блок 1.8).

**🎤 Прямая речь**
> Интерфейс в Go — это набор методов. Тип реализует интерфейс автоматически, если у него есть все эти методы, — никакого `implements`. По сути это утиная типизация, только проверяемая компилятором: если ходит как утка — значит, утка, но проверка во время компиляции, а не в рантайме.
>
> Отличие от Java и PHP в том, что там связь номинальная: класс сам объявляет, какие интерфейсы реализует, и автор класса должен о них знать. В Go интерфейс может появиться позже реализации и в другом пакете, поэтому интерфейсы маленькие и объявляются там, где их используют.

### 8. Неявная реализация интерфейсов — плюсы и минусы. Как заставить компилятор проверить, что тип реализует интерфейс?

**⚡ Суть**
Плюсы: пакеты не зависят друг от друга, интерфейс можно объявить у потребителя, легко подменять реализацию в тестах. Минусы: из кода типа не видно, какие интерфейсы он реализует, и тип может «перестать» реализовывать интерфейс после переименования метода. Проверка на этапе компиляции — пустое объявление:

```go
var _ Shape = (*Square)(nil) // если *Square не реализует Shape — ошибка компиляции
```

**🔧 Под капотом**
- `(*Square)(nil)` — типизированный nil-указатель: память не выделяется, переменная `_` не попадает в бинарник, работает только проверка типов.
- Ошибка компиляции подробно объясняет, чего не хватает:
  ```
  cannot use (*Missing)(nil) (value of type *Missing) as interface{Foo()} value in variable declaration: *Missing does not implement interface{Foo()} (missing method Foo)
  ```
- Частая причина — метод с pointer receiver, а проверяется значение:
  ```
  cannot use Square{} (value of struct type Square) as Shape value in variable declaration: Square does not implement Shape (method Area has pointer receiver)
  ```

**⚠️ Подвохи и версии Go**
- Без такой проверки ошибка всплывёт там, где тип впервые передадут как интерфейс, — возможно, в другом пакете.
- Проверку ставят рядом с типом, когда реализация интерфейса — часть контракта (например, `http.Handler`, `sql.Scanner`).
- Метод с pointer receiver входит в [method set](glossary.md#method-set) только у `*T`, поэтому `T` такой интерфейс не реализует.

**🎤 Прямая речь**
> Плюс неявной реализации — слабая связанность: пакету с реализацией не нужно импортировать пакет с интерфейсом, а потребитель объявляет ровно тот интерфейс, который ему нужен. Это сильно упрощает тесты и моки. Минус — из кода типа не видно, какие интерфейсы он реализует, и переименование метода может незаметно сломать реализацию.
>
> Поэтому, когда реализация интерфейса — часть контракта, я ставлю проверку `var _ Shape = (*Square)(nil)`. Она ничего не стоит в рантайме, а при расхождении компилятор скажет, какого метода не хватает или что метод объявлен на указателе.

### 9. Интерфейс как структура: `iface`, `eface`, `itab`

**⚡ Суть**
Интерфейсное значение — два машинных слова, 16 байт. Пустой интерфейс (`any`) — [`eface`](glossary.md#interface-layout): указатель на тип и указатель на данные. Непустой интерфейс — `iface`: указатель на `itab` и указатель на данные. `itab` — таблица для пары «интерфейс + конкретный тип»: в ней тип и адреса методов для динамического вызова.

```go
// runtime/runtime2.go
type eface struct {
	_type *_type
	data  unsafe.Pointer
}
type iface struct {
	tab  *itab
	data unsafe.Pointer
}

// internal/abi/iface.go
type ITab struct {
	Inter *InterfaceType
	Type  *Type
	Hash  uint32     // копия хеша типа, для type switch
	Fun   [1]uintptr // переменной длины; Fun[0] == 0 — тип не реализует интерфейс
}
```

**🔧 Под капотом**
- **Вызов метода** `r.Read(p)` = загрузить `tab.Fun[i]` и вызвать его, передав `data` как получатель. Методы в `Fun` отсортированы по имени.
- **Откуда берутся `itab`:**
  - для преобразований, известных при компиляции, компилятор генерирует `itab` заранее, а при старте рантайм складывает их в глобальную хеш-таблицу `itabTable`;
  - для динамических случаев (assertion из `any` к интерфейсу) рантайм строит `itab` в `getitab` и кэширует в той же таблице — вычисление происходит один раз для пары типов. Отрицательный результат тоже кэшируется (`Fun[0] == 0`).
  - у каждого места с type switch или assertion к интерфейсу есть ещё и свой маленький кэш.
- **`data`** — указатель на значение. Если значение само указатель (указатель, map, канал, функция), оно лежит прямо в `data` без копии.

**⚠️ Подвохи и версии Go**
- Интерфейс равен nil, только если оба слова нулевые ([вопрос 11](#q1-6-11)).
- Упаковка значения в интерфейс может аллоцировать ([вопрос 19](#q1-6-19)).

**🎤 Прямая речь**
> Интерфейсное значение — это два указателя. У пустого интерфейса, `eface`, первое слово указывает на [дескриптор](glossary.md#type-descriptor) типа, второе — на данные. У непустого, `iface`, первое слово указывает на `itab`: это таблица для пары «интерфейс и конкретный тип», где лежит тип и массив адресов методов. Вызов метода через интерфейс — это взять адрес из `itab` и вызвать его с указателем на данные.
>
> `itab` для преобразований, которые видны при компиляции, генерирует компилятор, а для динамических — рантайм строит один раз и кэширует в глобальной хеш-таблице. Поэтому повторные assertion к интерфейсу дешёвые. И из этой структуры следует классика про typed nil: интерфейс равен nil, только если пусты оба слова.

### 10. Пустой интерфейс, `any` — когда использовать?

**⚡ Суть**
`any` — алиас `interface{}` (с Go 1.18): тип, которому подходит любое значение. Использовать, когда тип действительно неизвестен на этапе компиляции: форматирование (`fmt.Println`), JSON с произвольной структурой, контейнеры в старом коде. В остальных случаях лучше конкретный тип, маленький интерфейс или дженерики.

**🔧 Под капотом**
- `any` — [`eface`](glossary.md#interface-layout): тип + данные. Чтобы что-то сделать со значением, нужно достать тип обратно — type assertion, type switch или [рефлексия](glossary.md#reflection).
- Упаковка в `any` может аллоцировать, а извлечение стоит проверки типа в рантайме.

**⚠️ Подвохи и версии Go**
- `any` отключает проверку типов: ошибка, которую поймал бы компилятор, становится [паникой](glossary.md#panic-recover) в рантайме.
- До Go 1.18 контейнеры писали на `interface{}` (`container/list`, `sync.Map`). Новый код — на дженериках: `func Max[T cmp.Ordered](a, b T) T`.
- `map[string]any` для JSON удобен для чтения неизвестной структуры, но для известной лучше структура с тегами — быстрее и проверяется компилятором.

**🎤 Прямая речь**
> `any` — это просто другое имя для `interface{}`, тип, которому подходит что угодно. Я использую его, только когда тип правда неизвестен при компиляции: форматирование и логирование, разбор JSON произвольной формы, рефлексия.
>
> Во всех остальных случаях беру конкретный тип, маленький интерфейс или дженерики: `any` выключает проверку типов, ошибки переезжают из компиляции в рантайм, а каждая упаковка может стоить аллокации. Типобезопасные контейнеры с Go 1.18 пишутся на дженериках.

### 11. nil-интерфейс ≠ интерфейс с nil-значением. Как вызов метода на интерфейсе, не равном nil, может упасть с nil pointer dereference?

**⚡ Суть**
Интерфейс равен nil, только когда в нём нет ни типа, ни значения. Если положить в интерфейс nil-указатель конкретного типа, тип в интерфейсе есть — и интерфейс уже не nil. Вызов метода пройдёт, а если метод обращается к полям получателя — будет nil pointer dereference.

```go
type MyErr struct{ Msg string }

func (e *MyErr) Error() string { return e.Msg }

func find(ok bool) error {
	var p *MyErr
	if !ok {
		p = &MyErr{"not found"}
	}
	return p // всегда не nil!
}

err := find(true)
fmt.Println(err == nil, err)       // false <nil>
fmt.Printf("%T\n", err)            // *main.MyErr

var s Shape = (*Sq)(nil)
fmt.Println(s == nil)              // false
s.Area() // panic: runtime error: invalid memory address or nil pointer dereference
```

**🔧 Под капотом**
- `return p` упаковывает `*MyErr` в `error`: первое слово — `itab` для `*MyErr`, второе — nil. Сравнение с nil проверяет оба слова.
- `fmt` печатает `<nil>`, потому что сам перехватывает [панику](glossary.md#panic-recover) при вызове `Error()` на nil-указателе. Поэтому в логах ошибка выглядит как `<nil>`, хотя `err != nil`.
- Метод на nil-получателе — законный вызов: если метод не трогает поля, он отработает.
  ```go
  func (n *Named) Hello() string {
  	if n == nil {
  		return "hello, nil"
  	}
  	return "hello, " + n.Name
  }
  ```

**⚠️ Подвохи и версии Go**
- Правило: функция, возвращающая `error`, на успехе пишет `return nil`, а не возвращает переменную конкретного типа.
- Проверить «внутри nil» можно через [рефлексию](glossary.md#reflection): `reflect.ValueOf(err).IsNil()` ([вопрос 12](#q1-6-12)) — но это признак проблемы в дизайне.

**🎤 Прямая речь**
> Интерфейс — это пара «тип и значение», и он равен nil, только если пусты обе части. Классическая ошибка: функция возвращает `error`, а внутри возвращает переменную типа `*MyErr`, равную nil. В интерфейс попадает тип `*MyErr` и nil-значение, поэтому `err != nil`, и вызывающий код считает, что произошла ошибка.
>
> Вызов метода на таком интерфейсе проходит, потому что тип известен, а получатель — nil-указатель. Если метод обращается к полям — паника nil pointer dereference. Поэтому функции с `error` на успехе всегда возвращают литерал `nil`, а не типизированную переменную.

### 12. Почему говорят, что у nil в Go есть тип? Как получить переменную, которая «не nil, но nil»?

**⚡ Суть**
Сам `nil` — предопределённый идентификатор без типа: он становится nil-значением того типа, куда его присваивают. Но любое nil-значение уже типизировано: nil-указатель `*int`, nil-слайс, nil-map, nil-интерфейс. Поэтому `x := nil` не компилируется, а nil-указатель внутри интерфейса делает интерфейс «не nil, но nil».

```go
x := nil // use of untyped nil in assignment

var p *int
var i any = p
fmt.Printf("%T %v\n", i, i == nil)        // *int false — «не nil, но nil»
fmt.Println(reflect.ValueOf(i).IsNil())   // true
fmt.Printf("%T\n", any(nil))              // <nil> — настоящий nil-интерфейс
```

**🔧 Под капотом**
- nil-указатель, nil-слайс, nil-map, nil-канал и nil-функция — нулевые значения своих типов. У каждого своё поведение: из nil-map можно читать, в nil-слайс можно делать `append`, nil-канал блокирует навсегда.
- nil-интерфейс — единственный nil «без типа внутри»: оба слова интерфейса нулевые.
- Проверка «nil внутри интерфейса» через [рефлексию](glossary.md#reflection):
  ```go
  func isNil(v any) bool {
  	if v == nil {
  		return true
  	}
  	rv := reflect.ValueOf(v)
  	switch rv.Kind() {
  	case reflect.Pointer, reflect.Map, reflect.Slice, reflect.Chan, reflect.Func, reflect.Interface:
  		return rv.IsNil()
  	}
  	return false
  }
  ```

**⚠️ Подвохи и версии Go**
- `rv.IsNil()` [паникует](glossary.md#panic-recover) для типов, которые не могут быть nil (например, `int`), поэтому сначала проверяют `Kind`.
- Нужда в `isNil` — обычно симптом: правильнее не класть типизированный nil в интерфейс.

**🎤 Прямая речь**
> Сам `nil` не имеет типа — поэтому `x := nil` не компилируется: компилятор не знает, какой тип вывести. Но любое nil-значение типизировано: nil-указатель на int, nil-слайс, nil-map — разные значения разных типов со своим поведением.
>
> «Не nil, но nil» получается, когда nil-указатель кладут в интерфейс: внутри появляется тип, и сравнение с nil даёт false. Проверить, что внутри nil, можно рефлексией через `IsNil`, но я считаю это запахом — лучше не допускать типизированный nil в интерфейсе.

### 13. Сравнение интерфейсов

**⚡ Суть**
Два интерфейсных значения равны, если у них одинаковый динамический тип и равные значения, или оба nil. Если типы разные — false. Если типы одинаковые, но несравнимые (слайс, map, функция) — [паника](glossary.md#panic-recover) в рантайме.

```go
var a, b any = 1, 1
fmt.Println(a == b)         // true
var c, d any = 1, int64(1)
fmt.Println(c == d)         // false: разные динамические типы

var e1, e2 error = &MyErr{"x"}, &MyErr{"x"}
fmt.Println(e1 == e2)       // false: сравниваются указатели
fmt.Println(errors.New("x") == errors.New("x")) // false

var x, y any = []int{1}, []int{1}
fmt.Println(x == y)         // panic: runtime error: comparing uncomparable type []int

var m, n any = map[string]int{}, 1
fmt.Println(m == n)         // false: типы разные — до сравнения значений не дошло

var i any = 42
fmt.Println(i == 42)        // true: 42 упаковывается в any типа int
```

**🔧 Под капотом**
- Рантайм сначала сравнивает первые слова (тип или `itab`), затем вызывает функцию равенства для этого типа. У несравнимых типов её нет — отсюда паника.
- Указатели сравниваются по адресу: две разные ошибки с одинаковым текстом не равны. Поэтому sentinel-ошибки (`io.EOF`) — одна переменная, с которой сравнивают.

**⚠️ Подвохи и версии Go**
- Интерфейс как ключ map — та же проверка: несравнимый тип внутри даёт панику `hash of unhashable type` ([1.4 · 10](1.4-maps.md#q1-4-10)).
- Ошибки сравнивают через `errors.Is`, а не `==`, чтобы учитывать обёртки (блок 1.7).

**🎤 Прямая речь**
> Интерфейсы равны, если совпадают динамические типы и значения, или оба nil. Если типы разные — сразу false: `1` и `int64(1)` в `any` не равны. Если тип одинаковый, но несравнимый — слайс или map, — будет паника в рантайме, компилятор это не ловит.
>
> Ещё важно, что указатели сравниваются по адресу: две ошибки с одинаковым текстом, созданные отдельно, не равны. Поэтому sentinel-ошибки — это одна переменная, а ошибки в целом я сравниваю через `errors.Is`, чтобы учесть обёртки.

### 14. Type assertion и `switch v := x.(type)`: способы применения

**⚡ Суть**
Type assertion `x.(T)` достаёт из интерфейса значение конкретного типа или проверяет, реализует ли значение другой интерфейс. Форма с одним результатом [паникует](glossary.md#panic-recover) при несовпадении, форма comma-ok — нет. Type switch перебирает несколько типов сразу.

```go
var x any = "hi"
s, ok := x.(string)  // "hi" true
n, ok2 := x.(int)    // 0 false
_ = x.(int)          // panic: interface conversion: interface {} is string, not int

func kind(x any) string {
	switch v := x.(type) {
	case nil:
		return "nil"
	case int, int64:
		return fmt.Sprintf("целое %v (%T)", v, v) // в case с несколькими типами v имеет тип any
	case string:
		return "строка длины " + fmt.Sprint(len(v)) // здесь v — string
	case error:
		return "ошибка: " + v.Error()
	case fmt.Stringer:
		return "Stringer: " + v.String()
	default:
		return fmt.Sprintf("другое %T", v)
	}
}
```

**🔧 Под капотом**
- Assertion к конкретному типу — сравнение указателя на тип, очень дёшево.
- Assertion к интерфейсу — поиск `itab` для пары типов: кэш у места вызова, затем глобальная таблица ([вопрос 9](#q1-6-09)).
- Type switch проверяет case по порядку.

**⚠️ Подвохи и версии Go**
- Порядок case важен: если `fmt.Stringer` стоит раньше `error`, тип с обоими методами попадёт в первый подходящий.
- Применения:
  - проверка необязательной возможности: `if f, ok := w.(http.Flusher); ok { f.Flush() }` — так сделаны `io.WriterTo`, `io.ReaderFrom`;
  - разбор значений из `any` (JSON, конфиги);
  - обработка вариантов типа-суммы ([вопрос 15](#q1-6-15)).
- Для ошибок вместо assertion — `errors.As`, он видит обёрнутые ошибки.

**🎤 Прямая речь**
> Type assertion достаёт из интерфейса конкретный тип: `x.(string)`. Если тип не совпал, форма с одним значением паникует, поэтому почти всегда я пишу comma-ok — `v, ok := x.(T)`. Assertion можно делать и к другому интерфейсу — так проверяют необязательные возможности, например есть ли у `ResponseWriter` метод `Flush`.
>
> Type switch — то же для нескольких типов: в каждой ветке переменная уже нужного типа. Важно помнить, что case проверяются по порядку, а для ошибок вместо assertion лучше `errors.As`, потому что он смотрит сквозь обёртки.

### 15. ⭐ Тип-сумма: что это и как реализовать на Go?

**⚡ Суть**
Тип-сумма (sum type, tagged union) — значение, которое может быть одним из фиксированного набора вариантов: например, «круг или квадрат», «успех или ошибка». В Rust и TypeScript это встроено, в Go — нет. Типичная замена — закрытый (sealed) интерфейс с неэкспортируемым методом-маркером плюс type switch.

```go
type Shape interface {
	Area() float64
	isShape() // неэкспортируемый: реализовать можно только в этом пакете
}

type Circle struct{ R float64 }
type Square struct{ S float64 }

func (c Circle) Area() float64 { return math.Pi * c.R * c.R }
func (s Square) Area() float64 { return s.S * s.S }
func (Circle) isShape()        {}
func (Square) isShape()        {}

func describe(s Shape) string {
	switch v := s.(type) {
	case Circle:
		return fmt.Sprintf("круг r=%v", v.R)
	case Square:
		return fmt.Sprintf("квадрат s=%v", v.S)
	default:
		panic("unknown shape")
	}
}
```

**🔧 Под капотом**
- Неэкспортируемый метод нельзя объявить в другом пакете, поэтому набор вариантов закрыт.
- Так сделаны, например, узлы AST в `go/ast` (`Expr`, `Stmt` с методами `exprNode()`, `stmtNode()`).

**⚠️ Подвохи и версии Go**
- Компилятор не проверяет полноту switch: добавил вариант — старые switch молча уйдут в `default`. Помогает линтер `exhaustive` и `panic` в `default`.
- nil-интерфейс — ещё одно «незапланированное» значение, его тоже нужно обработать.
- Альтернатива — структура с полем-тегом (`Kind`) и полями всех вариантов: проще, но тратит память и не защищает от несогласованных данных.
- Дженерики сумму не дают: ограничение `int | string` годится только для параметров типа, не для переменных.

**🎤 Прямая речь**
> Тип-сумма — это значение, которое может быть одним из фиксированного набора вариантов, как enum с данными в Rust. В Go такого нет, поэтому делают закрытый интерфейс: у него есть неэкспортируемый метод-маркер, и реализовать его можно только в своём пакете. Варианты — отдельные структуры, а обработка — через type switch.
>
> Минус — компилятор не проверяет, что switch разбирает все варианты, поэтому в `default` я ставлю [панику](glossary.md#panic-recover) и использую линтер `exhaustive`. Так устроены, например, узлы AST в `go/ast`.

### 16. Где объявлять интерфейс: на стороне потребителя или реализации? Почему?

**⚡ Суть**
На стороне потребителя — там, где интерфейс используется. Потребитель описывает только те методы, которые ему нужны, а реализация возвращает конкретный тип. Принцип: «принимай интерфейсы, возвращай структуры» (accept interfaces, return structs).

```go
// пакет service — потребитель
type UserStore interface {
	GetUser(ctx context.Context, id int64) (User, error)
}

type Service struct{ store UserStore }

// пакет postgres — реализация, о service ничего не знает
type Repo struct{ db *sql.DB }

func (r *Repo) GetUser(ctx context.Context, id int64) (service.User, error) { /* ... */ }
func (r *Repo) ListUsers(ctx context.Context) ([]service.User, error)      { /* ... */ }
```

**🔧 Под капотом**
- Это работает благодаря неявной реализации: `*Repo` подходит под `UserStore`, хотя пакет `postgres` его не импортирует.
- Зависимости направлены от деталей к бизнес-логике — основа чистой архитектуры (блок 5.2).

**⚠️ Подвохи и версии Go**
- Интерфейс на стороне реализации («`Repository` со всеми 20 методами рядом с `Repo`») — привычка из Java. Он раздувается, а каждый потребитель зависит от методов, которые не использует (нарушение ISP).
- Исключения: интерфейс и есть продукт пакета (`io.Reader`, `sort.Interface`, `http.Handler`), или у пакета много реализаций одного контракта (драйверы `database/sql/driver`).
- Не нужно заводить интерфейс «на будущее» для единственной реализации — его легко добавить у потребителя, когда понадобится мок.

**🎤 Прямая речь**
> Интерфейс объявляю у потребителя: сервис сам описывает, что ему нужно от хранилища, например один метод `GetUser`. Реализация в пакете с Postgres возвращает конкретную структуру и ничего не знает об этом интерфейсе — неявная реализация связывает их сама. Принцип называется «принимай интерфейсы, возвращай структуры».
>
> Так интерфейсы получаются маленькими, тесты пишутся с простым моком, а зависимости направлены от инфраструктуры к бизнес-логике. Интерфейс рядом с реализацией оправдан, когда он сам по себе продукт пакета, как `io.Reader`, или когда реализаций много, как у драйверов БД.

### 17. Embedding — это наследование? Почему нет?

**⚡ Суть**
Нет. Встраивание (embedding) — композиция с синтаксическим сахаром: поля и методы встроенного типа «продвигаются» во внешний и вызываются напрямую. Но внешняя структура не становится подтипом встроенной, а методы встроенного типа ничего не знают о внешнем — виртуальных методов и переопределения нет.

```go
type Animal struct{ Name string }

func (a Animal) Sound() string    { return "..." }
func (a Animal) Describe() string { return a.Name + " says " + a.Sound() }

type Dog struct {
	Animal // встраивание
	Breed  string
}

func (d Dog) Sound() string { return "woof" }

d := Dog{Animal{"Rex"}, "lab"}
fmt.Println(d.Sound(), d.Name, d.Animal.Sound()) // woof Rex ...
fmt.Println(d.Describe())                        // Rex says ... — а не woof
```

**🔧 Под капотом**
- `Dog` содержит поле `Animal`. `d.Describe()` компилятор переписывает в `d.Animal.Describe()`, и внутри получатель — `Animal`, а не `Dog`. Поэтому вызывается `Animal.Sound`.
- `Dog` нельзя передать туда, где ждут `Animal`:
  ```
  cannot use Dog{} (value of struct type Dog) as Animal value in argument to feed
  ```
- Продвинутые методы попадают в [method set](glossary.md#method-set) внешнего типа, поэтому `Dog` реализует те же интерфейсы, что и `Animal`. Полиморфизм в Go — через интерфейсы.

**⚠️ Подвохи и версии Go**
- Два встроенных типа с одинаковым методом на одной глубине — конфликт, ошибка при обращении: `ambiguous selector c.Hello`.
- Встраивание продвигает **все** экспортируемые методы. Встроишь `sync.Mutex` в публичную структуру — у неё появятся публичные `Lock`/`Unlock`. Мьютекс лучше делать именованным полем.
- Встраивать можно и интерфейсы — в интерфейсы (`io.ReadWriter`) и в структуры (обёртка, переопределяющая один метод).

**🎤 Прямая речь**
> Встраивание — это композиция, а не наследование. Встроенная структура становится полем, а её поля и методы можно вызывать напрямую — компилятор сам дописывает путь. Но внешний тип не становится подтипом: `Dog` нельзя передать туда, где ждут `Animal`, и нет виртуальных методов.
>
> Это видно на примере: если `Animal.Describe` вызывает `Sound`, то для `Dog` всё равно вызовется `Animal.Sound`, даже если у `Dog` есть свой. Полиморфизм в Go делается через интерфейсы. Встраивание удобно, но я помню, что оно продвигает все методы наружу, — поэтому мьютекс, например, делаю именованным полем.

### 18. Почему нельзя копировать структуру с `sync.Mutex` внутри? Как это ловит `go vet`?

**⚡ Суть**
`sync.Mutex` — это состояние в памяти (8 байт: флаги и семафор). Копия получает своё отдельное состояние: две [горутины](glossary.md#goroutine), работающие с разными копиями, не исключают друг друга. А копия заблокированного мьютекса остаётся заблокированной навсегда. `go vet` (анализатор `copylocks`) находит копирование типов с методами `Lock`/`Unlock`.

```go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Get() int { // value receiver — копия мьютекса при каждом вызове
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}

var c Counter
c2 := c
```

```
$ go vet ./cnt
cnt/main.go:13:9: Get passes lock by value: f16/cnt.Counter contains sync.Mutex
cnt/main.go:21:8: assignment copies lock value to c2: f16/cnt.Counter contains sync.Mutex
```

Копия заблокированного мьютекса:
```go
var c Counter
c.mu.Lock()
c2 := c // копия в состоянии «заблокирован»
c.mu.Unlock()
c2.mu.Lock() // fatal error: all goroutines are asleep - deadlock!
```

**🔧 Под капотом**
- В Go 1.26 `sync.Mutex` — это `struct{ _ noCopy; mu isync.Mutex }`, а внутри `state int32` и `sema uint32`.
- [`noCopy`](glossary.md#nocopy) — пустая структура с методами `Lock` и `Unlock`: по ним `copylocks` и узнаёт «некопируемые» типы. Тот же трюк можно применить к своей структуре: добавить поле `_ noCopy`.
- `go test` запускает только часть анализаторов vet, и `copylocks` в неё не входит. Поэтому нужен явный `go vet ./...` в CI.

**⚠️ Подвохи и версии Go**
- Где копия появляется незаметно: value receiver, передача структуры по значению, `range` по слайсу структур (`for _, c := range counters`), возврат по значению.
- Решение: pointer receiver для всех методов типа с мьютексом и передача `*Counter`.
- То же относится к `sync.WaitGroup`, `sync.Once`, `sync.Cond`, атомикам `atomic.Int64` и `strings.Builder` (у него своя проверка копирования в рантайме).

**🎤 Прямая речь**
> Мьютекс — это состояние в памяти: флаг блокировки и семафор. Если скопировать структуру с мьютексом, у копии будет отдельный мьютекс, и он ни от чего не защищает: горутины, работающие с разными копиями, не исключают друг друга. А если копировали заблокированный мьютекс, копия так и останется заблокированной — дальше дедлок.
>
> Чаще всего копия появляется незаметно — через value receiver или range по слайсу структур. Ловит это `go vet` анализатором copylocks: он ищет копирование типов с методами Lock и Unlock, у мьютекса для этого есть встроенный маркер `noCopy`. Поэтому у типов с мьютексом все методы — на указателе, и vet — в CI.

### 19. ⭐ Когда интерфейс вызывает аллокацию?

**⚡ Суть**
Второе слово интерфейса — указатель на данные. Если значение само является указателем (указатель, map, канал, функция), оно кладётся прямо туда — без аллокации. Иначе значение копируется в отдельную память, и если интерфейс убегает в [кучу](glossary.md#stack-heap), это аллокация. Исключения без аллокации: нулевые размеры, значения 0–255 для целых, однобайтовые типы, пустая строка, константы.

Замер на Go 1.26, значение передаётся в `any`, который сохраняется в глобальную переменную (убегает):

| Значение | Аллокаций |
|---|---:|
| `int` = 7 | 0 |
| `int` = 1000 | 1 |
| константа `1000` | 0 |
| `float64` | 1 |
| `bool`, `byte` = 200 | 0 |
| непустая `string` | 1 |
| пустая `string` | 0 |
| `struct{ A, B int }` | 1 |
| указатель | 0 |
| слайс | 1 |
| `struct{}` | 0 |

**🔧 Под капотом**
- Функции рантайма `convT16`, `convT32`, `convT64` для значений меньше 256 возвращают указатель на элемент статического массива `staticuint64s [256]uint64` — без аллокации.
- `convTstring` и `convTslice` для пустой строки или nil-слайса возвращают указатель на общий нулевой буфер `zeroVal`.
- Константы компилятор кладёт в [read-only секцию](glossary.md#rodata) бинарника и ссылается на неё.
- Если интерфейс не убегает (используется только локально), значение может остаться на стеке — тоже без аллокации. Проверка: `go build -gcflags=-m`.

**⚠️ Подвохи и версии Go**
- Горячий путь с `fmt.Sprintf`, `log.Printf("%d", x)`, `[]any` — каждая упаковка может аллоцировать. Отсюда типизированные API в быстрых логгерах (`zap.Int`, `slog.Int`).
- Дженерики вместо `any` в горячем коде часто убирают упаковку.
- Замер своего случая — `testing.AllocsPerRun` или бенчмарк с `b.ReportAllocs()`.

**🎤 Прямая речь**
> Интерфейс хранит указатель на данные. Если значение само по себе указатель — указатель, map, канал, — оно кладётся прямо в интерфейс без аллокации. Остальное копируется в отдельную память, и если интерфейс уходит в кучу, это аллокация: например, `int` 1000, float, непустая строка или структура.
>
> Есть оптимизации: для чисел от 0 до 255 рантайм берёт указатель из статического массива, пустая строка и нулевые размеры ссылаются на общий буфер, константы лежат в бинарнике. Я проверял через `AllocsPerRun`: `int` 7 даёт ноль аллокаций, а `int` 1000 — одну. Поэтому в горячем коде избегаю `any` и `fmt`, а логгеры используют типизированные поля.

### 20. Сериализация: что это, зачем; JSON-теги, неэкспортируемые поля

**⚡ Суть**
Сериализация — превращение значения в байты для передачи по сети или сохранения (JSON, Protobuf, gob), десериализация — обратно. `encoding/json` работает через [рефлексию](glossary.md#reflection): видит только экспортируемые поля, а имена и поведение задаются тегами.

```go
type User struct {
	ID       int       `json:"id"`
	Name     string    `json:"name,omitempty"`  // пропустить, если ""
	Email    string    `json:"-"`               // никогда не сериализовать
	password string                             // неэкспортируемое — json его не видит
	Created  time.Time `json:"created,omitzero"` // пропустить нулевое время (Go 1.24)
	Tags     []string  `json:"tags,omitempty"`
	Score    int       `json:"score,string"`    // число как строка
}

b, _ := json.Marshal(User{ID: 1, Email: "a@b", password: "x", Score: 5})
fmt.Println(string(b)) // {"id":1,"score":"5"}
```

**🔧 Под капотом**
- `json.Marshal` разбирает тип через рефлексию один раз и кэширует кодировщик для типа.
- Поиск ключа при `Unmarshal` — без учёта регистра; неизвестные поля молча игнорируются (запретить — `Decoder.DisallowUnknownFields`).
- `omitempty` пропускает false, 0, nil, пустые строки, слайсы и map, но **не** пустую структуру:
  ```go
  // `json:"created,omitempty"` → {"created":"0001-01-01T00:00:00Z"}
  // `json:"created,omitzero"`  → {}
  ```
  `omitzero` (Go 1.24) пропускает нулевое значение любого типа и учитывает метод `IsZero() bool`.

**⚠️ Подвохи и версии Go**
- Неэкспортируемое поле не попадёт в JSON и не заполнится из него — частая причина «пустых» ответов API. Тег на нём ничего не меняет.
- `json:"-"` защищает секреты при сериализации, но не заменяет отдельную DTO для ответа.
- Числа в `map[string]any` после `Unmarshal` — `float64`, большие ID теряют точность. Решение — `Decoder.UseNumber` или конкретные типы.
- `encoding/json/v2` в Go 1.26 доступен только с `GOEXPERIMENT=jsonv2`.
- Для внутреннего общения сервисов чаще Protobuf: компактнее, быстрее, со схемой.

**🎤 Прямая речь**
> Сериализация — это превращение значения в байты, чтобы передать по сети или сохранить, десериализация — обратный процесс. Стандартный `encoding/json` работает через рефлексию, поэтому видит только экспортируемые поля, а теги задают имя в JSON и правила: `omitempty` — пропустить пустое значение, минус — никогда не сериализовать, `string` — число как строку.
>
> Подводные камни: неэкспортируемое поле молча пропадает из JSON, `omitempty` не работает для структур вроде `time.Time` — для этого с Go 1.24 есть `omitzero`, а числа в `map[string]any` становятся float64. Для межсервисного общения я бы взял Protobuf — компактнее и со схемой.

### 21. Реализуй интерфейс площади для `Circle` и `Square`

**⚡ Суть**
Интерфейс с одним методом `Area() float64` и две структуры, у которых есть этот метод. Дальше обе работают как `Shape` — например, в одном слайсе.

```go
type Shape interface {
	Area() float64
}

type Circle struct{ R float64 }
type Square struct{ S float64 }

func (c Circle) Area() float64 { return math.Pi * c.R * c.R }
func (s Square) Area() float64 { return s.S * s.S }

var (
	_ Shape = Circle{}
	_ Shape = Square{}
)

func TotalArea(shapes ...Shape) float64 {
	total := 0.0
	for _, s := range shapes {
		total += s.Area()
	}
	return total
}

fmt.Printf("%.2f\n", TotalArea(Circle{1}, Square{2})) // 7.14
```

**⚠️ Подвохи и версии Go**
- Value receiver: метод не меняет фигуру, а `Circle` и `Square` — маленькие. Тогда интерфейс реализуют и значения, и указатели.
- Если сделать `func (s *Square) Area()`, то `Square{}` уже не подойдёт как `Shape`, только `&Square{}` ([вопрос 8](#q1-6-08)).
- На собесе могут попросить расширить: добавить `Perimeter()` (все реализации должны его получить) или `String()` для вывода через `fmt`.
- Нужен закрытый набор фигур — тип-сумма ([вопрос 15](#q1-6-15)).

**🎤 Прямая речь**
> Объявляю интерфейс `Shape` с методом `Area`, две структуры — `Circle` с радиусом и `Square` со стороной — и у каждой метод `Area` с value receiver, потому что метод ничего не меняет, а структуры маленькие. Реализацию проверяю строкой `var _ Shape = Circle{}`. После этого фигуры можно класть в один слайс `[]Shape` и считать общую площадь в цикле.
>
> Если бы я сделал receiver указателем, `Square{}` перестал бы реализовывать интерфейс — только `&Square{}`. Это частый вопрос вдогонку, поэтому про [method set](glossary.md#method-set) стоит сказать сразу.
