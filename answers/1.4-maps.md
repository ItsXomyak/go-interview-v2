### 1. Как работает хеш-таблица? Что такое хеш-функция?

**⚡ Суть**
Хеш-таблица хранит пары «ключ → значение» и даёт поиск, вставку и удаление за O(1) в среднем. [Хеш-функция](glossary.md#hash-function) превращает ключ в число, по числу вычисляется номер ячейки в массиве. Разные ключи могут попасть в одну ячейку — это коллизия, поэтому таблица хранит и сам ключ и при поиске сравнивает его.

**🔧 Под капотом**
- Номер ячейки: `hash(key) mod N`. Если N — степень двойки, это просто младшие биты: `hash & (N-1)`.
- [Load factor](glossary.md#load-factor) — сколько элементов приходится на ячейку (или доля занятых слотов). При превышении порога таблица растёт, обычно вдвое, и все элементы перераскладываются по новым ячейкам. Рост стоит O(n), но бывает редко, поэтому вставка — O(1) [амортизированно](glossary.md#amortized).
- Требования к хеш-функции для таблицы:
  - равные ключи дают равный хеш (согласованность с `==`);
  - хеши распределены равномерно — иначе всё ляжет в несколько ячеек;
  - быстрая;
  - со случайным seed — чтобы злоумышленник не подобрал ключи с одинаковым хешем ([hash flooding](glossary.md#hash-flooding)).
- Криптостойкость не нужна: SHA-256 для хеш-таблицы слишком медленный.

**⚠️ Подвохи и версии Go**
- Хеш — не идентификатор: совпадение хешей не значит равенство ключей, сравнение ключа обязательно.
- Плохая хеш-функция превращает таблицу в список: все ключи в одной ячейке → O(n) на операцию.
- В Go хеш 64-битный, и у каждой map свой случайный seed ([вопрос 7](#q1-4-07)).

**🎤 Прямая речь**
> Хеш-таблица — массив ячеек, куда пары ключ-значение раскладываются по хешу ключа. Хеш-функция превращает ключ в число, по нему вычисляется номер ячейки, поэтому поиск, вставка и удаление в среднем работают за O(1). Разные ключи могут попасть в одну ячейку — это коллизия, поэтому ключ хранится рядом со значением и при поиске сравнивается.
>
> От хеш-функции нужно, чтобы равные ключи давали равный хеш, хеши распределялись равномерно и считались быстро. Ещё нужен случайный seed, чтобы нельзя было подобрать ключи с одинаковым хешем и положить сервис. Когда таблица заполняется выше порога, она растёт вдвое и перераскладывает элементы — это O(n), но редко, поэтому вставка остаётся O(1) амортизированно.

### 2. Методы разрешения коллизий (цепочки, открытая адресация)

**⚡ Суть**
Два основных подхода. **Цепочки** (separate chaining): каждая ячейка хранит список элементов с таким номером. **[Открытая адресация](glossary.md#open-addressing)**: все элементы лежат в одном массиве, а при коллизии ищется следующий слот по заданной последовательности проб.

**🔧 Под капотом**
- **Цепочки:** вставка — добавить в список ячейки, поиск — пройти список. Выдерживают [load factor](glossary.md#load-factor) больше 1, удаление простое. Минус — указатели и промахи кэша на каждом узле. В Java `HashMap` длинная цепочка (больше 8 элементов) превращается в красно-чёрное дерево.
- **Открытая адресация:** последовательность проб бывает:
  - линейная (`i, i+1, i+2…`) — лучшая локальность, но элементы слипаются в кластеры;
  - квадратичная (шаги 1, 2, 3… от предыдущей позиции) — меньше кластеров;
  - двойное хеширование — шаг считается второй [хеш-функцией](glossary.md#hash-function).
- В открытой адресации удалённый слот нельзя просто очистить: поиск остановится на пустом слоте и не найдёт элементы дальше по цепочке проб. Поэтому слот помечают [tombstone](glossary.md#tombstone) («удалено»), а чистят их при перестройке таблицы.
- Открытая адресация компактнее и дружелюбнее к кэшу CPU (данные подряд, без указателей), но чувствительна к заполнению: ближе к 100% пробы становятся длинными. Поэтому порог роста ~70–90%.

**В Go:**
- Классическая map (до 1.24) — гибрид: бакеты по 8 слотов, внутри бакета линейный просмотр, при переполнении — цепочка overflow-бакетов.
- Map на [Swiss Tables](glossary.md#swiss-tables) (1.24+) — открытая адресация: группы по 8 слотов и квадратичное пробирование групп.

**⚠️ Подвохи и версии Go**
- Вопрос «что лучше» — про trade-off: цепочки проще и устойчивы к переполнению, открытая адресация быстрее за счёт локальности, но сложнее с удалением.

**🎤 Прямая речь**
> Есть два классических подхода. Метод цепочек — в каждой ячейке список элементов с одинаковым номером: просто и выдерживает высокое заполнение, но каждый узел — указатель и промах кэша. Открытая адресация — всё в одном массиве, а при коллизии идём по последовательности проб, линейной или квадратичной, до свободного слота. Это компактнее и быстрее за счёт локальности, но таблицу нельзя заполнять почти полностью, а удалённые элементы помечаются tombstone, иначе поиск оборвётся раньше времени.
>
> В Go классическая map была гибридом: бакеты по 8 элементов и цепочки overflow-бакетов. С 1.24 map построена на Swiss Tables — это открытая адресация с группами по 8 слотов.

### 3. Как устроена map в Go под капотом (классическая: `hmap`, бакеты)? Сколько элементов в бакете?

**⚡ Суть**
Переменная типа map — указатель на структуру рантайма `hmap`. В ней массив из 2^B бакетов, в каждом бакете **8 слотов** под пары ключ-значение и указатель на overflow-бакет. Таблица растёт, когда в среднем на бакет приходится больше 6.5 элементов. Так map была устроена до Go 1.24; новая устроена иначе ([вопрос 5](#q1-4-05)), но группа в ней тоже на 8 слотов.

**🔧 Под капотом**
```go
// runtime/map.go, Go 1.23
type hmap struct {
	count      int            // число элементов, его возвращает len()
	flags      uint8          // идёт запись, есть итератор и т.п.
	B          uint8          // log2 числа бакетов
	noverflow  uint16         // примерное число overflow-бакетов
	hash0      uint32         // seed хеша
	buckets    unsafe.Pointer // массив из 2^B бакетов
	oldbuckets unsafe.Pointer // старый массив во время роста
	nevacuate  uintptr        // прогресс эвакуации
	extra      *mapextra
}

type bmap struct {
	tophash [8]uint8 // старшие 8 бит хеша каждого слота
	// дальше 8 ключей подряд, потом 8 значений подряд, потом указатель на overflow
}
```
- Номер бакета — младшие B бит хеша, `tophash` — старшие 8 бит. Значения `tophash` от 0 до 4 зарезервированы под состояние слота («пусто», «эвакуирован»), поэтому реальный tophash меньше 5 сдвигается.
- Ключи и значения лежат не вперемешку, а блоками: так нет [padding](glossary.md#alignment) у `map[int64]int8`.
- Ключи и значения больше 128 байт хранятся по указателю.
- Порог [load factor](glossary.md#load-factor) — 6.5 из 8 (~81%). Растёт и при переизбытке overflow-бакетов ([вопрос 4](#q1-4-04)).
- Сама `hmap` на 64-битной платформе — 48 байт.

**⚠️ Подвохи и версии Go**
- Map — ссылочный тип: в функцию копируется 8-байтный указатель, изменения видны снаружи. Но присвоить новую map параметру внутри функции — не изменить переменную снаружи.
- С Go 1.24 `hmap` нет: в 1.24–1.25 старую реализацию можно было вернуть флагом `GOEXPERIMENT=noswissmap`, в 1.26 её код удалён. Отвечая, назови обе и уточни, о какой версии речь.

**🎤 Прямая речь**
> Переменная map — указатель на структуру рантайма. В классической реализации это `hmap`: число элементов, seed хеша, B — логарифм числа бакетов — и указатель на массив из 2^B бакетов. В каждом бакете 8 слотов: массив tophash со старшими байтами хешей, потом 8 ключей, потом 8 значений и указатель на overflow-бакет, если слоты кончились. Бакет выбирается по младшим битам хеша, tophash позволяет быстро отсеять несовпадающие слоты без сравнения ключей.
>
> Map растёт, когда в среднем на бакет больше 6.5 элементов. С Go 1.24 map переписали на [Swiss Tables](glossary.md#swiss-tables) — там группы, тоже по 8 слотов, и [открытая адресация](glossary.md#open-addressing) вместо цепочек overflow.

### 4. Что такое эвакуация, когда она происходит и как её избежать?

**⚡ Суть**
[Эвакуация](glossary.md#evacuation) — перенос элементов из старого массива бакетов в новый при росте классической map. Она постепенная: не за одну вставку, а понемногу при каждой записи и удалении. Избежать — задать размер заранее: `make(map[K]V, n)`.

**🔧 Под капотом**
- Рост запускает вставка в двух случаях:
  1. элементов больше 6.5 × 2^B — массив **удваивается** (B+1);
  2. слишком много overflow-бакетов (не меньше 2^min(B, 15)) — рост **того же размера** (same-size grow): элементы переупаковываются плотнее. Так бывает после множества удалений.
- `hashGrow` выделяет новый массив, старый сохраняет в `oldbuckets`. Дальше каждая вставка и удаление вызывает `growWork`: эвакуирует бакет, с которым сейчас работает, и ещё один по счётчику `nevacuate`.
- При удвоении старый бакет делится на два — X (тот же номер) и Y (номер + 2^oldB) — по следующему биту хеша.
- Пока рост идёт, поиск смотрит в старый бакет, если тот ещё не эвакуирован.
- Зачем постепенно: перенос сразу всех элементов — это O(n) за одну вставку и пик латентности.

**Map на [Swiss Tables](glossary.md#swiss-tables) (1.24+):** слова «эвакуация» там нет. Таблица до 1024 слотов растёт целиком (заменяется вдвое большей), а дальше делится на две (split). За одну вставку переносится не больше одной таблицы, поэтому пауза ограничена.

Предварительный размер на Go 1.26, 100 000 вставок `map[int]int`:

| | время | аллокаций | память |
|---|---:|---:|---:|
| `make(map[int]int)` | ~4.9 мс | 532 | 4.6 МБ |
| `make(map[int]int, 100_000)` | ~2.0 мс | 258 | 2.3 МБ |

**⚠️ Подвохи и версии Go**
- Map никогда не уменьшается: same-size grow убирает overflow-бакеты, но число бакетов не уменьшает ([вопрос 13](#q1-4-13)).
- Hint — подсказка, а не лимит: map вырастет дальше, если элементов больше.
- Слишком большой hint — лишняя память сразу.

**🎤 Прямая речь**
> Эвакуация — перенос элементов в новый массив бакетов, когда классическая map растёт. Рост запускается, если в среднем на бакет больше 6.5 элементов — тогда массив удваивается, или если накопилось слишком много overflow-бакетов — тогда map переупаковывается без изменения размера. Переносится не всё сразу: при каждой записи или удалении эвакуируются бакет, с которым работаем, и ещё один. Пока перенос идёт, поиск заглядывает и в старый массив. Так нет одной долгой вставки на O(n).
>
> Избежать — передать размер в `make`, если он известен: меньше аллокаций и никаких переносов. В новой map на Swiss Tables эвакуации в таком виде нет — растёт отдельная таблица до 1024 слотов, поэтому пауза ограничена.

<a id="q1-4-05"></a>
### 5. ⭐ Map на Swiss Tables (Go 1.24+): чем отличается от старой реализации?

**⚡ Суть**
С Go 1.24 map построена на [Swiss Tables](glossary.md#swiss-tables): [открытая адресация](glossary.md#open-addressing) вместо бакетов с цепочками overflow. Слоты объединены в группы по 8, у группы есть контрольное слово, по которому проверяются все 8 слотов одной операцией. По данным команды Go — до 60% быстрее на микробенчмарках, около 1.5% CPU в среднем на реальных приложениях.

**🔧 Под капотом**
- **Группа:** 8 слотов + контрольное слово из 8 байт, по байту на слот. Байт хранит состояние (пусто / удалено / занято) и для занятого слота — младшие 7 бит хеша (**H2**).
- **Поиск в группе:** H2 искомого ключа сравнивается сразу со всеми 8 байтами битовой арифметикой; на amd64 — [SIMD](glossary.md#simd)-инструкциями. Ложное совпадение — 1 из 128 на слот, ключ всё равно сравнивается.
- **Пробирование:** старшие 57 бит хеша (**H1**) выбирают стартовую группу, дальше квадратичная последовательность. Пустой слот в группе означает «ключа нет, дальше не ищем».
- **[Load factor](glossary.md#load-factor)** — 7/8 (у старой ~6.5/8).
- **Каталог таблиц** (extendible hashing): map — массив указателей на таблицы до 1024 слотов, таблица выбирается по старшим битам хеша. Растёт только переполненная таблица: удваивается, а дойдя до 1024 слотов, делится на две.
- **Маленькая map** (до 8 элементов) — одна группа без каталога и таблиц.
- **Удаление:** если в группе есть пустой слот, слот сразу пустой; если группа полная — ставится [tombstone](glossary.md#tombstone).

| | Классическая (до 1.24) | Swiss Tables (1.24+) |
|---|---|---|
| Коллизии | бакеты + цепочки overflow | открытая адресация |
| Блок | бакет: 8 слотов + `tophash[8]` | группа: 8 слотов + контрольное слово |
| Отсев слотов | по одному байту tophash | все 8 сразу (SWAR / SIMD) |
| Порог роста | 6.5 из 8 | 7 из 8 |
| Рост | постепенная [эвакуация](glossary.md#evacuation) всей map | одна таблица до 1024 слотов за раз |

**⚠️ Подвохи и версии Go**
- Семантика для кода не изменилась: случайный порядок, [неадресуемые](glossary.md#addressability) элементы, падение при конкурентной записи.
- В 1.24–1.25 старая map включалась `GOEXPERIMENT=noswissmap`, в 1.26 её удалили.
- Map по-прежнему не уменьшается.
- Команда Go отмечала, что на некоторых сценариях новая map медленнее старой.

**🎤 Прямая речь**
> С Go 1.24 map реализована на Swiss Tables — дизайн из Abseil от Google. Это открытая адресация: элементы лежат в группах по 8 слотов, у каждой группы контрольное слово, где на каждый слот есть байт с состоянием и 7 младшими битами хеша. При поиске старшие биты хеша выбирают группу, а младшие 7 бит сравниваются сразу со всеми восемью байтами одной операцией, на amd64 — SIMD-инструкциями. Ключи сравниваются только у кандидатов, а пустой слот в группе означает, что ключа нет.
>
> Вторая идея — map разбита на таблицы до 1024 слотов, и растёт только переполненная таблица. Поэтому нет постепенной эвакуации всей map, а пауза при росте ограничена. Порог заполнения выше — 7/8. По данным команды Go, операции с map стали до 60% быстрее на микробенчмарках и около 1.5% CPU в среднем на приложениях.

<a id="q1-4-06"></a>
### 6. Как происходит поиск по ключу?

**⚡ Суть**
Хеш ключа с seed этой map → по хешу выбирается место (бакет или группа) → по короткой части хеша отсеиваются слоты → у кандидатов ключ сравнивается полностью. Ключа нет — возвращается нулевое значение.

**🔧 Под капотом**

[Swiss Tables](glossary.md#swiss-tables) (Go 1.24+):
1. `hash := hasher(key, m.seed)`.
2. Маленькая map (до 8 элементов) — одна группа: сравнить H2 со всеми слотами, проверить ключи кандидатов.
3. Иначе выбрать таблицу из каталога по старшим битам хеша.
4. Стартовая группа — `H1 & mask`. Сравнить H2 с контрольным словом → кандидаты → сравнить ключи. Совпал — вернуть значение.
5. В группе есть пустой слот — ключа нет. Нет пустых — следующая группа по квадратичной последовательности.

Классическая map (до 1.24):
1. Бакет — младшие B бит хеша. Если идёт рост и старый бакет ещё не эвакуирован — искать в `oldbuckets`.
2. Пройти 8 `tophash` бакета, при совпадении старшего байта сравнить ключ.
3. Не нашли — перейти в overflow-бакет и повторить.

Компилятор подставляет разные функции рантайма: `v := m[k]` → `mapaccess1`, `v, ok := m[k]` → `mapaccess2`. Для ключей `int32`/`uint32`, `int64`/`uint64` и `string` есть ускоренные версии `mapaccess1_fast32`, `_fast64`, `_faststr`.

**⚠️ Подвохи и версии Go**
- Чтение одновременно с записью из разных [горутин](glossary.md#goroutine) — `fatal error: concurrent map read and map write`. Это не [паника](glossary.md#panic-recover): `recover` не поможет, процесс падает. Нужен `sync.RWMutex` или `sync.Map`.
- Ключ NaN не найти никогда ([вопрос 10](#q1-4-10)).

**🎤 Прямая речь**
> Сначала считается хеш ключа с seed конкретной map. В Swiss Tables старшие биты выбирают таблицу и стартовую группу, а младшие 7 бит сравниваются сразу с контрольными байтами всех восьми слотов. Для совпавших слотов ключ сравнивается полностью. Если в группе есть пустой слот, а ключ не нашёлся — его нет, иначе идём в следующую группу по квадратичной последовательности.
>
> В старой реализации младшие биты хеша выбирали бакет, старший байт сравнивался с tophash восьми слотов, потом шла цепочка overflow-бакетов, а во время роста ещё проверялся старый массив. В обоих случаях отсутствующий ключ даёт нулевое значение, а одновременное чтение и запись без синхронизации роняют процесс.

<a id="q1-4-07"></a>
### 7. Какая хеш-функция используется в map?

**⚡ Суть**
[Хеш-функцию](glossary.md#hash-function) выбирает рантайм по типу ключа, задать свою нельзя. Для байтов и строк на процессорах с AES-инструкциями используется **aeshash**, без них — функция на основе wyhash. У каждой map свой случайный seed.

**🔧 Под капотом**
- При старте рантайм проверяет CPU: на amd64 нужны AES, SSSE3 и SSE4.1, на arm64 — AES. Тогда `memhash`/`strhash` используют аппаратные раунды AES, иначе — `memhashFallback` (по мотивам wyhash).
- Для каждого типа ключа своя функция:
  - 4 и 8 байт — `memhash32`/`memhash64`;
  - строки — `strhash` (хеш байтов строки);
  - `float64` — `f64hash`: +0 и −0 дают один хеш, NaN — случайный;
  - интерфейсы — хеш по функции динамического типа; несравнимый тип → [паника](glossary.md#panic-recover);
  - структуры и массивы — комбинация хешей полей и элементов.
- Seed: `m.seed = rand()` при создании map. `clear(m)` выдаёт новый seed — ещё одна защита от [hash flooding](glossary.md#hash-flooding).

**⚠️ Подвохи и версии Go**
- Хеш нестабилен между запусками и между map — его нельзя сохранять или использовать для шардирования.
- Для своей хеш-таблицы, bloom-фильтра, шардирования внутри процесса — `hash/maphash`: `maphash.String`, `maphash.Bytes`, `maphash.Comparable` (Go 1.24). Для хеша, стабильного между запусками, — `hash/fnv`, `hash/crc32`, xxhash.

**🎤 Прямая речь**
> Хеш-функцию выбирает рантайм по типу ключа, своей задать нельзя. Для строк и байтов на процессорах с AES-инструкциями — а это почти все современные amd64 и arm64 — используется aeshash, иначе запасная функция на основе wyhash. Для чисел фиксированного размера, float, интерфейсов и структур есть свои версии: например, у float +0 и −0 считаются одним ключом.
>
> Каждая map получает случайный seed — это защита от hash flooding, когда атакующий подбирает ключи с одинаковым хешем и превращает O(1) в O(n). Поэтому хеш нестабилен между map и запусками. Если нужен свой хеш внутри процесса — беру `hash/maphash`, если стабильный — fnv или xxhash.

### 8. Что вернётся по несуществующему ключу? Как проверить наличие ключа?

**⚡ Суть**
Нулевое значение типа значения, без [паники](glossary.md#panic-recover). Проверить наличие — форма comma-ok: `v, ok := m[k]`.

```go
m := map[string]int{"a": 1}
v, ok := m["x"]
fmt.Println(m["x"], v, ok) // 0 0 false
```

**🔧 Под капотом**
- `m[k]` компилируется в `mapaccess1` — возвращает указатель на значение или на общую область нулей рантайма. `v, ok := m[k]` — в `mapaccess2`, которая дополнительно возвращает bool.

**⚠️ Подвохи и версии Go**
- Нулевое значение полезно в идиомах:
  ```go
  cnt := map[string]int{}
  cnt["x"]++                         // 1: отсутствующий ключ читается как 0
  g := map[string][]string{}
  g["k"] = append(g["k"], "v")       // append к nil-слайсу работает
  set := map[string]struct{}{}       // множество: значение 0 байт
  ```
- `map[string]bool`: `m[k] == false` не отличает «нет ключа» от «ключ со значением false» — нужен comma-ok.
- `map[string]*T`: отсутствующий ключ → `nil`, обращение к полю → nil pointer dereference.

**🎤 Прямая речь**
> По отсутствующему ключу map возвращает нулевое значение типа: 0, пустую строку, nil — без паники. Чтобы отличить «ключа нет» от «ключ есть со значением по умолчанию», использую comma-ok: `v, ok := m[k]`, ok будет false.
>
> Это поведение удобно: счётчик пишется как `m[k]++`, группировка — как `m[k] = append(m[k], v)`. Но для `map[string]bool` или map указателей без comma-ok легко ошибиться: false и nil там неотличимы от отсутствия ключа.

<a id="q1-4-09"></a>
### 9. Чтение и запись в nil-map

**⚡ Суть**
Из nil-map можно читать: чтение возвращает нулевое значение, `len` — 0, `range` — ни одной итерации, `delete` и `clear` ничего не делают. Запись — [паника](glossary.md#panic-recover) `assignment to entry in nil map`.

```go
var m map[string]int
fmt.Println(m["a"], len(m), m == nil) // 0 0 true
delete(m, "a")                        // ок
m["a"] = 1                            // panic: assignment to entry in nil map
```

**🔧 Под капотом**
- nil-map — нулевой указатель на структуру рантайма. Функции чтения сразу проверяют `m == nil` и возвращают ноль.
- Для записи нужна выделенная память. Рантайм не может создать её сам: map передаётся как указатель, и новая структура не попала бы в переменную вызывающего кода.

**⚠️ Подвохи и версии Go**
- Частый баг — поле-map в структуре, не инициализированное в конструкторе: `type Cache struct{ items map[string]int }`, `var c Cache; c.items["a"] = 1` → паника.
- `json.Unmarshal` в nil-map сам создаёт map, если передан указатель на неё.
- Возвращать nil-map из функции «только для чтения» нормально — читать её безопасно.

**🎤 Прямая речь**
> nil-map ведёт себя как пустая map только для чтения: обращение по ключу даёт нулевое значение, len — ноль, range ничего не делает, delete тоже. Записать нельзя — будет паника assignment to entry in nil map, потому что под nil-map нет выделенной памяти.
>
> На практике это всплывает, когда map — поле структуры и её забыли инициализировать в конструкторе. Поэтому map создаю через `make` или литерал в конструкторе, а в методах при необходимости делаю ленивую инициализацию.

### 10. Что может быть ключом map?

**⚡ Суть**
Любой сравнимый (comparable) тип — тот, для которого определён `==`: bool, числа, строки, указатели, каналы, интерфейсы, массивы и структуры из сравнимых полей. Нельзя: слайсы, map, функции и структуры или массивы с ними.

```go
bad := map[[]int]int{} // ошибка компиляции: invalid map key type []int

type P struct{ X, Y int }
pm := map[P]string{{1, 2}: "a"}          // составной ключ — структура
am := map[[2]int]string{{1, 2}: "b"}     // или массив
```

**🔧 Под капотом**
- Компилятор генерирует для типа ключа функции хеширования и сравнения. Для слайса, map и функции `==` не определён, поэтому и хеша нет.
- Интерфейсный ключ проверяется только в рантайме:
  ```go
  im := map[any]int{}
  im[[]int{1}] = 1 // panic: runtime error: hash of unhashable type []int
  ```

**⚠️ Подвохи и версии Go**
- **NaN:** `NaN != NaN`, поэтому каждая вставка NaN создаёт новую запись, найти её нельзя:
  ```go
  f := map[float64]int{}
  f[math.NaN()] = 1
  f[math.NaN()] = 2
  _, ok := f[math.NaN()]
  fmt.Println(len(f), ok) // 2 false
  ```
  Удалить такие записи можно только `clear(f)` (Go 1.21).
- `+0.0` и `-0.0` — один ключ.
- Указатель как ключ сравнивается по адресу, а не по содержимому.
- Составной ключ лучше делать структурой, а не склейкой строк `a + ":" + b`: нет коллизий вида `"a:" + "b"` и `"a" + ":b"` и лишних аллокаций.
- Ключи больше 128 байт хранятся по указателю — лишняя аллокация на элемент.

**🎤 Прямая речь**
> Ключом может быть любой comparable тип — тот, что сравнивается через `==`: числа, строки, bool, указатели, каналы, интерфейсы, а также массивы и структуры из таких типов. Слайсы, map и функции нельзя — компилятор скажет invalid map key type. Для составного ключа удобно брать структуру.
>
> Есть два подвоха. Интерфейсный ключ проверяется только в рантайме: положишь в `map[any]` слайс — получишь [панику](glossary.md#panic-recover) hash of unhashable type. И float: NaN не равен сам себе, поэтому каждая вставка NaN создаёт новую запись, которую потом не найти, — их убирает только `clear`.

### 11. Почему порядок итерации по map случайный?

**⚡ Суть**
Спецификация не задаёт порядок, а рантайм намеренно начинает обход со случайного места. Так никто не полагается на порядок, который всё равно меняется при росте map и между версиями Go.

```go
m := map[int]bool{0: true, 1: true, 2: true, 3: true, 4: true, 5: true, 6: true, 7: true, 8: true, 9: true}
for range 3 {
	s := ""
	for k := range m {
		s += fmt.Sprint(k)
	}
	fmt.Println(s)
}
// 2356780149
// 0149235678
// 3567801492   (у тебя будет другой порядок)
```

**🔧 Под капотом**
- Классическая map: итератор выбирает случайный стартовый бакет и случайное смещение внутри бакета.
- [Swiss Tables](glossary.md#swiss-tables): случайные смещения по каталогу таблиц и по слотам (`dirOffset`, `entryOffset`).
- Плюс у каждой map свой seed хеша — даже одинаковые map раскладывают ключи по-разному.

**⚠️ Подвохи и версии Go**
- Тесты, сравнивающие вывод `range` по map, падают через раз. Нужен порядок — сортируй ключи:
  ```go
  for _, k := range slices.Sorted(maps.Keys(m)) { // Go 1.23
  	fmt.Println(k, m[k])
  }
  ```
- `fmt.Println(m)` и `json.Marshal` выводят ключи отсортированными — это не значит, что map упорядочена.
- Менять map во время `range` можно: удалённые элементы больше не встретятся, а добавленные могут встретиться, а могут и нет.
- Порядок случайный, но не равномерно случайный: перемешивать данные через map нельзя, для этого есть `rand.Shuffle`.

**🎤 Прямая речь**
> Спецификация Go не гарантирует порядок обхода map, а рантайм специально стартует со случайной позиции. Порядок в хеш-таблице и так зависит от хешей, seed и истории роста, и меняется между версиями. Рандомизация не даёт случайно на него завязаться: такой баг всплывёт сразу, а не после обновления Go.
>
> Если нужен детерминированный порядок, собираю ключи и сортирую — с Go 1.23 это `slices.Sorted(maps.Keys(m))`. А то, что `fmt` печатает map отсортированной, — фича форматирования, а не map.

### 12. Почему нельзя взять адрес элемента `&m[k]`? Как изменить поле структуры, лежащей в map?

**⚡ Суть**
Элементы map [неадресуемы](glossary.md#addressability): при росте рантайм переносит их в другую память, и указатель указывал бы на старое место. Поэтому нельзя ни `&m[k]`, ни `m[k].Field = v`. Изменить поле можно так: прочитать копию → изменить → записать обратно, или хранить в map указатели.

```go
type User struct{ Name string; Age int }
m := map[string]User{}
m["a"].Age = 1 // cannot assign to struct field m["a"].Age in map
p := &m["a"]   // invalid operation: cannot take address of m["a"] (map index expression of struct type User)
```

**🔧 Под капотом**
- Слот элемента живёт, пока таблица не перестроится. После роста ([эвакуация](glossary.md#evacuation) или замена таблицы) значение лежит в другом месте, а старая память освобождается.
- `m[k]++` и `m[k] += v` разрешены: компилятор разворачивает их в чтение и запись, адрес наружу не выдаётся.

**Варианты изменения:**
```go
// 1. Копия → изменить → записать обратно
u := m["bob"]
u.Age++
m["bob"] = u

// 2. Хранить указатели
pm := map[string]*User{"bob": {Name: "Bob", Age: 30}}
pm["bob"].Age++
```

**⚠️ Подвохи и версии Go**
- Trade-off: указатели — изменение на месте и нет копирования больших структур, но отдельная аллокация на каждый элемент и больше работы для [GC](glossary.md#gc). Значения — компактнее и без лишних указателей, но с копированием.
- `for _, v := range m { v.Age++ }` меняет копию, map не изменится.
- Элемент слайса адресуем (`&s[i]`), но после `append` с переаллокацией такой указатель смотрит в старый массив.

**🎤 Прямая речь**
> Элементы map неадресуемы, потому что при росте рантайм переносит их в новую память — указатель на элемент мог бы указывать в старое место. Поэтому компилятор запрещает и `&m[k]`, и присваивание полю структуры прямо в map.
>
> Решения два. Если структура небольшая — прочитать копию, изменить и записать обратно. Если структуры большие или их часто меняют — хранить в map указатели, тогда `m[k].Field = v` работает. Цена — аллокация на каждый элемент и нагрузка на GC. При этом `m[k]++` работает, потому что компилятор разворачивает его в чтение и запись.

<a id="q1-4-13"></a>
### 13. Освобождает ли `delete` память? Как избежать утечек памяти в слайсах и map?

**⚡ Суть**
Нет. `delete` обнуляет ключ и значение — объекты, на которые они ссылались, может собрать [GC](glossary.md#gc), — но память самой таблицы остаётся: map никогда не уменьшается. Вернуть память можно, только создав новую map.

**🔧 Под капотом**
- Удалённый слот помечается пустым или [tombstone](glossary.md#tombstone), ключ и значение зануляются. Массив групп (или бакетов) остаётся того же размера.
- `clear(m)` (Go 1.21) зануляет всё сразу, но тоже не уменьшает таблицу.

Замер на Go 1.26, `map[int][64]byte` на 1 000 000 элементов:

| Действие | [Куча](glossary.md#stack-heap) |
|---|---:|
| заполнили | 160 МБ |
| `delete` всех ключей | 160 МБ |
| `clear(m)` | 160 МБ |
| скопировали живые элементы в новую map | 0 МБ |

Ещё одно последствие — медленный `range`: обход проходит все слоты. Map, в которой из миллиона элементов остался один, обходится ~2 мс, а свежая map с одним элементом — ~0.4 мкс.

**Как избежать утечек**
- **Map:**
  - после массового удаления пересоздать map: `nm := make(map[K]V, len(m))`, скопировать, `m = nm`;
  - кэши — с ограничением размера (LRU) или TTL, а не «растущая навсегда» map;
  - большие значения хранить по указателю: после `delete` в слоте останется 8 байт, а не всё значение. Значения больше 128 байт рантайм и так хранит по указателю.
- **Слайсы:**
  - маленький подслайс держит весь большой массив — копировать нужное: `slices.Clone`, `copy` ([1.3 · 14](1.3-slices.md#q1-3-14));
  - указатели за пределами `len` (после `s = s[:n]`) не дают GC собрать объекты — зануляй хвост: `clear(s[n:])`. `slices.Delete` и `slices.Compact` с Go 1.22 делают это сами;
  - `s = s[:0]` для переиспользования оставляет весь массив в памяти — нормально для буферов, плохо для разовых гигантских слайсов.

**⚠️ Подвохи и версии Go**
- Утечка «на ровном месте»: map-кэш на пике нагрузки вырос до гигабайта, потом почти опустел — память не вернётся, пока не пересоздашь map.
- `m = nil` или новая map работают, только если на старую map больше никто не ссылается.

**🎤 Прямая речь**
> `delete` память не освобождает. Он зануляет ключ и значение, поэтому объекты, на которые они ссылались, GC собрать сможет, но массив слотов самой map остаётся того же размера — map в Go никогда не уменьшается. Я проверял: map на миллион элементов занимает 160 мегабайт и после удаления всех ключей, и после `clear`. Плюс range по такой почти пустой map всё равно проходит все слоты.
>
> Поэтому для map, которые сильно растут и потом пустеют, — например, кэшей, — пересоздаю map, копируя живые элементы, или ограничиваю размер через LRU или TTL. В слайсах две типичные утечки: маленький подслайс, держащий огромный массив, — лечится копированием, и указатели в хвосте за длиной — лечится `clear` хвоста. `slices.Delete` с 1.22 зануляет хвост сам.

<a id="q1-4-14"></a>
### 14. Big-O операций с map

**⚡ Суть**
Поиск, вставка, удаление — O(1) в среднем (вставка — [амортизированно](glossary.md#amortized)). Худший случай — O(n), если все ключи попали в одно место, но в Go это почти исключено случайным seed. `len` — O(1). Обход и `clear` — O(ёмкости), а не O(len).

| Операция | Сложность | Комментарий |
|---|---|---|
| `m[k]`, `v, ok := m[k]` | O(1) в среднем | худший O(n) |
| `m[k] = v` | O(1) амортизированно | рост — O(n) по одной таблице, редко |
| `delete(m, k)` | O(1) в среднем | память не возвращается |
| `len(m)` | O(1) | число хранится в структуре |
| `for k, v := range m` | O(ёмкости) | после массовых удалений обход медленный |
| `clear(m)` | O(ёмкости) | зануление всех слотов |
| `maps.Clone(m)`, копирование | O(n) | |
| поиск по значению | O(n) | нужен обход |
| обход в отсортированном порядке | O(n log n) | `slices.Sorted(maps.Keys(m))` |

**🔧 Под капотом**
- В [Swiss Tables](glossary.md#swiss-tables) таблица не больше 1024 слотов, поэтому одна вставка с ростом переносит не больше одной таблицы — пик латентности ограничен. В классической map рост размазан по операциям [эвакуацией](glossary.md#evacuation).
- Память: `map[int]int` на Go 1.26 занимает ~26–36 байт на элемент (зависит от заполнения после роста), хотя полезных данных 16 байт. Слайс пар — ровно 16.

**⚠️ Подвохи и версии Go**
- O(1) — не значит «бесплатно»: хеш, сравнение ключа и промах кэша. Для десятка элементов линейный поиск по слайсу бывает быстрее map.
- Map не потокобезопасна: конкурентная запись — `fatal error: concurrent map writes`, процесс падает без возможности `recover`.

**🎤 Прямая речь**
> Чтение, вставка и удаление в map — O(1) в среднем, вставка — амортизированно, потому что иногда таблица растёт за O(n). Худший случай O(n), когда все ключи коллизируют, но случайный seed делает его практически недостижимым. len — O(1), он хранится в структуре.
>
> Два неочевидных момента: range и clear работают за O(ёмкости), а не числа элементов, — после массового удаления обход остаётся медленным. И константа у O(1) немаленькая: на маленьких наборах слайс с линейным поиском может обогнать map, а по памяти map примерно вдвое тяжелее слайса.

### 15. Сколько весят слайс, map, пустая строка, int?

**⚡ Суть**
На 64-битной платформе: `int` — 8 байт, слайс — 24 (указатель, len, cap), строка — 16 (указатель и len) даже пустая, map — 8 (это указатель). `unsafe.Sizeof` считает только заголовок, без данных, на которые он ссылается.

```go
var s []int; var str string; var i int; var m map[int]int
var e struct{}; var a any; var ch chan int
fmt.Println(unsafe.Sizeof(s), unsafe.Sizeof(str), unsafe.Sizeof(i), unsafe.Sizeof(m),
	unsafe.Sizeof(e), unsafe.Sizeof(a), unsafe.Sizeof(ch))
// 24 16 8 8 0 16 8
```

| Тип | Размер (64 бит) | Из чего |
|---|---:|---|
| `int`, `uint`, указатель | 8 | машинное слово; на 32-битных — 4 |
| `bool`, `int8`, `byte` | 1 | |
| `string` (и `""`) | 16 | указатель + длина; у `""` данных 0 байт |
| `[]T` | 24 | указатель + len + cap |
| `map[K]V`, `chan T`, `func` | 8 | указатель на структуру рантайма |
| `any`, интерфейс | 16 | указатель на тип или [itab](glossary.md#interface-layout) + указатель на данные |
| `struct{}`, `[0]T` | 0 | |

**🔧 Под капотом**
- Map — указатель на структуру рантайма. Замер на Go 1.26: `make(map[int]int)` выделяет 48 байт под структуру, первая вставка — группу из 8 слотов: 8 байт контрольного слова + 8 × 16 байт пар = 136 байт, аллокатор округляет до 144.
- Пустая строка не выделяет память: указатель nil или общий, длина 0.
- Размер структуры — сумма полей плюс [выравнивание](glossary.md#alignment) ([1.1 · 5](1.1-basics.md#q1-1-05)).

**⚠️ Подвохи и версии Go**
- `unsafe.Sizeof(make([]int, 1_000_000))` — 24, а не 8 МБ: данные считаются отдельно.
- Map, которая не выходит из функции, компилятор может разместить на [стеке](glossary.md#stack-heap) вместе с первой группой.

**🎤 Прямая речь**
> На 64-битной платформе int — 8 байт, слайс — 24: указатель на массив, длина и capacity. Строка — 16 байт: указатель и длина, и у пустой строки тоже 16, просто данных ноль. Map — 8 байт, потому что переменная map — указатель на структуру рантайма. Интерфейс — 16, пустая структура — 0.
>
> Важно, что `unsafe.Sizeof` показывает только заголовок. Реальная map весит больше: на Go 1.26 сама структура — 48 байт, плюс группы по 8 слотов, плюс запас под [load factor](glossary.md#load-factor).

<a id="q1-4-16"></a>
### 16. ⭐ Как реализовать разреженный массив на Go?

**⚡ Суть**
Разреженный массив — массив, где почти все элементы нулевые; хранят только ненулевые. Варианты: `map[int]T` (проще всего), отсортированные слайсы индексов и значений (компактно, бинарный поиск), страничный массив (как таблица страниц ОС), битовая карта + плотный массив.

**🔧 Под капотом**

Страничный массив: индекс делится на номер страницы и смещение, страница выделяется при первой записи.
```go
const pageBits = 10
const pageSize = 1 << pageBits

// Sparse — разреженный массив из страниц по 1024 элемента.
type Sparse[T any] struct {
	pages map[int]*[pageSize]T
}

func (s *Sparse[T]) Set(i int, v T) {
	if s.pages == nil {
		s.pages = make(map[int]*[pageSize]T)
	}
	p := s.pages[i>>pageBits]
	if p == nil {
		p = new([pageSize]T)
		s.pages[i>>pageBits] = p
	}
	p[i&(pageSize-1)] = v
}

func (s *Sparse[T]) Get(i int) T {
	if p := s.pages[i>>pageBits]; p != nil {
		return p[i&(pageSize-1)]
	}
	var zero T
	return zero
}

// s.Set(5, "a"); s.Set(1_000_000_000, "b"); s.Set(-3, "c")
// s.Get(1_000_000_000) == "b", s.Get(7) == "", страниц — 3
```
Отрицательные индексы тоже работают: `>>` арифметический, а `&` даёт смещение 0…1023.

| Вариант | Get | Set | Память | Когда |
|---|---|---|---|---|
| `map[int]T` | O(1) | O(1) | ~2× данных, без порядка | по умолчанию, точки разбросаны |
| отсортированные `[]int` + `[]T` | O(log n) | O(n) | минимум | построил один раз — много читаешь, нужен обход по порядку |
| страничный массив | O(1) | O(1) | страницы целиком | данные кластерами, нужна локальность |
| битовая карта + плотный массив | O(1) с popcount | O(n) | очень мало | множества, read-mostly (roaring bitmap, HAMT) |

**⚠️ Подвохи и версии Go**
- Отсутствующий элемент — нулевое значение `T`, как у обычного массива. Если ноль — допустимое значение, нужен признак наличия (comma-ok).
- Страничный вариант плох, если точки одиночные и разбросаны: на каждую выделяется страница на 1024 элемента.
- В интервью стоит уточнить: какая доля ненулевых, нужен ли порядок, чего больше — чтения или записи.

**🎤 Прямая речь**
> Сначала уточню профиль: насколько разрежены данные, нужен ли обход по порядку, чего больше — чтений или записей. Самый простой вариант — `map[int]T`: O(1), но map примерно вдвое тяжелее данных и без порядка. Если массив строится один раз, а потом читается, — два отсортированных слайса, индексы и значения, с бинарным поиском: компактно и обход по порядку бесплатный.
>
> Если ненулевые элементы идут кластерами — страничный массив, как таблица страниц в ОС: индекс делится на номер страницы и смещение, страница выделяется при первой записи. Это O(1) и хорошая локальность. Для множеств есть битовые карты вроде roaring bitmap.
