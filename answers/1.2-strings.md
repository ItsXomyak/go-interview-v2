### 1. Как устроена строка? Почему immutable, почему нельзя `s[0] = 'a'`?

**⚡ Суть**
Строка — неизменяемая последовательность байтов: заголовок из указателя на данные и длины, 16 байт. Байты обычно в [UTF-8](glossary.md#utf8), но гарантии нет. Изменить байт нельзя: `s[0] = 'a'` — ошибка компиляции.

**🔧 Под капотом**
- В рантайме строка — `{str unsafe.Pointer, len int}`. В отличие от C, нет завершающего нуля и нет capacity, как у слайса.
- Что даёт неизменяемость:
  - подстрока `s[i:j]` — новый заголовок над теми же байтами, без копирования, за O(1);
  - присваивание и передача в функцию копируют только 16 байт заголовка;
  - строку безопасно использовать как ключ map и читать из многих [горутин](glossary.md#goroutine) без синхронизации;
  - литералы лежат в [read-only секции](glossary.md#rodata) бинарника, одинаковые объединяются.
- `s[i]` возвращает **байт** (`byte`), а не символ.
- «Изменить» строку — значит создать новую:

```go
s := "hello"
// s[0] = 'H' // ошибка: cannot assign to s[0] (neither addressable nor a map index expression)
b := []byte(s) // копия №1
b[0] = 'H'
s = string(b)  // копия №2 → "Hello"
```

**⚠️ Подвохи и версии Go**
- **Утечка через подстроку:** маленькая подстрока держит в памяти всю исходную строку — например, ID, вырезанный из ответа на 10 МБ. Лечится `strings.Clone(sub)` (Go 1.18).
- Изменение байтов строки через `unsafe` ломает инварианты, а для литерала — `SIGSEGV`.
- Строка может содержать невалидный UTF-8 и нулевые байты — для Go это просто байты.
- `string(s[0])` — не первый байт, а символ с кодом этого байта: для `"привет"` получится `"Ð"`. Первый байт как строка — `s[:1]`.

**🎤 Прямая речь**
> Строка в Go — неизменяемая последовательность байтов. Под капотом это заголовок из двух слов: указатель на данные и длина, 16 байт на 64-битной платформе. Неизменяемость даёт много бесплатного: подстрока — это новый заголовок над теми же байтами без копирования, строки дёшево передавать, их безопасно читать из разных горутин и использовать как ключи map.
>
> Поэтому `s[0] = 'a'` не компилируется. Чтобы изменить строку, её конвертируют в `[]byte` или используют `strings.Builder` — и это всегда новая память. Из практических ловушек: подстрока держит всю исходную строку в памяти, поэтому кусок большой строки, который надо хранить долго, я отвязываю через `strings.Clone`.

### 2. Что такое `rune` и `byte`?

**⚡ Суть**
`byte` — алиас `uint8`, один байт. `rune` — алиас `int32`, одна кодовая точка Unicode (code point). Строка индексируется байтами, а `range` по строке выдаёт руны.

**🔧 Под капотом**
- Это алиасы, а не новые типы: `byte` и `uint8` полностью взаимозаменяемы, `%T` печатает `uint8` и `int32`.
- Рунный литерал `'я'` — нетипизированная рунная константа с типом по умолчанию `rune`; её значение — номер символа в Unicode (U+044F = 1103).
- 4 байт руны хватает на любую кодовую точку (максимум U+10FFFF).
- `[]rune(s)` декодирует [UTF-8](glossary.md#utf8) в массив кодовых точек по 4 байта на символ: удобно для посимвольной работы, но это аллокация и в 2–4 раза больше памяти.

```go
var b byte = 'A' // 65
var r rune = 'я' // 1103
fmt.Printf("%T %T %c %U\n", b, r, r, r) // uint8 int32 я U+044F

s := "мир"
fmt.Println(s[0], []rune(s)[0]) // 208 1084 — байт против руны
```

**⚠️ Подвохи и версии Go**
- **Руна ≠ видимый символ.** «é» может быть буквой `e` плюс комбинируемым акцентом (две руны); эмодзи с флагами и «семьями» — несколько рун. Для пользовательских символов (графем) нужна сегментация: `golang.org/x/text` или `github.com/rivo/uniseg`.
- Развернуть строку по байтам — значит сломать UTF-8. Разворачивают `[]rune` (с оговоркой про комбинируемые символы).
- `string(r)` для руны — нормально; `string(n)` для `int` — ловушка, которую ловит `go vet`.

**🎤 Прямая речь**
> `byte` и `rune` — алиасы: `byte` — это `uint8`, сырой байт, `rune` — это `int32`, кодовая точка Unicode. Строка в Go — последовательность байтов, поэтому `s[i]` возвращает `byte`, а `range` по строке декодирует UTF-8 и возвращает руны.
>
> Руна — ещё не «символ на экране»: буква с диакритикой может состоять из двух рун, а эмодзи — из нескольких. Для большинства задач рун достаточно: посчитать символы, развернуть кириллическую строку через `[]rune`. Если нужны именно видимые символы, использую сегментацию графем из `x/text` или `uniseg`.

### 3. Как в UTF-8 кодируется, сколькими байтами описан конкретный символ?

**⚡ Суть**
[UTF-8](glossary.md#utf8) — кодировка переменной длины: символ занимает от 1 до 4 байт. ASCII — 1 байт, кириллица — 2, большинство иероглифов и знак € — 3, эмодзи — 4. Длину символа показывают старшие биты его первого байта.

**🔧 Под капотом**

| Диапазон | Байт | Шаблон битов | Примеры |
|---|---|---|---|
| U+0000 – U+007F | 1 | `0xxxxxxx` | латиница, цифры |
| U+0080 – U+07FF | 2 | `110xxxxx 10xxxxxx` | é, кириллица, греческий |
| U+0800 – U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` | €, 世 |
| U+10000 – U+10FFFF | 4 | `11110xxx` + 3 × `10xxxxxx` | 😀 |

- Число единиц в начале первого байта — это длина символа; байты продолжения всегда начинаются с `10`. Поэтому из середины строки легко найти начало символа (самосинхронизация), а ASCII-байт никогда не встречается внутри многобайтного символа.
- Пакет `unicode/utf8`: `RuneLen`, `DecodeRuneInString`, `EncodeRune`, `ValidString`, константы `RuneSelf` (0x80 — граница ASCII) и `RuneError` (U+FFFD).
- Исходники Go — в UTF-8, поэтому строковые литералы тоже в UTF-8.

```go
for _, c := range []string{"a", "é", "п", "€", "世", "😀"} {
    fmt.Print(c, "=", len(c), " ")
}
// a=1 é=2 п=2 €=3 世=3 😀=4
```

**⚠️ Подвохи и версии Go**
- Строка в Go не обязана быть валидным UTF-8. Внешние данные проверяй через `utf8.ValidString`; `strings.ToValidUTF8` заменяет битые последовательности.
- Обрезка по байтам (`s[:10]`) может разрезать символ пополам — в логах и JSON появится мусор. Обрезать надо по рунам.
- В Java и JavaScript строки в UTF-16, поэтому «длина строки» в разных языках не совпадает — это важно на стыке систем.

**🎤 Прямая речь**
> UTF-8 — кодировка переменной длины, символ занимает от одного до четырёх байт. ASCII — один байт, кириллица — два, большинство иероглифов — три, эмодзи — четыре. Длину видно по первому байту: число ведущих единиц равно числу байтов символа, а байты продолжения всегда начинаются с `10`. Поэтому кодировка самосинхронизируется и совместима с ASCII.
>
> На практике это значит: обрезать строку по байтам опасно — можно разрезать символ, а данные извне стоит проверять на валидность через `utf8.ValidString`, потому что Go не гарантирует, что строка — валидный UTF-8.

### 4. Длина строки в байтах и в символах: что вернёт `len("привет")`? `utf8.RuneCountInString`

**⚡ Суть**
`len(s)` — число байтов: `len("привет")` = **12** (6 букв по 2 байта). Число символов (рун) — `utf8.RuneCountInString(s)` = **6**.

**🔧 Под капотом**
- `len` работает за O(1): длина хранится в заголовке строки.
- `RuneCountInString` работает за O(n): проходит строку и считает начала символов, с быстрым путём для ASCII.
- `len([]rune(s))` даёт то же число. Компилятор распознаёт этот шаблон и не создаёт слайс (проверено: 0 аллокаций), но для читаемости лучше `RuneCountInString`.

```go
s := "привет"
fmt.Println(len(s))                    // 12
fmt.Println(utf8.RuneCountInString(s)) // 6
fmt.Println(len([]rune(s)))            // 6
```

**⚠️ Подвохи и версии Go**
- Проверка «имя до 50 символов» через `len` для кириллицы фактически пропустит только 25 букв. Реши, что ограничиваешь — байты или символы. Например, `VARCHAR(n)` в PostgreSQL считает символы, а не байты.
- Руны ≠ графемы ([вопрос 2](#q1-2-02)).
- Невалидный байт считается одной руной (`RuneError`).

**🎤 Прямая речь**
> `len` у строки возвращает количество байтов, а не символов, и работает мгновенно, потому что длина хранится в заголовке. Для «привет» это 12, так как каждая кириллическая буква в [UTF-8](glossary.md#utf8) занимает два байта. Число символов считает `utf8.RuneCountInString` — уже за линейное время, проходом по строке; `len([]rune(s))` даёт то же самое.
>
> Это важно в валидации: лимит «50 символов» через `len` для кириллицы превращается в 25 букв. Поэтому на границах системы я явно решаю, что ограничиваю — байты для хранения или символы для пользователя.

### 5. Как работает `range` по строке? Чем отличается от итерации по индексу?

**⚡ Суть**
Цикл по индексу `s[i]` идёт по **байтам**. `for i, r := range s` декодирует [UTF-8](glossary.md#utf8): `r` — руна, `i` — байтовый индекс начала руны, и он прыгает на длину символа.

**🔧 Под капотом**
- Компилятор разворачивает `range` по строке в цикл с быстрым путём: байт меньше 0x80 (ASCII) — это и есть руна, индекс растёт на 1; иначе вызывается `runtime.decoderune`, и индекс сдвигается на 2–4.
- Невалидный байт даёт `r = utf8.RuneError` (U+FFFD) и сдвиг на 1, без [паники](glossary.md#panic-recover).
- Данные строки при этом не копируются.

```go
s := "héllo"
for i := 0; i < len(s); i++ {
    fmt.Print(s[i], " ") // 104 195 169 108 108 111 — байты, é занимает два
}
for i, r := range s {
    fmt.Print(i, ":", string(r), " ") // 0:h 1:é 3:l 4:l 5:o
}
```

**⚠️ Подвохи и версии Go**
- Индексы в `range` идут не подряд: `i` — не номер символа. Нужен номер — заведи счётчик или работай с `[]rune`.
- `for i, b := range []byte(s)` перебирает байты без копирования — компилятор это оптимизирует.
- Невалидные байты молча превращаются в U+FFFD. При обработке бинарных данных так можно их испортить — бинарь обрабатывай как `[]byte`.

**🎤 Прямая речь**
> Если идти по строке через индекс до `len`, получаем байты: `s[i]` — это `byte`, и многобайтный символ разваливается на части. `range` по строке декодирует UTF-8 на лету: на каждой итерации получаем руну и байтовый индекс её начала, поэтому индексы идут с пропусками — у «héllo» это 0, 1, 3, 4, 5.
>
> Под капотом компилятор делает быстрый путь для ASCII и вызывает декодер рантайма только для многобайтных символов, а битые байты превращает в `RuneError` без паники. Для текста я использую `range`, для бинарных данных и протоколов — индексы или `[]byte`.

### 6. Что происходит при конкатенации? Как эффективно склеивать много строк?

**⚡ Суть**
Строки неизменяемы, поэтому `+` создаёт новую строку и копирует обе части. В цикле `s += x` — это аллокация на каждой итерации и O(n²) копирования. Для многих частей используют `strings.Builder` (с `Grow`) или `strings.Join`.

**🔧 Под капотом**
- `a + b + c` в одном выражении — один вызов рантайма: он считает общую длину, делает одну аллокацию и копирует части. Если результат маленький (до 32 байт) и не убегает, используется буфер на [стеке](glossary.md#stack-heap) — вообще без аллокации.
- `strings.Builder` хранит `[]byte` и растит его как слайс, а `String()` возвращает строку **без копирования**, через `unsafe` поверх того же буфера. Поэтому копировать Builder после начала записи нельзя: [паника](glossary.md#panic-recover) `strings: illegal use of non-zero Builder copied by value`.
- `strings.Join` сначала считает итоговый размер — одна аллокация.
- `bytes.Buffer` — буфер для чтения и записи (`io.Reader` / `io.Writer`); его `String()` копирует данные.

Аллокации при склейке 100 частей по 10 байт (Go 1.26, `testing.AllocsPerRun`):

| Способ | Аллокаций |
|---|---|
| `s += p` в цикле | 99 |
| `strings.Builder` без `Grow` | 8 |
| `bytes.Buffer` + `String()` | 6 |
| `strings.Builder` с `Grow(1000)` | 1 |
| `strings.Join` | 1 |

```go
var sb strings.Builder
sb.Grow(len(parts) * 10) // размер известен заранее — одна аллокация
for _, p := range parts {
    sb.WriteString(p)
}
s := sb.String() // без копирования
```

**⚠️ Подвохи и версии Go**
- `fmt.Sprintf` для склейки медленный: [рефлексия](glossary.md#reflection) и упаковка в интерфейсы.
- `strings.Builder` не потокобезопасен и не копируется по значению — передавай `*strings.Builder`.
- Константы склеиваются на этапе компиляции: `"a" + "b"` ничего не стоит.
- Для 2–3 частей в одном выражении `+` — нормальный выбор; Builder нужен в циклах.

**🎤 Прямая речь**
> Так как строки неизменяемы, каждая конкатенация создаёт новую строку и копирует данные. В одном выражении `a + b + c` это одна аллокация — рантайм заранее считает общую длину. Но `s += x` в цикле даёт аллокацию на каждой итерации и квадратичное копирование: на ста частях я намерил 99 аллокаций.
>
> Для склейки в цикле беру `strings.Builder`: он копит байты в слайсе и отдаёт строку без копирования, а если вызвать `Grow` с известным размером, получается ровно одна аллокация. Для готового слайса строк — `strings.Join`, он тоже выделяет память один раз. `bytes.Buffer` нужен, когда буфер ещё и читают как `io.Reader`. Главное правило с Builder — не копировать его по значению, он из-за этого паникует.

### 7. Конвертация `string ↔ []byte` — всегда ли копирование?

**⚡ Суть**
По смыслу — да: строка неизменяема, а `[]byte` можно менять, поэтому конверсия копирует данные и обычно аллоцирует. Исключения — оптимизации компилятора, где копия незаметна, и ручной zero-copy через `unsafe` (Go 1.20+).

**🔧 Под капотом**
- Конверсии вызывают в рантайме `stringtoslicebyte` / `slicebytetostring`: аллокация и копирование. Маленький результат (до 32 байт), который не убегает, кладётся во временный буфер на [стеке](glossary.md#stack-heap).
- Компилятор обходится без копии, когда результат только читается и не переживает выражение:
  - поиск в map: `m[string(b)]`;
  - сравнение: `string(b) == "x"`;
  - части конкатенации: `"a" + string(b)`;
  - `for i, c := range []byte(s)`;
  - `switch string(b)`.
- Замер: `string(b) == s` — 0 аллокаций; `sink = string(b)` и `sink = []byte(s)` — по одной.
- Zero-copy вручную (Go 1.20+):

```go
s := unsafe.String(unsafe.SliceData(b), len(b)) // []byte → string
b := unsafe.Slice(unsafe.StringData(s), len(s)) // string → []byte
```

Цена — ответственность. После `[]byte → string` нельзя менять `b`: строка «изменится», сломаются ключи map и другие инварианты. После `string → []byte` нельзя писать в слайс: у литерала данные в read-only памяти, получишь `SIGSEGV`.

**⚠️ Подвохи и версии Go**
- Частые конверсии в горячем пути (парсинг, логирование) — главный источник лишних аллокаций. Лучше сразу работать в одном представлении: с `[]byte` через пакет `bytes` и `strconv.Append*`, или со строками.
- Старый трюк через `reflect.StringHeader` / `SliceHeader` устарел — используй `unsafe.String`, `StringData`, `SliceData`.
- `[]rune(s)` и `string(runes)` тоже копируют, да ещё и декодируют [UTF-8](glossary.md#utf8).

**🎤 Прямая речь**
> Семантически конверсия между `string` и `[]byte` всегда копирует данные: строка неизменяема, а слайс байтов можно менять, и они не могут делить память. В рантайме это аллокация и копирование, кроме маленьких неубегающих значений, которые помещаются во временный буфер на стеке.
>
> Компилятор умеет обходиться без копии там, где результат только читается: поиск в map по `string(b)`, сравнение, конкатенация, `range` по `[]byte(s)`. Для горячего кода есть zero-copy через `unsafe.String` и `unsafe.StringData` начиная с Go 1.20, но тогда я гарантирую, что байты больше никто не изменит, — иначе это неопределённое поведение. Чаще правильнее просто не конвертировать туда-обратно и работать в одном представлении.

### 8. Пакет `strings`: основные функции; новое в `strings`/`bytes`

**⚡ Суть**
`strings` — функции для поиска, разбиения, замены, обрезки и сравнения строк, плюс `Builder`. Пакет `bytes` повторяет то же для `[]byte`. Из нового: `Cut` и `Clone` (1.18), `CutPrefix` / `CutSuffix` (1.20), итераторы `Lines`, `SplitSeq`, `FieldsSeq` (1.24), `bytes.Buffer.Peek` (1.26).

**🔧 Под капотом**
- Поиск (`Index`, `IndexByte`, `Contains`, `Count`) реализован в `internal/bytealg` на ассемблере с [SIMD](glossary.md#simd)-инструкциями; для длинных образцов — алгоритм Рабина–Карпа. Поэтому `strings.Index` быстрее ручного цикла.
- `Split` и `Fields` создают слайс подстрок (подстроки делят память с исходной строкой). Итераторы `SplitSeq` / `FieldsSeq` (1.24) отдают части по одной, без слайса.
- `EqualFold` сравнивает без учёта регистра и без аллокаций — лучше, чем `ToLower(a) == ToLower(b)`.
- `NewReplacer` делает много замен за один проход.

| Задача | Функции |
|---|---|
| Поиск | `Contains`, `ContainsAny`, `ContainsRune`, `Index`, `LastIndex`, `IndexByte`, `HasPrefix`, `HasSuffix`, `Count` |
| Разбиение и склейка | `Split`, `SplitN`, `Fields`, `FieldsFunc`, `Join`, `Cut`, `CutPrefix`, `CutSuffix` |
| Замена | `Replace`, `ReplaceAll`, `NewReplacer`, `Map` |
| Обрезка | `TrimSpace`, `Trim`, `TrimLeft`, `TrimRight`, `TrimPrefix`, `TrimSuffix` |
| Регистр и сравнение | `ToLower`, `ToUpper`, `EqualFold`, `Compare` |
| Итераторы (1.24) | `Lines`, `SplitSeq`, `SplitAfterSeq`, `FieldsSeq`, `FieldsFuncSeq` |
| Прочее | `Repeat`, `Clone`, `Builder`, `NewReader` |

```go
before, after, ok := strings.Cut("key=value", "=") // "key" "value" true

for part := range strings.SplitSeq("a,b,c", ",") { // без промежуточного слайса
    fmt.Print(part, " ")
}

fmt.Println(strings.Trim("xxhixx", "xh"))    // "i"   — Trim убирает НАБОР символов
fmt.Println(strings.TrimPrefix("xxhi", "x")) // "xhi" — TrimPrefix убирает префикс один раз
fmt.Println(strings.Count("abc", ""))        // 4     — пустая подстрока: число рун + 1
fmt.Printf("%q %q\n", strings.Split("", ","), strings.Fields("")) // [""] []
```

**⚠️ Подвохи и версии Go**
- `Trim` и `TrimPrefix` — классическая путаница: `Trim(s, "xh")` убирает с краёв все символы из набора, а не подстроку.
- `strings.Split("", ",")` возвращает `[""]` — слайс из одной пустой строки, а `strings.Fields("")` — пустой слайс.
- `strings.Title` устарел (Go 1.18): неправильно определяет границы слов в Unicode. Замена — `golang.org/x/text/cases`. Она же нужна для регистра с учётом языка (турецкая `i`).
- Подстроки из `Split` держат исходную строку в памяти — если исходник большой, а части живут долго, делай `strings.Clone`.

**🎤 Прямая речь**
> В пакете `strings` есть всё базовое: поиск через `Contains`, `Index`, `HasPrefix`; разбиение и склейка через `Split`, `Fields`, `Join` и удобный `Cut`, который заменяет пару `Index` плюс срезы; замены через `Replace` и `NewReplacer`; обрезка через `TrimSpace` и `TrimPrefix`; сравнение без учёта регистра через `EqualFold`, которое не аллоцирует. Пакет `bytes` зеркалит то же API для `[]byte`.
>
> Поиск там реализован на ассемблере с SIMD, так что он быстрее ручных циклов. Из нового — `CutPrefix` и `CutSuffix` в 1.20 и итераторы `SplitSeq`, `FieldsSeq`, `Lines` в 1.24, которые отдают части без создания слайса. Из ловушек назову разницу `Trim` и `TrimPrefix`, `Split` пустой строки, который даёт слайс с одной пустой строкой, и устаревший `strings.Title`.
