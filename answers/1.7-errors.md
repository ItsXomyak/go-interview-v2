### 1. Что такое `error`? Как правильно обрабатывать ошибки?

**⚡ Суть**
`error` — встроенный интерфейс с одним методом `Error() string`. Ошибка в Go — обычное значение: функция возвращает её последним результатом, вызывающий код проверяет `if err != nil`. Правило обработки: каждую ошибку обрабатываешь **ровно один раз** — либо возвращаешь выше, добавив контекст, либо обрабатываешь на месте (логируешь, ретраишь, отдаёшь клиенту).

```go
type error interface {
	Error() string
}

func loadUser(id int) (*User, error) {
	row, err := db.Query(id)
	if err != nil {
		return nil, fmt.Errorf("load user %d: %w", id, err) // контекст + исходная ошибка
	}
	// ...
}
```

**🔧 Под капотом**
- `error` — обычный интерфейс, поэтому в памяти это пара «тип + указатель на данные» ([iface](glossary.md#interface-layout)). `nil` — это интерфейс без типа и без значения.
- `errors.New("x")` возвращает указатель на внутреннюю структуру, поэтому две ошибки с одинаковым текстом не равны: `errors.New("x") == errors.New("x")` — `false`. Сравнивают по идентичности значения, а не по тексту.

**⚠️ Подвохи и версии Go**
- **Логировать и возвращать одновременно** — антипаттерн: одна ошибка попадает в лог по разу на каждом уровне. Логирует тот, кто обрабатывает, обычно самый верхний уровень (HTTP-хендлер, воркер).
- **Не сравнивай текст ошибки** (`strings.Contains(err.Error(), "not found")`): текст меняется, сравнение ломается. Для проверки есть `errors.Is` и `errors.As` ([вопрос 4](#q1-7-04)).
- **Типизированный nil:** функция с результатом `error`, вернувшая nil-указатель своего типа, вернёт ошибку, не равную `nil`:
  ```go
  func check() error {
  	var p *ValidationError // nil
  	return p               // интерфейс с типом *ValidationError, != nil
  }
  ```
  Возвращай `nil` явно.
- Контекст пиши коротко и без слов «failed to», «error»: `load user 42: query: connection refused` читается как цепочка.

**🎤 Прямая речь**
> `error` в Go — встроенный интерфейс с одним методом `Error() string`. Ошибки — обычные значения: функция возвращает их последним результатом, а вызывающий проверяет `err != nil`. Исключений нет, поэтому путь ошибки виден прямо в коде.
>
> Главное правило — обработать ошибку один раз. Либо я возвращаю её выше и оборачиваю через `fmt.Errorf` с `%w`, добавляя контекст — что делал и с какими параметрами, — либо обрабатываю на месте: логирую, ретраю, отвечаю клиенту. Логировать и одновременно возвращать нельзя — получаются дубли в логах. И я никогда не сравниваю текст ошибки, для этого есть `errors.Is` и `errors.As`.

### 2. Sentinel errors, кастомные типы ошибок, обёртки — когда что?

**⚡ Суть**
Три способа сделать ошибку, которую вызывающий код сможет распознать:
- **sentinel** — заранее объявленное значение (`io.EOF`, `sql.ErrNoRows`): когда достаточно знать «что случилось»;
- **свой тип** (`*fs.PathError`): когда вызывающему нужны данные — какое поле, какой файл, какой код;
- **обёртка** (`fmt.Errorf("...: %w", err)`): когда нужно добавить контекст и сохранить исходную ошибку.

```go
var ErrNotFound = errors.New("not found") // sentinel

type ValidationError struct{ Field string } // свой тип

func (e *ValidationError) Error() string { return "invalid field " + e.Field }

return fmt.Errorf("find user %d: %w", id, ErrNotFound) // обёртка
```

**⚠️ Подвохи и версии Go**
- **Sentinel и экспортируемый тип — часть публичного API.** Пользователи начнут на них завязываться, поменять их — ломающее изменение. Поэтому экспортируй только ошибки, на которые вызывающий код реально должен реагировать.
- **Обёртка через `%w` тоже делает исходную ошибку частью API**: снаружи её найдёт `errors.Is`. Не хочешь раскрывать детали (например, ошибку драйвера БД) — оборачивай через `%v`, а наружу отдавай свою ошибку.
- Свой тип обычно делают с методом на указателе (`*ValidationError`) и возвращают указатель — тогда `errors.As` ищет `*ValidationError`.
- Альтернатива для поведения — маленький интерфейс: `interface{ Timeout() bool }` ([вопрос 6](#q1-7-06)).

**🎤 Прямая речь**
> Sentinel-ошибка — заранее объявленное значение вроде `io.EOF` или `sql.ErrNoRows`. Её хватает, когда вызывающему достаточно знать, что именно случилось. Свой тип нужен, когда к ошибке надо приложить данные: какое поле не прошло валидацию, какой путь, какой статус — как `fs.PathError`. Обёртка через `%w` добавляет контекст по пути наверх и сохраняет исходную ошибку для `errors.Is` и `errors.As`.
>
> Важно помнить, что экспортированные sentinel-ошибки и типы становятся частью API: на них завяжутся пользователи. Поэтому я экспортирую только то, на что вызывающий код должен реагировать, а детали реализации — например, ошибки драйвера — оборачиваю через `%v` или заменяю своей ошибкой.

### 3. Зачем врапать ошибки? Способы врапинга (`%w`, свой тип с `Unwrap`)

**⚡ Суть**
Врапинг добавляет к ошибке контекст — где и что делали — и сохраняет исходную ошибку внутри. В итоге и в логе понятная цепочка, и код может проверить причину через `errors.Is`/`errors.As`. Два способа: `fmt.Errorf` с `%w` (Go 1.13) или свой тип с методом `Unwrap() error`.

```go
var ErrNotFound = errors.New("not found")

err := fmt.Errorf("find user %d: %w", 42, ErrNotFound)
fmt.Println(err)                             // find user 42: not found
fmt.Println(err == ErrNotFound)              // false
fmt.Println(errors.Is(err, ErrNotFound))     // true
fmt.Println(errors.Unwrap(err) == ErrNotFound) // true

v := fmt.Errorf("find user %d: %v", 42, ErrNotFound)
fmt.Println(errors.Is(v, ErrNotFound))       // false: %v только склеивает текст
```

**🔧 Под капотом**
- `fmt.Errorf` с одним `%w` возвращает `*fmt.wrapError{msg, err}` с методом `Unwrap() error`. С несколькими `%w` (Go 1.20) — `*fmt.wrapErrors` с методом `Unwrap() []error`.
- Ошибки образуют дерево: `errors.Is` и `errors.As` обходят его в глубину, вызывая `Unwrap`.
- Свой тип с обёрткой:
  ```go
  type QueryError struct {
  	Query string
  	Err   error
  }

  func (e *QueryError) Error() string { return e.Query + ": " + e.Err.Error() }
  func (e *QueryError) Unwrap() error { return e.Err }
  ```

**⚠️ Подвохи и версии Go**
- `%w` vs `%v`: текст одинаковый, но `%v` рвёт цепочку — исходную ошибку больше не найти.
- `fmt.Errorf("ctx: %w", nil)` не вернёт nil, а напечатает `ctx: %!w(<nil>)`. Сначала проверяй `err != nil`.
- `errors.Unwrap` не разворачивает `Unwrap() []error`: для `errors.Join` и нескольких `%w` вернёт `nil`.
- Не каждую ошибку надо оборачивать: если контекст уже есть (например, `*fs.PathError` содержит путь), лишний слой только удлинит сообщение.

**🎤 Прямая речь**
> Врапинг нужен, чтобы по пути наверх добавлять к ошибке контекст — что делали и с какими параметрами — и при этом не терять исходную ошибку. В логе получается цепочка вроде «load user 42: query: connection refused», а код выше может проверить причину через `errors.Is` или `errors.As`.
>
> Обычно я оборачиваю через `fmt.Errorf` с `%w`. Если к ошибке нужно приложить данные, делаю свой тип с полем `Err` и методом `Unwrap`. Разница `%w` и `%v` принципиальная: текст одинаковый, но `%v` рвёт цепочку, и `errors.Is` исходную ошибку уже не найдёт. Иногда это и нужно — чтобы не раскрывать наружу детали реализации.

### 4. `errors.Is` vs `errors.As` vs `==`; `errors.AsType`

**⚡ Суть**
- `==` сравнивает конкретное значение и не видит обёрток.
- `errors.Is(err, target)` — есть ли в цепочке ошибка, равная `target`. Для sentinel-ошибок.
- `errors.As(err, &target)` — есть ли в цепочке ошибка нужного **типа**; если есть, кладёт её в `target`. Для своих типов.
- `errors.AsType[T](err)` (Go 1.26) — то же, что `As`, но с дженериком: возвращает значение и `bool`, без переменной-указателя.

```go
verr := fmt.Errorf("handler: %w", &ValidationError{Field: "email"})

var ve *ValidationError
if errors.As(verr, &ve) {
	fmt.Println("As:", ve.Field) // As: email
}
if ve, ok := errors.AsType[*ValidationError](verr); ok { // Go 1.26
	fmt.Println("AsType:", ve.Field) // AsType: email
}

_, err := os.Open("/no/such/file")
fmt.Println(errors.Is(err, fs.ErrNotExist)) // true
pe, ok := errors.AsType[*fs.PathError](err)
fmt.Println(ok, pe.Op, pe.Path)             // true open /no/such/file
```

**🔧 Под капотом**
- Обе функции обходят дерево ошибок в глубину: сама ошибка → `Unwrap() error` или каждый элемент `Unwrap() []error`.
- `Is` на каждом шаге сравнивает через `==` (если тип сравнимый) и вызывает метод `Is(target error) bool`, если он есть. Так тип может считаться равным другой ошибке:
  ```go
  var ErrClient = errors.New("client error")

  type StatusError struct{ Code int }

  func (e *StatusError) Error() string { return fmt.Sprintf("status %d", e.Code) }
  // любая 4xx «равна» ErrClient
  func (e *StatusError) Is(target error) bool {
  	return target == ErrClient && e.Code >= 400 && e.Code < 500
  }

  err := fmt.Errorf("call api: %w", &StatusError{404})
  fmt.Println(errors.Is(err, ErrClient)) // true
  ```
- `As` проверяет, присваивается ли ошибка типу `*target`, через [рефлексию](glossary.md#reflection) (`internal/reflectlite`), и вызывает метод `As(any) bool`, если он есть. `AsType` делает то же через дженерик и type assertion.

**⚠️ Подвохи и версии Go**
- `errors.As` [паникует](glossary.md#panic-recover), если `target` — не указатель на тип, реализующий `error`, или на интерфейс: `errors.As(err, ve)` вместо `&ve` — частая опечатка. `go vet` это ловит: `second argument to errors.As must be a non-nil pointer to either a type that implements error, or to any interface type`. `AsType` такую ошибку не допускает: всё проверяется при компиляции.
- Ищи тот тип, который реально возвращается: если возвращают `*ValidationError`, а ищешь `ValidationError` — не найдётся.
- `==` остаётся нормальным для ошибок, которые по контракту не оборачиваются: `if err == io.EOF` в цикле чтения. Но `errors.Is` безопаснее всегда.
- Версии: `Is`, `As`, `Unwrap` — Go 1.13; `AsType` — Go 1.26, документация теперь рекомендует его вместо `As`.

**🎤 Прямая речь**
> `==` сравнивает только верхнее значение и не видит обёрток, поэтому после `fmt.Errorf` с `%w` он перестаёт работать. `errors.Is` проходит всю цепочку и ищет конкретное значение — это для sentinel-ошибок вроде `sql.ErrNoRows`. `errors.As` ищет в цепочке ошибку определённого типа и записывает её в переменную, чтобы достать поля — например, путь из `fs.PathError`.
>
> С Go 1.26 есть `errors.AsType` — дженерик-версия `As`: `pe, ok := errors.AsType[*fs.PathError](err)`. Не нужна отдельная переменная, и не получится передать не тот указатель — `As` в этом случае паникует. Ещё тип может определить свои методы `Is` или `As`: например, любая ошибка с 4xx-статусом может считаться равной `ErrClient`.

### 5. Несколько ошибок сразу (`errors.Join`)

**⚡ Суть**
`errors.Join(errs...)` (Go 1.20) объединяет несколько ошибок в одну. `nil` среди них пропускаются, а если все `nil` — результат `nil`. `errors.Is` и `errors.As` находят любую из вложенных ошибок. Второй способ — `fmt.Errorf` с несколькими `%w`.

```go
j := errors.Join(ErrNotFound, &ValidationError{"name"})
fmt.Printf("%q\n", j.Error())             // "not found\ninvalid field name"
fmt.Println(errors.Is(j, ErrNotFound))    // true

m := fmt.Errorf("multi: %w; %w", ErrNotFound, os.ErrPermission)
fmt.Println(m)                            // multi: not found; permission denied
fmt.Println(errors.Is(m, os.ErrPermission)) // true

fmt.Println(errors.Join(nil, nil) == nil) // true
```

**🔧 Под капотом**
- `Join` возвращает `*errors.joinError` с методом `Unwrap() []error`; текст — сообщения через перевод строки.
- `Is`/`As` обходят такое дерево в глубину, по порядку элементов.

**⚠️ Подвохи и версии Go**
- `errors.Unwrap(j)` вернёт `nil`: он понимает только `Unwrap() error`. Чтобы получить список, приведи ошибку к `interface{ Unwrap() []error }`.
- Многострочный текст `Join` неудобен в однострочных логах — для логов иногда лучше `fmt.Errorf` с `%w; %w`.
- Где полезно: валидация всех полей сразу, ошибки из нескольких [горутин](glossary.md#goroutine), ошибка операции + ошибка `Close` в `defer` ([вопрос 11](#q1-7-11)).
- До Go 1.20 для этого брали `hashicorp/go-multierror` или `uber-go/multierr`.

**🎤 Прямая речь**
> С Go 1.20 несколько ошибок объединяются через `errors.Join` или через `fmt.Errorf` с несколькими `%w`. `Join` пропускает nil и возвращает nil, если ошибок не было, поэтому его удобно вызывать без проверок. `errors.Is` и `errors.As` находят любую вложенную ошибку — внутри это дерево с методом `Unwrap() []error`.
>
> Использую для валидации, когда хочу вернуть все ошибки полей сразу, для сбора ошибок из параллельных задач и для `defer f.Close`, чтобы вернуть и ошибку записи, и ошибку закрытия. Подвох — `errors.Unwrap` такие ошибки не разворачивает, он видит только одиночный `Unwrap`.

### 6. Recoverable vs fatal ошибки: как это сделано в пакете `net` и как делать в современном Go?

**⚡ Суть**
В `net` это сделано через поведенческий интерфейс `net.Error` с методами `Timeout() bool` и `Temporary() bool`: вызывающий код спрашивает не «какой это тип», а «можно ли повторить». `Temporary()` объявлен устаревшим в Go 1.18. Сейчас проверяют конкретную причину: `errors.Is(err, os.ErrDeadlineExceeded)`, `errors.Is(err, context.DeadlineExceeded)`, `Timeout()` через `errors.As`.

```go
type Error interface {
	error
	Timeout() bool // Is the error a timeout?

	// Deprecated: Temporary errors are not well-defined.
	// Most "temporary" errors are timeouts, and the few exceptions are surprising.
	// Do not use this method.
	Temporary() bool
}
```

**🔧 Под капотом**
Проверено на Go 1.26:
```go
c.SetReadDeadline(time.Now().Add(50 * time.Millisecond))
_, err := c.Read(buf)
fmt.Println(err)                                // read tcp 127.0.0.1:…->127.0.0.1:…: i/o timeout
fmt.Println(errors.Is(err, os.ErrDeadlineExceeded)) // true
var ne net.Error
fmt.Println(errors.As(err, &ne) && ne.Timeout())    // true

// HTTP-запрос с таймаутом контекста
_, err = http.DefaultClient.Do(req)
fmt.Println(err)                                // Get "http://…": context deadline exceeded
fmt.Println(errors.Is(err, context.DeadlineExceeded)) // true
```
- `Temporary()` всё ещё есть в стандартной библиотеке: например, `net/http.Server` при ошибке `Accept` проверяет `ne.Temporary()` и повторяет с паузой.

**⚠️ Подвохи и версии Go**
- Почему `Temporary` устарел: понятие «временная ошибка» не определено. Большинство таких ошибок — таймауты, а остальные исключения неочевидны.
- Современный подход:
  - проверять конкретные причины через `errors.Is`: `os.ErrDeadlineExceeded` (Go 1.15), `context.DeadlineExceeded`, `context.Canceled`, `syscall.ECONNRESET`;
  - для своих ошибок — маленький поведенческий интерфейс (`interface{ Retryable() bool }`) или sentinel вроде `ErrRetryable`, проверка через `errors.As`/`errors.Is`;
  - решение «повторять или нет» принимать на уровне, который знает про идемпотентность операции.
- `http.Client{Timeout: …}` даёт текст `context deadline exceeded (Client.Timeout exceeded while awaiting headers)`: `errors.Is(err, context.DeadlineExceeded)` — `true`, `errors.Is(err, os.ErrDeadlineExceeded)` — `false`. Надёжнее всего `errors.As` в `net.Error` и `Timeout()`.

**🎤 Прямая речь**
> В пакете `net` это решено поведенческим интерфейсом `net.Error`: у ошибки есть методы `Timeout` и `Temporary`, и код спрашивает не тип ошибки, а можно ли повторить операцию. Но `Temporary` с Go 1.18 объявлен устаревшим: понятие «временная ошибка» оказалось размытым — почти все такие ошибки таймауты, а остальные случаи неочевидны.
>
> Сейчас я проверяю конкретные причины: `errors.Is(err, os.ErrDeadlineExceeded)` для дедлайнов сокета, `context.DeadlineExceeded` и `context.Canceled` для контекста, `Timeout()` через `errors.As`. Для своих ошибок делаю маленький интерфейс вроде `Retryable() bool` или sentinel и проверяю через `errors.As` или `errors.Is`. А решение о ретрае принимаю там, где известно, идемпотентна ли операция.

### 7. Что такое panic? Когда её использовать? Что будет при `panic(nil)`?

**⚡ Суть**
Panic — аварийная остановка текущей [горутины](glossary.md#goroutine): обычное выполнение прерывается, выполняются отложенные (`defer`) вызовы, и если никто не вызвал `recover`, программа падает с кодом 2 и стектрейсом. Panic — для ошибок программиста и невозможных состояний, а не для ожидаемых ошибок вроде «файл не найден». `panic(nil)` с Go 1.21 превращается в `*runtime.PanicNilError`.

```go
defer func() {
	r := recover()
	fmt.Printf("%T %v\n", r, r) // *runtime.PanicNilError panic called with nil argument
}()
panic(nil)
```

**🔧 Под капотом**
- Рантайм сам [паникует](glossary.md#panic-recover) при ошибках выполнения. Значение паники реализует `runtime.Error`:
  ```
  runtime error: index out of range [5] with length 3
  runtime error: invalid memory address or nil pointer dereference
  runtime error: integer divide by zero
  assignment to entry in nil map
  ```
- `panic(v)` компилируется в вызов `runtime.gopanic`: он создаёт структуру `_panic` и по очереди выполняет отложенные вызовы горутины ([вопрос 10](#q1-7-10)).
- `PanicNilError` нужен, чтобы `recover()` после `panic(nil)` не возвращал `nil` — раньше это было неотличимо от «паники не было». Старое поведение возвращает `GODEBUG=panicnil=1`.

**Когда panic уместна:**
- нарушен инвариант, который «не может» нарушиться: недостижимая ветка `switch`, повреждённое внутреннее состояние;
- ошибка при инициализации, без которой программа бессмысленна: в `init` или `main` при старте;
- функции `Must*` для данных, известных при компиляции: `regexp.MustCompile`, `template.Must`. Неверный шаблон — ошибка программиста:
  ```
  regexp: Compile(`(`): error parsing regexp: missing closing ): `(`
  ```

**⚠️ Подвохи и версии Go**
- Не используй panic вместо ошибок в API библиотеки: вызывающий не ждёт паники, а `recover` на каждом уровне — плохой дизайн.
- Внутри пакета panic/recover иногда используют для выхода из глубокой рекурсии (так делает `encoding/json`), но наружу всегда отдают ошибку.
- Паника в HTTP-хендлере не роняет сервер: `net/http` ловит её для этого запроса. А паника в горутине, запущенной из хендлера, роняет весь процесс ([вопрос 8](#q1-7-08)).

**🎤 Прямая речь**
> Panic — аварийное завершение горутины: выполнение прерывается, отрабатывают defer'ы, и если панику никто не перехватил, процесс падает с кодом 2 и стектрейсом. Рантайм паникует сам при выходе за границы слайса, разыменовании nil и делении на ноль.
>
> Я использую panic только для ошибок программиста и невозможных состояний: недостижимая ветка, сломанный инвариант, фатальная ошибка конфигурации при старте, функции `Must*` вроде `regexp.MustCompile` для литералов. Всё ожидаемое — сеть, файлы, валидация — возвращаю как `error`. Про `panic(nil)`: с Go 1.21 `recover` вернёт не nil, а `*runtime.PanicNilError`, чтобы такую панику можно было отличить от её отсутствия. Старое поведение включается `GODEBUG=panicnil=1`.

### 8. Как работает `recover`? Поймает ли он панику из другой горутины? Что нельзя поймать?

**⚡ Суть**
`recover()` останавливает [панику](glossary.md#panic-recover) и возвращает её значение, но только если вызван **непосредственно в отложенной функции** во время паники. В остальных случаях возвращает `nil`. Панику из другой [горутины](glossary.md#goroutine) не поймать: каждая горутина ловит свои паники сама, иначе падает весь процесс. Не ловятся [fatal error](glossary.md#fatal-error) рантайма, `os.Exit` и `runtime.Goexit` — это не паники.

```go
// Паника → ошибка через именованный результат
func safeDiv(a, b int) (res int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	return a / b, nil
}

fmt.Println(safeDiv(6, 3)) // 2 <nil>
fmt.Println(safeDiv(1, 0)) // 0 recovered: runtime error: integer divide by zero
```

**🔧 Под капотом**
- `recover` компилируется в `runtime.gorecover`. Он возвращает значение, только если между `gopanic` и вызовом `recover` в [стеке](glossary.md#stack-heap) ровно одна «настоящая» функция — та, которую отложили. Поэтому:
  ```go
  func helper() { fmt.Println("helper recover:", recover()) }

  defer func() { helper() }() // helper recover: <nil> — две функции между gopanic и recover
  defer recover()             // не работает — ноль функций
  ```
- После успешного `recover` отложенная функция доходит до конца, рантайм раскручивает стек до функции, в которой был `defer`, и она **возвращается обычным образом** с текущими значениями именованных результатов. Код после места паники не выполняется.

**Другая горутина:**
```go
defer func() { fmt.Println("main recover:", recover()) }() // не напечатается
go func() { panic("in goroutine") }()
time.Sleep(100 * time.Millisecond)
// panic: in goroutine — процесс упал с кодом 2
```
Поэтому каждая горутина в долгоживущем сервисе, если она может паниковать, ставит свой `defer recover` — обычно через небольшую обёртку над `go` или в пуле воркеров.

**Что не поймать:**
- **fatal error** рантайма: `concurrent map writes`, `all goroutines are asleep - deadlock!`, `stack overflow`, нехватка памяти ([вопрос 9](#q1-7-09));
- **`os.Exit`** — завершает процесс сразу, отложенные вызовы не выполняются;
- **`runtime.Goexit`** — завершает горутину с выполнением defer'ов, но это не паника, `recover` вернёт `nil`;
- сигналы ОС (`SIGKILL`, OOM killer).

**⚠️ Подвохи и версии Go**
- `recover()` вне паники возвращает `nil` — его можно вызывать безусловно.
- Не глуши все паники молча: восстановился — залогируй значение и стек (`debug.Stack()`), иначе баг спрячется.
- `log.Fatal` вызывает `os.Exit(1)` — defer'ы не выполнятся, буферы не сбросятся.

**🎤 Прямая речь**
> `recover` работает только внутри отложенной функции, и только если вызван в ней напрямую, а не во вложенном хелпере. Тогда он останавливает панику и возвращает её значение, а функция, где стоял `defer`, возвращается обычным образом. Через именованный результат можно превратить панику в ошибку. В остальных случаях `recover` возвращает nil.
>
> Паника из другой горутины так не ловится: каждая горутина отвечает за себя, и непойманная паника в любой из них роняет весь процесс. Поэтому в горутинах сервиса я ставлю свой `defer` с `recover` и логированием стека. Совсем не ловятся fatal error рантайма — конкурентная запись в map, дедлок, переполнение стека, нехватка памяти, — а ещё `os.Exit` и `runtime.Goexit`, потому что это не паники.

### 9. ⭐ Чем отличаются panic, fatal error и throw? Почему конкурентная запись в map роняет процесс так, что `recover` не поможет?

**⚡ Суть**
- **panic** — штатный механизм: выполняются defer'ы, можно перехватить `recover`.
- **[fatal error](glossary.md#fatal-error)** — необратимая остановка процесса: рантайм печатает `fatal error: …` и стеки и завершает процесс с кодом 2. defer'ы не выполняются, `recover` не помогает.
- **throw** и **fatal** — внутренние функции рантайма, которые и вызывают fatal error. `throw` — когда виноват, скорее всего, сам рантайм; `fatal` — когда виноват код пользователя (например, гонка на map).

Конкурентная запись в map — это `fatal`: после гонки внутреннее состояние map может быть уже испорчено, и продолжать выполнение небезопасно.

**🔧 Под капотом**
- Map при записи переключает флаг `writing` и проверяет его. Видит, что другая [горутина](glossary.md#goroutine) пишет одновременно, — вызывает `fatal("concurrent map writes")` ([1.4 · 6](1.4-maps.md#q1-4-06)). Это не `gopanic`, а `fatalthrow`: процесс останавливается, defer'ы не запускаются.
- Из комментариев `runtime/panic.go`:
  - `throw` — «for runtime-internal fatal errors where Go itself, rather than user code, may be at fault»;
  - `fatal` — «equivalent to throw, but is used when user code is expected to be at fault for the failure, such as racing map writes». Его стектрейс короче: без системных горутин и кадров рантайма, пока не задан `GOTRACEBACK=system`.
- Примеры fatal error, проверено на Go 1.26:
  ```
  fatal error: concurrent map writes
  fatal error: all goroutines are asleep - deadlock!

  runtime: goroutine stack exceeds 1000000000-byte limit
  fatal error: stack overflow
  ```
  Нехватка памяти — `fatal error: runtime: out of memory`.

**⚠️ Подвохи и версии Go**
- Почему не panic: [паника](glossary.md#panic-recover) выполняет defer'ы, а они могут снова обратиться к той же испорченной map или другим структурам. Остановить процесс сразу безопаснее, чем работать с повреждёнными данными.
- Детектор гонок замечает гонку раньше: `go test -race` сообщит `WARNING: DATA RACE` даже без падения.
- Защита — `sync.Mutex`/`sync.RWMutex` вокруг map или `sync.Map` ([2.3](../ROADMAP.md#stage-2)).
- Переполнение [стека](glossary.md#stack-heap) тоже fatal: лимит стека горутины — 1 ГБ на 64-битных системах, поймать бесконечную рекурсию через `recover` нельзя.

**🎤 Прямая речь**
> Panic — штатный механизм: выполняются defer'ы, и её можно перехватить через `recover`. Fatal error — необратимая остановка: рантайм печатает «fatal error» и стеки и сразу завершает процесс, defer'ы не выполняются. Внутри рантайма для этого есть `throw` — когда сломался сам рантайм — и `fatal` — когда виноват код пользователя.
>
> Конкурентная запись в map — как раз `fatal`. Map замечает одновременную запись по флагу и останавливает процесс, потому что её внутренние структуры уже могут быть повреждены: если бы это была паника, defer'ы могли бы продолжить работать с испорченными данными. Так же падают дедлок «all goroutines are asleep», переполнение стека и нехватка памяти. Лечится не `recover`, а синхронизацией — мьютекс или `sync.Map` — и прогоном тестов с `-race`.

### 10. Порядок выполнения при панике

**⚡ Суть**
1. Выполнение функции останавливается в месте [паники](glossary.md#panic-recover); код после неё не выполняется.
2. Отложенные вызовы текущей функции выполняются в обратном порядке (LIFO).
3. Затем — отложенные вызовы вызывающей функции, и так вверх по [стеку](glossary.md#stack-heap) [горутины](glossary.md#goroutine).
4. Если какой-то defer вызвал `recover` — паника останавливается, функция с этим `defer` возвращается нормально.
5. Если никто не перехватил — печатается `panic: …` со стеком, процесс завершается с кодом 2.

```go
func inner() {
	defer fmt.Println("inner defer")
	panic("boom")
}

func middle() {
	defer fmt.Println("middle defer")
	inner()
	fmt.Println("after inner — не выполнится")
}

func main() {
	defer func() { fmt.Println("main recover:", recover()) }()
	defer fmt.Println("main defer")
	middle()
}
// inner defer
// middle defer
// main defer
// main recover: boom
```

**🔧 Под капотом**
- `runtime.gopanic` создаёт `_panic` и добавляет его в список паник горутины, затем по очереди запускает отложенные вызовы, поднимаясь по кадрам стека. С Go 1.14 большинство defer'ов «[open-coded](glossary.md#open-coded-defer)»: компилятор вставляет их прямо в код функции, а при панике рантайм находит их по метаданным функции.
- Паника внутри defer'а не отменяет первую: обе выводятся цепочкой, остальные defer'ы продолжают выполняться.
  ```go
  defer fmt.Println("defer 1")
  defer func() { panic("second") }()
  defer fmt.Println("defer 3")
  panic("first")
  // defer 3
  // defer 1
  // panic: first
  // 	panic: second
  ```

**⚠️ Подвохи и версии Go**
- Повторная паника тем же значением после `recover` (`panic(r)`) с Go 1.25 выводится одной строкой: `panic: first [recovered, repanicked]`. До 1.25 значение печаталось дважды: `panic: first [recovered]` и следом `panic: first`.
- `os.Exit` в defer'е или в любом месте обрывает всё: остальные defer'ы не выполнятся.
- Аргументы отложенных вызовов вычисляются в момент `defer`, а не в момент выполнения ([1.5 · 9](1.5-functions.md#q1-5-09)).

**🎤 Прямая речь**
> При панике функция сразу прекращает выполнение, и начинают работать отложенные вызовы: сначала текущей функции в обратном порядке, потом вызывающей и так вверх по стеку горутины. Если какой-то defer вызвал `recover`, паника останавливается, и функция, где стоял этот defer, возвращается как обычно. Если нет — рантайм печатает значение паники со стектрейсом и завершает процесс с кодом 2.
>
> Если внутри defer'а возникает новая паника, она не отменяет первую: оставшиеся defer'ы всё равно выполнятся, а в выводе будет цепочка из обеих паник. С Go 1.25 повторная паника тем же значением после `recover` печатается одной строкой с пометкой «recovered, repanicked».

### 11. Ошибка в `defer f.Close` — теряем? Как не потерять?

**⚡ Суть**
Да, `defer f.Close()` выбрасывает возвращённую ошибку. Для файлов на чтение это обычно не важно, а для **записи** — важно: часть ошибок записи проявляется только при `Close` (или `Sync`), и функция вернёт `nil`, хотя данные не сохранились. Решение — именованный результат и отложенная функция, которая объединяет ошибки.

```go
func writeFile(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, f.Close()) // не теряем ни ошибку записи, ни ошибку Close
	}()
	if _, err = f.Write(data); err != nil {
		return fmt.Errorf("write %s: %w", path, err)
	}
	return f.Sync() // данные дошли до диска, а не только до page cache
}
```

Проверка, когда `Close` возвращает ошибку:
```go
func broken(path string) error {
	f, _ := os.Create(path)
	defer f.Close() // ошибка выброшена
	f.Close()       // имитируем: файл уже закрыт
	return nil
}
// broken(p) → <nil>
// та же функция с defer func() { err = errors.Join(err, f.Close()) }() →
// close /…/f17.txt: file already closed
```

**🔧 Под капотом**
- `Write` для файла обычно кладёт данные в page cache ОС и сразу возвращается. Ошибки записи на диск (например, кончилось место на сетевой ФС) могут прийти только при `fsync` или `close`.
- `f.Sync()` вызывает `fsync`: после него данные на диске. Без него «успешно записанный» файл может пропасть при падении машины.
- Отложенная функция может менять именованный результат, потому что выполняется после `return`, но до фактического возврата.

**⚠️ Подвохи и версии Go**
- `errors.Join(nil, nil)` — `nil`, поэтому успешный путь не сломается.
- До Go 1.20 писали вручную: `if cerr := f.Close(); cerr != nil && err == nil { err = cerr }`.
- Для чтения `defer f.Close()` допустим: данные уже прочитаны, ошибка закрытия ни на что не влияет.
- Тот же приём нужен для `rows.Close()`, `tx.Commit()`, `resp.Body.Close()` и любых `Close`, которые сбрасывают буферы (`gzip.Writer`, `bufio.Writer` — у него вместо `Close` есть `Flush`).
- Повторный `Close` у `*os.File` безопасен, но возвращает `file already closed` — это можно использовать: явный `Close` в конце для проверки ошибки и `defer f.Close()` как страховка на ранних выходах.

**🎤 Прямая речь**
> `defer f.Close()` ошибку теряет. Для чтения это не страшно, а для записи — проблема: запись обычно попадает в page cache, и реальная ошибка — например, нет места на диске — может прийти только при `Close` или `fsync`. Тогда функция вернёт nil, хотя данные не сохранились.
>
> Поэтому для записи я делаю именованный результат `err` и отложенную функцию `err = errors.Join(err, f.Close())` — так возвращаются обе ошибки, а на успешном пути `Join` даёт nil. Если данные важны, перед закрытием вызываю `f.Sync()`, чтобы они точно дошли до диска. То же самое делаю с `tx.Commit`, `gzip.Writer.Close` и другими закрытиями, которые сбрасывают буферы.
